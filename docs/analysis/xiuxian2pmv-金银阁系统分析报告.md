## 二、机制还原

### 2.1 指令与解析

**唯一真实可用的指令形态**（正则捕获组）：

```
金银阁 <金额> [大|小|奇|偶|猜 [点数]]
```

| 输入 | `args` 元组 | 结果 |
|------|-------------|------|
| `金银阁10大` | `('金银阁','10','大',None)` | 猜大 |
| `金银阁 100 猜 3` | `('金银阁','100','猜','3')` | 猜点数 3 |
| `金银阁10` | `('金银阁','10',None,None)` | 提示"请输入正确的指令" |
| `金银阁10猜` | `('金银阁','10','猜',None)` | 提示"请输入正确的指令" |
| `金银阁10猜7` | `('金银阁','10','猜','7')` | 提示"请输入正确的指令" |
| `金银阁0大` | `('金银阁','0','大',None)` | 走 `price_num==0` 分支（**但仍会结算**，见 §3.4） |

⚠️ **正则缺陷**：`([大|小|奇|偶|猜])` 是**字符类**，`|` 被当成普通字符，因此 `金银阁10|` 也能匹配（`mode='|'`），随后落入"猜错"分支白扣一次灵石。同时正则**未加 `^...$` 锚定**，`"随便说点什么金银阁10大"` 也会触发。

⚠️ **文档与代码不符**：`完整文档.md:2688-2691` 写的是 `/金银阁`、`/猜大`、`/猜小` 三个指令——**这三个指令在代码里都不存在**，实际是单条正则。照文档配置的运营方会以为功能坏了。

### 2.2 结算流程（实际执行路径）

```
收到消息
 └─ Cooldown 检查（10s，按 user_id 隔离，parallel=1）
     ├─ limit_all_run / admin_debug 检查
     └─ CD 未到 → 提示"时间还没到"或静默 finish
 └─ check_user(event) → (isUser, user_info, msg)
     └─ user_id = user_info['user_id']        ← ★ user_info 为 None 时在此崩溃
     └─ if not isUser: 发提示 + finish()
 └─ user_message = get_user_info_with_id(user_id)   ← 与上一步重复查询
 └─ args[2] is None → 提示 + finish()
 └─ mode == '猜' 且点数非法 → 提示 + finish()
 └─ price_num = int(price)                    ← ★ 无上限
 └─ if stone < price_num: 发"金额不足"        ← ★★ 没有 finish()！继续往下走
 └─ elif price_num == 0: 发"走开走开"          ← ★★ 也没有 finish()！
 └─ value = random.randint(1, 6)              ← 无论上面是否报警都会掷骰
 └─ 6 个 if/elif 分支：
     ├─ 大赢 / 小赢 / 奇赢：+price，发骰子，发文本
     ├─ 偶赢：+price，发文本（漏骰子）
     ├─ 猜赢：+price*5，发文本（漏骰子）
     └─ else（输）：-price，发文本（漏骰子）
```

### 2.3 赔率与期望值（精确计算）

设单注 `S`，记账方式为**净额记账**（赢 = `+S`，输 = `−S`，下注额从不预扣）：

| 玩法 | 中奖条件 | 中奖概率 | 赢时收益 | 输时收益 | 期望值 EV |
|------|----------|----------|----------|----------|-----------|
| 猜大 | `value ∈ {4,5,6}` | 3/6 = 50% | `+S` | `−S` | `0.5S − 0.5S = **0**` |
| 猜小 | `value ∈ {1,2,3}` | 3/6 = 50% | `+S` | `−S` | **0** |
| 猜奇 | `value ∈ {1,3,5}` | 3/6 = 50% | `+S` | `−S` | **0** |
| 猜偶 | `value ∈ {2,4,6}` | 3/6 = 50% | `+S` | `−S` | **0** |
| 猜点数 | `value == 猜测值` | 1/6 | `+5S` | `−S` | `(1/6)·5S − (5/6)·S = **0**` |

**结论**：三种玩法期望值**全部精确为 0**，庄家优势（house edge）= 0。

这是本模块最有意思的设计判断失误：

- ✅ 从"不坑玩家"角度看很厚道；
- 🔴 从经济系统角度看，**赌场最核心的职能（货币回收水槽）完全失效**。真实赌场靠 2.7%~5.3% 的抽水长期回收货币，这里 0 抽水意味着：
  - 它不制造通胀（**包括 §3.2 的漏洞在内**——实测 EV=0，见 §3.2）；
  - 它也**不回收货币**，无法承担任何水槽职能；
  - 它唯一的效果是**把个人资产变成高方差随机游走**——玩家的灵石余额从"稳定增长曲线"变成"布朗运动"，长期看被方差吞掉的是玩家的**留存**而不是玩家的**余额**。
- ⚠️ 若要与"银行利息"（见经济系统报告）联动，会出现"存款吃无风险利息 → 取出来赌零和局"的荒诞结构：赌局本身不亏，但赌局的方差会让人反复存取，放大货币流通速度与服务器压力。

## 三、缺陷清单

严重度定义：**致命** = 可凭空产生货币 / 必崩；**高** = 功能异常或体验割裂；**中** = 代码质量与一致性；**低** = 风格与洁癖。

### 3.1 🔴 致命-1：未注册玩家必崩（空指针）

**证据**：`xiuxian_dufang/__init__.py:57-59`

```python
isUser, user_info, msg = check_user(event)
user_id = user_info['user_id']        # ← user_info 为 None 时抛 TypeError
if not isUser:
    ...
```

`check_user`（`xiuxian_utils/utils.py:81-99`）在玩家不存在时返回 `(False, None, "修仙界没有道友的信息，请输入【我要修仙】加入！")`。

**复现**：任意未注册账号在群里发送 `金银阁10大`。

**影响**：
- 抛 `TypeError: 'NoneType' object is not subscriptable`；
- `check_user` 精心准备的引导文案**永远不会被发出**（错误发生在它之前）；
- NoneBot 捕获异常后玩家收不到任何回复 → 玩家会反复尝试 → 日志刷屏。

**修法**：
```python
isUser, user_info, msg = check_user(event)
if not isUser:
    await _reply(bot, send_group_id, event, msg)
    await dufang.finish()
user_id = user_info['user_id']
```

> 这是**本项目的高发模式**：校验与使用顺序颠倒。同一仓库里其它模块（如 `xiuxian_bank`）也建议统一按"先判后用"重构。

### 3.2 🔴 致命-2：余额不足仍然结算 → 允许"无本金下注"并制造负余额

> ⚠️ **本节结论已被实测修正**。初稿曾判断此缺陷是"印钞机（期望 +50% 单注）"，经 20 万次/场景的 1:1 逻辑复刻实测后推翻：**它不创造货币（EV 恒为 0），但它把赌场变成了一条无抵押信贷线，并以约 50% 的概率把玩家送进负余额**。详见《金银阁深度分析与加固方案》§二。

**证据**：`xiuxian_dufang/__init__.py:93-106`

```python
if int(user_message['stone']) < price_num:
    msg = "道友的金额不足，请重新输入！"
    ... 发送 msg ...
    # ★ 这里缺少 await dufang.finish() 或 return
elif price_num == 0:
    msg = "走开走开，没钱也敢来这赌！"
    ... 发送 msg ...
    # ★ 这里也缺少 finish()

value = random.randint(1, 6)      # ← 无论余额是否充足都会掷骰
```

对比同文件 `:65`、`:76`、`:90` 三处校验分支**都正确调用了 `await dufang.finish()`**，说明这是纯粹的复制粘贴遗漏。

**复现**（余额 0，输入 `金银阁100大`）：
1. 收到"道友的金额不足，请重新输入！"；
2. **紧接着**又收到一条结算消息；
3. 50% 概率："最终结果为 5，你猜对了，收获灵石 100 块" → 余额 `0 → 100`；
4. 50% 概率："最终结果为 2，你猜错了，损失灵石 100 块" → 余额 `0 → **−100**`。

**实测数据**（1:1 逻辑复刻，每场景 20 万次）：

| 场景（余额 0，下注 100 万） | 单次期望 | 负余额率 | 余额范围 |
|---|---|---|---|
| 押大 | +850 | **49.96%** | −100 万 ~ +100 万 |
| 押小 | +1130 | 49.94% | −100 万 ~ +100 万 |
| 押奇 | +3560 | 49.82% | −100 万 ~ +100 万 |
| 押偶 | +4300 | 49.79% | −100 万 ~ +100 万 |
| 猜 3 | −1150 | **83.35%** | −100 万 ~ +500 万 |

> 期望值全部落在统计噪声内（σ≈100 万，标准误≈2236），**证实 EV = 0，不存在货币凭空产生**。

**真正的危害（重新定级：高危而非印钞）**：

1. **无抵押信贷**：赌注额无上限（`:91` 无校验），玩家可以在 0 余额下押任意金额。输掉的"债务"没有任何系统惩罚，且一次炼金（60 万~670 万）或几天签到即可抹平 → **债务是软约束**。
2. **击穿其它系统的不变量**：负余额会让别的模块崩溃。已实测：`偷灵石` 对被偷者计算 `randint(int(0.01*stone), int(0.5*stone))`（`base:1127-1128`），当 `stone < 0` 时区间反向，抛出 `ValueError: empty range in randint(-1, -50)`。
3. **双消息自相矛盾**：先发"金额不足"，再发"猜对了/猜错了"，运营一眼可见，属于必然被玩家发现并复现的 bug。
4. **权限若放开即失控**：当前是 `SUPERUSER`（见 §3.5），只有机器人主人能触发；一旦改成 `GROUP`，任何玩家都能把余额刷成任意负数，并连带触发上面第 2 条的崩溃链。

**修法**（二选一，推荐 A）：
```python
# A. 单一出口 + 预扣保证金（彻底杜绝此类问题）
if not (1 <= price_num <= MAX_BET):
    await _reply(..., "下注金额需在 1 ~ {MAX_BET} 之间"); await dufang.finish()
if int(user_message['stone']) < price_num:
    await _reply(..., "道友的金额不足，请重新输入！"); await dufang.finish()
sql_message.update_ls(user_id, price_num, 2)   # 先扣注
... 结算 ...
# 赢：update_ls(user_id, price_num + payout, 1)
```
```python
# B. 最小改动（治标）
if int(user_message['stone']) < price_num:
    ...
    await dufang.finish()      # 补上这一行
elif price_num == 0:
    ...
    await dufang.finish()      # 补上这一行
```

### 3.3 🟠 高危-1：金额无上限 → SQLite 整数溢出异常

**证据**：`:91` `price_num = int(price)`（无任何上限）→ `:112/158` 直接传给 `update_ls` → `xiuxian2_handle.py:388-393` 直接进 SQL 参数。

**复现**：`金银阁 99999999999999999999 大`（20 位数字，Python `int` 无压力）→ 若掷出大，`sqlite3` 抛 `OverflowError: Python int too large to convert to SQLite INTEGER`（int64 上限 9.22e18）。

**影响**：异常中断 → 玩家看到骰子但没看到结算文案（或反之），且**写库与发消息不同步**，产生"幽灵交易"。配合 §3.2，还能构造"扣款溢出但加款成功"的不一致状态。

**修法**：`MAX_BET` 常量 + 边界校验（同时防负数、防 0）。

### 3.4 🟠 高危-2：`price_num == 0` 同样漏 `finish()`，且是 `elif`

**证据**：`:100-106`。语义上"金额不足"与"金额为 0"是互斥的（`stone < 0` 才可能同时成立），但因为 `elif` 且两者都漏 `finish()`，`金银阁0大` 会先收到"走开走开，没钱也敢来这赌！"再收到一次完整结算（`+0` 或 `−0`，无实际收益但产生两条矛盾消息）。属于同一 bug 的孪生体，修 §3.2 时一并处理。

### 3.5 🟠 高危-3：权限写法错误 + 功能定位自相矛盾

**证据**：
- `:32` `permission=GROUP and (SUPERUSER)`
- `:28` `dufang_help = on_command("金银阁帮助", permission=GROUP, ...)`

**分析**：Python 的 `and` 返回第二个操作数，所以 `GROUP and SUPERUSER` **恒等于 `SUPERUSER`**——`GROUP`（群聊约束）被静默丢弃。也就是说：

| 对象 | 帮助 | 游玩 |
|------|------|------|
| 普通群成员 | ✅ 能看到 | ❌ 无响应（被权限静默吞掉） |
| 机器人主人（超管） | ✅ | ✅ |

后果：
1. **幽灵功能**：普通玩家看到 `· /金银阁帮助`（`xiuxian_base/__init__.py:98` 的帮助列表里有它），点开只看到"封群的，不建议玩！！！"，然后**永远无法游玩**，也不知道为什么。这是典型的"功能可见但不可用"体验事故。
2. **超管在群里玩博彩** = 把机器人账号本身暴露在风控面前，比普通玩家玩更危险。
3. 帮助文案（`:24-27`）**没有任何玩法说明**，只有一句警告——既不是帮助，也不是公告。

**修法**：
- 权限想表达"仅群聊"就用 `permission=GROUP`；想表达"仅超管"就写 `SUPERUSER` 并**同步从玩家帮助列表里删掉这一行**；
- 真正的开关应该是 `_config.disabled_plugins = ["dufang"]`（`xiuxian_utils/config.py:8-10` + `xiuxian/__init__.py:52-55`，`module.name[11:]` 即 `"dufang"`，逻辑正确、可用），而不是靠权限"藏"起来。

### 3.7 🟡 中危-2：无流水、无统计、无风控

- **无下注记录表**：只有 `stone` 字段被就地加减（`update_ls`），没有任何 `bet_records`。这意味着：
  - 无法审计"某人 3 天赢了 5 亿灵石"是否来自 §3.2 的漏洞；
  - 无法做输赢统计、无法做数据看板、无法回滚；
  - 出现纠纷时**无任何证据链**。
- **无风控**：没有单注上限、没有日累计上限、没有连败保护、没有"余额不足强制冷静"、没有与体力系统挂钩（对比其它玩法普遍使用 `stamina_cost`）。
- **无状态互斥**：全项目普遍用 `check_user_type`（`utils.py:47-78`）保证"闭关/悬赏/秘境"互斥，金银阁**完全没有校验**，可以在闭关中赌博。

## 五、经济影响评估

| 维度 | 结论 |
|------|------|
| 是否货币水槽 | ❌ **不是**。0 庄家优势 → 长期净回收为 0。若想当水槽必须引入抽水（如 1:0.9） |
| 是否通胀源 | ⚠️ 正常情况下**不是**；§3.2 的缺陷经实测也**不是**通胀源（EV=0），它制造的是负余额与无抵押信贷，而非新增货币 |
| 方差影响 | 🔴 极大。单次 ±100% 资产波动，且无单注上限 → 玩家可一把押上全部身家，形成"梭哈文化"，破坏成长曲线的可预期性 |
| 与银行联动 | ⚠️ 见经济系统报告：若银行有正利息，会形成"存款生息 → 取款赌博 → 赌赢再存"的循环，放大货币流通速度 |
| 与宗门联动 | ⚠️ 宗门有 `sect_used_stone` 捐赠体系，赌博的方差会冲击捐赠稳定性 |
| 财富分配 | 零和 → 不改变总量，但**显著加剧个体差距**（随机游走的吸收壁效应） |
| 数值量级 | 下注额无上限，与签到（1e4~5e4）、仙途奇缘（2e5~5e5）等产出口相比可跨越 3~4 个数量级 → **单次赌博即可覆盖数天的正常产出**，这是最致命的经济设计问题 |

**一句话**：在当前数值体系下，金银阁不是"娱乐玩法"，而是"用 10 秒 CD 换一次跨量级资产重估的按钮"。

## 六、合规与风控

作者自己在 `:25-26` 写下：

```
封群的，不建议玩！！！
超管可以调试，如果你真想玩并且不介意封群风险，可以让超管修改代码
```

这不是夸张。QQ 群内博彩类玩法面临的实际风险：

1. **关键词风控**：群内高频出现"赌""灵石 X 块"等模式化文案，容易触发腾讯的内容风控模型；
2. **CQ 骰子刷屏**：`[CQ:dice]` 是显式骰子消息，连续出现会被判定为赌博群特征；
3. **机器人账号风险**：超管用机器人账号在群里玩，风控命中对象是**机器人 QQ 号本身**，可能导致机器人被封（连带整个修仙插件下线）；
4. **群主风险**：群可能被降权或封停，而这是运营方最不可承受的损失。

**建议**：如果只是想要"随机娱乐"，把玩法从"博彩"改为**无货币输赢的抽奖/占卜**（如"摇骰定吉凶"给 buff、给小额彩头但**不扣本金**），既保留随机乐趣，又不构成赌博结构，风控风险下降一个数量级。

## 八、对 Java 版主项目（`E:\xiuxiangame\main`）的启示

### 8.1 值得借鉴（3 条）

1. **用 CQ 骰子展示真实随机值**：把服务端算出的 `value` 直接渲染成玩家可见的骰子动画，比"你输了"这种黑箱文案更能建立信任。Java 版若做抽奖/鉴定类随机，可用等价手法（前端动画 + 服务端签名结果）。
2. **赔率参数化 + 期望值显式化**：把 `(赔付倍率, 中奖概率)` 做成配置表，并在注释里写出 EV 算式。本项目 `XiuConfig` 集中配置的做法值得保留（虽然它把玩法数值和基础设施配置混在一起，见经济报告）。
3. **模块级开关**：`disabled_plugins` + `module.name[11:]` 的自动发现机制，比注释掉代码干净。Java 版可以用配置项控制功能模块是否注册。

### 8.2 必须避免（5 条）

1. **校验分支必须 `return`**：本项目最严重的系统性缺陷就是"校验后忘了 `finish()`/`return`"。Java 里务必用"卫语句（guard clause）+ 早返回"，禁止 `if (校验失败) { 提示(); }` 之后继续执行。
2. **先扣后结算（保证金模型）**：绝不要"赢了才加钱、输了才扣钱"的净额记账，那会让"余额不足"变成漏洞。正确顺序永远是：校验 → 扣款（事务）→ 结算 → 发货。
3. **不要用权限当功能开关**：`permission=GROUP and SUPERUSER` 这种写法既丢了 `GROUP` 约束，又制造了"看得到玩不了"的幽灵功能。
4. **金额必须做上下限与类型校验**：Java 的 `long` 一样会溢出，`Integer.parseInt` 一样会抛异常。下注/交易/捐赠类入口必须 `1 <= amount <= min(balance, MAX)`。
5. **赌博类玩法不要做成可自由下注的群聊功能**：合规风险（封群/封号）远大于收益。要做随机玩法就做"无本金输赢"的抽奖/占卜，或做成单机/私聊玩法。

### 8.3 当前主项目状态

已检索 `E:\xiuxiangame\main\src` 中的 `赌`/`博彩`/`gamble`/`casino` 关键词：**无匹配**——主项目目前没有博彩模块。本报告的价值在于**"反面教材清单"**：如果未来要加随机娱乐玩法，请直接按 §7.2 的 10 条改造点设计，绕开本项目的全部坑。
