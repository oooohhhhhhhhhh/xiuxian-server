## 1. 适配器架构总览

### 1.1 三层结构

```
config/adapters.json  ──►  AdapterConfigManager (静态单例缓存)
                                  │
                                  ▼
                        AdapterManager (静态门面 / 生命周期)
             ┌────────────┬───────┴────────┬──────────────────┐
             ▼            ▼                ▼                  ▼
     OneBotWebSocket   QqOfficial    MinecraftAdapter   第三方 ManagedAdapter
     OneBotScreenshot  Adapter       MinecraftPlayerAdapter (AdapterFactory 创建)
             │            │                │
             └────────────┴────────────────┴──►  CommandRegistry ──► Command.execute(CommandContext)
                                                        │
                                     ┌──────────────────┼──────────────────┐
                                     ▼                  ▼                  ▼
                          OneBotCommandContext  OneBotClientCommandContext  MinecraftCommandContext
```

关键点：**适配器本身几乎不含业务逻辑**，它们只做三件事——把外部协议消息归一化成
`CommandContext`、把 `Command` 的回复写回外部通道、以及维护"身份绑定"（QQ号/openid/MC UUID ↔ `user_id`）。
真正的玩法逻辑全部落在 `Command` 子类与 `game/service`。

### 1.3 配置来源与"双份配置"问题

- 配置入口：`AdapterConfigManager.CONFIG_FILE = "config/adapters.json"`（`adapter/AdapterConfigManager.java:22`），
  用 Gson 反序列化 `AdaptersConfig{ List<AdapterConfig> }`，缺文件时 `createDefaultConfig()` 落盘
  （`AdapterConfigManager.java:104-128`）。
- 仓库内已有实文件 `config/adapters.json`（33 行），只含 `onebot-default`（enabled=true, port 6700, mode ws_server）
  与 `minecraft-default`（enabled=false）。

**问题：配置源分裂成两份且互不一致。**

| 配置项 | 声明位置 | 实际读取处 |
|---|---|---|
| `onebot.port` / `onebot.mode` | `adapters.json` | `AdapterManager.java:321,330` ✔ |
| `onebot.send_mode` | `adapters.json` + `application.yml:143` | `OneBotWebSocketServer.java:433`（读 `AppConfig`，**adapters.json 里的值被忽略**） |
| `onebot.screenshot_window_title` / `poll_interval` | `adapters.json` + `application.yml:144-146` | `OneBotScreenshotBot.java:47-48`（读 `AppConfig`，**同上被忽略**） |
| `minecraft.jar_path` / `server_dir` / `java_path` / 内存 / `extra_jvm_args` | `adapters.json` + `application.yml:152-161` | `MinecraftServerProcess.java:47-56`（全部读 `AppConfig`，**adapters.json 的 minecraft 段整体无人读取**） |
| `minecraft-player.host/port/username/password` | 仅 `adapters.json` | `MinecraftPlayerAdapter.java:65-73` ✔ |

`application.yml:3` 的注释写着"OneBot/Minecraft 适配器的实际运行参数由 config/adapters.json 控制"，
而代码事实上只对 `mode/port` 与 `minecraft-player` 生效。运维改 `adapters.json` 的 `send_mode`、
`minecraft.max_memory_mb` 会**静默无效**。

更能说明问题的是同一个键名在两条通道上读的是两份配置：`send_mode`
在 QQ 官方适配器里读 `AdapterConfig`（`QqOfficialAdapter.java:312`），
在 OneBot 适配器里读 `AppConfig`（`OneBotWebSocketServer.java:433`）。
改一处生效、改另一处不生效，且没有任何文档说明差异。

### 1.4 与 `GameWebSocketApp` 的关系

`Main.java:240-241` 先创建 `GameWebSocketApp` 并注册到 Grizzly `WebSocketEngine` 的 `"/"` 路径；
`Main.java:268` 调用 `AdapterManager.setGameWebSocketApp(gameWebSocketApp)`；`Main.java:269` 才 `startAll()`。

但 **`AdapterManager` 中的 `gameWebSocketApp` 字段是只写不读的死字段**
（`AdapterManager.java:39` 声明、`:310-312` 赋值，全文件无任何读取点），
同文件的 `motdServer` 字段（`:40`、`:314-316`）同样如此——而 `setMotdServer` 在整个工程里**没有任何调用方**
（`Main.java:315` 使用的是自己的局部字段 `motdServer`）。
`AdapterManager.java:10` 的 `import com.mtxgdn.util.AppConfig` 也未使用。

也就是说：适配器层与 WebSocket 游戏主通道**实际上没有任何运行时耦合**，唯一的关联是二者共用
Grizzly 的 worker 线程池（`ServerConfigurator.java:36-44`，core=4 / max=8 / queueLimit=100）。

### 1.5 启动 / 停止顺序（`Main.java`）

1. `CommandScanner.scanAndRegister("com.mtxgdn.onebot.command")`（`Main.java:182`）——命令必须在适配器之前就位；
2. `I18nManager.load()`（`Main.java:188`）；
3. `PluginManager.loadPlugins()` → `BuiltInPluginRegistry.enableAll()`（`Main.java:191-205`）；
4. Grizzly REST 服务器启动（`Main.java:226-228`）+ `PluginWebManager.init`；
5. `GameWebSocketApp` 注册到 `"/"`（`Main.java:240-241`）；
6. `AdapterManager.startAll()`（`Main.java:269`）——此时 REST/WS 已就绪，适配器内可以安全回调业务；
7. `MinecraftMotdServer.start()`（`Main.java:315-329`）——MOTD 在适配器之后启动，与适配器无依赖；
8. 关闭：`Main.java:88` 注册 `AdapterManager.stopAll()` 钩子，`Main.java:575/591` 在 demo/nogui 退出路径上再次调用（幂等）。

`bootStarted` 标志（`AdapterManager.java:36,56`）用于区分"启动阶段"与"运行阶段"，
使得内置插件 `AdapterChannelPlugin` 的启停只在启动完成后才真正作用于通道。

## 2. OneBot 接入层详解

### 2.1 协议实现形态

**OneBot v11 正向 WebSocket 服务端**（bot 主动连过来），而非反向 WS / HTTP POST。

- 监听：`AdapterManager.java:330-348` 新建独立 `HttpServer` + `NetworkListener("onebot-"+id, "0.0.0.0", port)`，
  注册 `WebSocketAddOn`，再由 `WebSocketEngine.getEngine().register("", "/onebot", wsServer)` 绑定应用。
  默认端口 6700，**绑定地址硬编码为 `0.0.0.0`**（`AdapterManager.java:332`），不可配置。
- 应用类：`OneBotWebSocketServer extends WebSocketApplication implements OneBotMessageSender, OneBotAccountFlow`
  （`onebot/OneBotWebSocketServer.java:39-40`）。
- 入站分流（`OneBotWebSocketServer.java:199-215`）按字段存在性判断消息种类：
  `post_type` → 事件；`echo`+`status` → API 响应；`meta_event_type` → 元事件；否则 `log.warn("未知消息类型")`。
- 事件处理只实现 `post_type=message`（`OneBotWebSocketServer.java:280-288`），
  `notice` / `request` 分支是空的 `break`。
- 元事件只处理 `lifecycle`（`OneBotWebSocketServer.java:267-276`），用 `self_id` 建立 `sessionBots` / `botSessions` 双向映射。
- 出站动作（`action` 字段）：`send_private_msg`（`:466-481`）、`send_group_msg`（`:484-499`）、
  `send_private_forward_msg`（`:501-513`）、`send_group_forward_msg`（`:515-527`）、
  `get_group_member_info`（`:103-126`）、`set_group_ban`（`:1034-1049`）。
  每条动作都带 `echo=UUID.randomUUID()`（如 `:477`），但**没有任何 echo→回调的关联表**，
  业务侧完全依赖"把参数编码进 echo 字符串"这种旁路手法（见 2.6）。

### 2.2 鉴权：**完全没有**

- `OneBotWebSocketServer` 未覆写 `onConnect` 做任何 token 校验（`OneBotWebSocketServer.java:193-196` 只有两行日志）；
- 未读取 `Authorization` 头（全 `com.mtxgdn.onebot` 包内 `grep token|Authorization|auth` 仅命中一条注释：
  `onebot/command/map/MapCommand.java:169`）；
- `adapters.json` 的 onebot 段也没有 `access_token` 字段（`adapter/AdapterConfigManager.java:105-110`）。

后果：**任何能连上 6700 端口的人都可以伪装成"QQ 平台"**，向服务端推送
`post_type=message` + 任意 `sender.user_id`，从而以任意 QQ 号身份执行全部指令
（`/发放`、`/编辑玩家` 等管理指令仍受 `PermissionService` 保护，但**任何玩家的账号可被完全冒用**）。
监听地址又是 `0.0.0.0`，默认部署即为公网可达面。

### 2.3 消息解析

`handleMessageEvent`（`OneBotWebSocketServer.java:291-305`）：

```java
String messageType = json.get("message_type").getAsString();
String selfId      = json.get("self_id").getAsString();
String rawMessage  = json.get("raw_message").getAsString();
JsonObject sender  = json.getAsJsonObject("sender");
String senderQq    = sender.get("user_id").getAsString();
```

全部为 `get(...)` 无 `has()` 保护，任一字段缺失即 `NullPointerException`，
被 `onMessage` 的 `catch (Exception e)`（`:212-214`）兜住并只写日志——**消息被静默丢弃**。
同文件其他位置则使用 `json.has("x") ? ... : 默认值` 风格（如 `:270,297,420`），风格不统一。

命令识别与分词（`OneBotWebSocketServer.java:858-871`）：前缀集合 `"/" "." "！" "!"`，
`. / ！ / !` 会被归一化成 `/`，然后 `substring(1).split("\\s+", 2)` → `[cmd, arg]`，
`cmd` 转小写。CQ 码不做解析（`raw_message` 里若含 `[CQ:at,qq=...]` 会原样进入 `arg`）。

### 2.4 会话 / 上下文管理

三张 `ConcurrentHashMap`（`OneBotWebSocketServer.java:48-50`）：

| 字段 | 键 → 值 | 用途 | 清理 |
|---|---|---|---|
| `sessionBots` | `WebSocket` → `selfId` | 断线时反查 bot 号 | `onClose`（`:218-225`） |
| `botSessions` | `selfId` → `WebSocket` | 主动推送（黑名单续期） | 同上 |
| `pendingSessions` | `QQ号` → `PendingSession` | 多步向导状态机 | **仅 `/cancel` 或流程正常走完时移除** |

`PendingSession`（`:172-190`）是一个**裸 POJO 状态机**，状态集合为
`WAITING_USERNAME / WAITING_PASSWORD / WAITING_OLD_PASSWORD / WAITING_NEW_PASSWORD /
WAITING_DELETE_CONFIRM / WAITING_EMAIL / WAITING_CODE`（`handlePendingFlow` `:637-720`）。

**没有任何超时/过期机制**：玩家发起 `/注册` 后中途不发消息，条目永久驻留内存；
`pendingSessions` 也无容量上限。同时它是**跨会话的**——玩家在私聊里发起的向导，
在群聊里发下一句也会被消费（`handleGroupMessage` 不走 pending 分支，但 `handlePrivateMessage` 走，
所以群聊中不会被误消费，这一点是安全的；但私聊中"任意一条消息"都会被吞进向导，包括 `/帮助`）。

### 2.5 限流

- 命令级：`RateLimiter.allow("qq:" + senderQq, 10, 60)`（`OneBotWebSocketServer.java:327` 私聊、`:357` 群聊）
  ——**私聊与群聊共用同一个 key**，10 次/60 秒；
- 登录/改密/注销：`verifyUserCredentials` 内 `RateLimiter.allow("onebot_login_" + username, 5, 60)`（`:874-877`）；
- 验证码：`VerificationCodeService.canSendCode(email)`（`:693`）；
- 实现：`util/RateLimiter.java` 为内存滑动窗口，带 10 万条目上限与惰性清扫（`:37,81-117`），实现质量尚可。

注意：限流发生在**业务处理之后**——`processOfflineReward`（见 2.7）在限流判断之前执行（`:313-316` 早于 `:327`），
所以刷屏仍会触发每次消息一次离线奖励结算。

### 2.6 黑名单与自动禁言（echo 字符串当状态机）

- 每次群消息先 `blacklistService.isBlacklisted(senderQq)`（`OneBotWebSocketServer.java:346`），命中且该群开了自动禁言则调用
  `checkAndMuteBlacklistedUser`（`:995-998`）→ 发 `get_group_member_info` 查**机器人自己**是不是管理员，
  `echo` 编码为 `"check_admin_<groupId>_<targetQq>_<muteDays>"`（`:1007`）；
- 响应回来后在 `handleAdminCheckResponse`（`:1013-1032`）用 `echo.substring(...).split("_")` **反解参数**，
  再 `Long.parseLong(parts[0])` / `Integer.parseInt(parts[2])`；
- 另一条链路 `renewMuteForBlacklistedUsers`（`:65-101`，每 12 小时由 `muteRenewalScheduler` 触发）用
  `"renew_mute_..."` / `"check_target_admin_..."` 两套 echo 前缀做同样的事（`:128-170`）。

问题：
1. 用字符串拼接 + `split("_")` 传递参数，QQ 号/群号里只要出现 `_` 或解析失败即抛异常
   （`NumberFormatException` 被 `onMessage` 的 catch 吞掉，禁言静默失败）；
2. 三处逻辑（`check_admin_` / `renew_mute_` / `check_target_admin_`）是同一段代码的三个复制品；
3. `checkAndRenewMute` 里 `params.addProperty("user_id", selfId)`（`:108`）查的是机器人自身角色，
   与后续 `set_group_ban` 的目标不一致，语义靠注释维持。

### 2.7 每条消息都触发离线奖励结算

`handlePrivateMessage`（`:313-316`）与 `handleGroupMessage`（`:340-343`）在**任何一条消息**（不管是不是指令）上都会：

```java
QqBinding binding = bindingService.findByQq(senderQq);      // 1 次 DB
if (binding != null) processOfflineReward(socket, selfId, senderQq, binding.getUserId());  // 结算 + 可能 1 次私聊推送
```

`processOfflineReward`（`:232-265`）`new OfflineRewardService().processOfflineRewards(userId)`。
在群聊里这意味着：**任何人随便说一句话，机器人都会给该玩家发一条私聊离线奖励**（若满足结算条件），
且每句话至少 1 次 `qq_bindings` 查询。这是显著的性能与骚扰风险点。

### 2.8 账号流程（注册/绑定/改密/注销）直接写 SQL

`OneBotWebSocketServer` 内部自带一套 JDBC（`:873-991`）：
`verifyUserCredentials`、`incrementFailedAttempts`、`resetFailedAttempts`、`isUsernameExists`、
`insertUser`、`deleteUser`、`getUsernameByUserId`、`updatePassword`。

这些方法与 `com.mtxgdn.service.UserService` **职责完全重叠**（适配器层直接操作 `users` 表），
且 `BCrypt.checkpw` / `BCrypt.hashpw`（`:890,753,807`）在 Grizzly worker 线程上同步执行
（bcrypt cost 默认 10，约 50-100ms/次），直接把 IO 线程池（max=8）打成瓶颈。

注册流程还会做一次**跨资源的手工回滚**（`:820-828`）：

```java
} catch (RuntimeException e) {
    if (userId != null) {
        try { bindingService.unbindByQq(senderQq); } catch (Exception ignored) {}
        try { deleteUser(userId); } catch (Exception ignored) {}
    }
```

——`createPlayer` 失败后用户与绑定被删，但 `PermissionService.assignDefaultRole`（`:814`）写入的
`user_roles` 行不会回滚，留下孤儿角色记录。

### 2.9 截图机器人（`OneBotScreenshotBot`，526 行）

工作方式：`java.awt.Robot` 截屏 + `Runtime.exec("powershell ...")` 调 Win32 `FindWindow`/`GetWindowRect`
（`:63-82`）+ Windows.Media.Ocr 识别（`recognizeText` `:270-309`）+ 剪贴板粘贴发送（`:394-428`）。

**它实际上只实现了"发"，没有实现"收"。**
`pollOnce`（`:170-190`）检测到画面变化后 `onNewMessageDetected`（`:311-330`）→ `recognizeText` →
`processOcrResult`（`:332-340`），而后者**只有 `log.info`，从不调用 `CommandRegistry`**：

```java
if (!newText.isEmpty()) {
    log.info("OCR 识别到新消息: " + newText.substring(0, Math.min(200, newText.length())));
}
```

因此类注释（`:17-28`）宣称的"识别消息内容，解析指令"是**未完成的**：截图模式下机器人能回话，
但永远不会有指令被执行。同时它仍以 `OneBotMessageSender` 的身份被注册（`AdapterManager.java:323-327`），
`replyToSource/sendPrivateMsg/sendGroupMsg` 全部退化成 `simulateTyping + clickSend`（`:365-387`），
参数 `socket/selfId/targetQq` 完全被忽略——群聊回复里甚至会把 `[CQ:at,qq=...]` **当纯文本贴进 QQ 输入框**（`:370`）。

其它实现细节问题：`init()` 用 `800x600` 硬编码窗口尺寸推算坐标（`:133-141`），
找不到窗口时 `Thread.sleep(5000)`（`:125`）阻塞调用线程（即启动线程）。

### 2.10 日志

`util/OneBotLogger`（单例，`getInstance` 双检锁）提供 `logRecv / logSend / logSendToGroup / logSystem`，
`OneBotWebSocketServer` 在 `onMessage` 入口（`:200`）与每个出站动作前（`:112,124,479,497,511,525,1009,1046`）记录**完整原始 JSON**。
`PlayerActionLogger` 记录玩家动作（`:543,757,819`），`StatsCollector` 记录消息/命令计数（`:311,338,372`）。

风险：`logRecv(text)` 会把**玩家明文密码**（`WAITING_PASSWORD` 阶段的私聊内容）原样写入日志
（`OneBotWebSocketServer.java:200` 对每条消息无条件调用），
`handlePrivateMessage` 还有一行 `log.info("[私聊:" + senderQq + "] " + senderNickname + ": " + rawMessage)`（`:309`）
同样无条件打印全文；账号流程本身却反复强调"密码将在下一步通过私聊安全发送"（`:557`）。

## 3. 命令系统详解

### 3.1 基类 `Command`（`common/command/Command.java`，335 行）

构造器即注册（`:71-81`）：

```java
protected Command(String[] names, String description, String usage,
                  String category, String permission, boolean privateOnly, boolean requiresLogin) {
    ...
    CommandRegistry.register(this);   // 构造函数里的副作用
}
```

7 参构造 + 3 个便捷重载（`:83-95`），参数语义依次为
**别名数组 / 描述 / 用法 / 分类 / 权限码 / 仅私聊 / 需登录**。
分类排序表 `CATEGORY_ORDER` 硬编码 12 个中文分类（`:19-32`）。

两种"后置注入"的元数据：

- `setModule(String)`（`:103-105`）：绑定内置玩法模块，`isModuleEnabled()`（`:130-133`）查询

## 4. QQ 官方适配器（`qq/QqOfficialAdapter`，1 915 行）

### 4.1 与 OneBot 的定位差异

| 维度 | OneBot | QQ 官方 |
|---|---|---|
| 身份标识 | 真实 QQ 号（`sender.user_id`） | `openid`（按 AppID 隔离，与 QQ 号无关） |
| 接入方向 | bot 连服务端（正向 WS 服务端） | 服务端连腾讯网关（`wss://api.sgroup.qq.com/websocket`）或自建 webhook |
| 鉴权 | 无 | AppID+ClientSecret → access_token（`QQBot <token>`） |
| 收消息 | WS 文本事件 | WS 网关（op 0-11 协议）或 HTTP 回调（HMAC 签名） |
| 发消息 | WS `action` JSON | HTTP REST（`/v2/groups/{openid}/messages`、`/v2/users/{openid}/messages`） |
| 绑定表 | `qq_bindings` | `qq_official_bindings`（唯一键含 `app_id`） |
| 回复约束 | 无 | 被动回复窗口（群 5 分钟 / 单聊 60 分钟）+ `msg_seq` 递增 + 5 次上限 |

适配器通过实现 `OneBotSession / OneBotMessageSenderClient / OneBotAccountFlowClient`
（`QqOfficialAdapter.java:73`）复用全部命令与账号流程——这是本层**设计最好的一处**：
把"传输"和"业务"用 `OneBotSession`（`onebot/OneBotSession.java:7-28`）这层抽象隔开了。

### 4.2 启动与鉴权

`start(AdapterConfig)`（`:231-265`）：

1. `loadConfig(cfg)`（`:303-322`）读 `app_id / client_secret / gateway_url / sandbox / intents /
   command_prefix / send_mode / reconnect_interval_ms / remove_at / mode / webhook_*`，
   并按 `app_id` **重建** `QqOfficialBindingService`（`:307`）——openid 按 AppID 隔离，这一处隔离做对了；
2. 缺 `app_id/client_secret` 时**只打日志并 return**（`:251-255`），`started` 已置 true，
   于是 `AdapterManager` 会认为启动成功（`AdapterManager.java:360-364` 不检查返回值）；
3. `fetchAccessToken()`（`:402-440`）：`POST https://bots.qq.com/app/getAppAccessToken`，
   拿到 `expires_in` 后在 `expiresIn-60` 秒后由 `scheduler` 自我调度刷新（`:425-428`）；
   `getAccessToken()`（`:391-396`）在发送路径上**同步补刷**——网络阻塞会直接打到调用线程；
4. 模式分流：`webhook` → `startWebhook()`（`:271-295`）；否则 `connectGateway()`（`:444-469`）。

### 4.3 WebSocket 网关协议实现

`GatewayClient implements WebSocket.Listener`（内部类，`:503-682`）：

- opcode 处理（`:699-729`）：`10`(Hello→心跳间隔+Identify/Resume)、`11`(心跳 ACK)、`1`(服务端要心跳)、
  `0`(Dispatch)、`7`(Reconnect)、`9`(Invalid Session)；
- 心跳：独立单线程 `QQBot-Heartbeat`（`:578-588`），`tickHeartbeat` 在 `now - lastHeartbeatAck > interval*3`
  时主动断开重连（`:601-613`）；
- 重连：指数退避 `min(base * 2^attempts, 60s)`（`:474-478`），`reconnecting` 用 `AtomicBoolean` 去重（`:480-498`）；
- 事件分发（`:734-764`）：`READY / GROUP_AT_MESSAGE_CREATE / C2C_MESSAGE_CREATE / INTERACTION_CREATE /
  GROUP_ADD_ROBOT / GROUP_DEL_ROBOT`；
- **`onText` 里同步执行完整业务**（`:629-646`）：解析 → `handleGatewayPayload` → 命令执行 →
  `postApi` 阻塞 HTTP 回包。JDK `WebSocket.Listener` 的回调线程是 `HttpClient` 的执行器线程，
  一次 `/状态` 会在该线程上串行做完 3-12 次 DB 查询 + 1 次 HTTPS 请求。

群 openid ↔ 内部 Long 的映射是**进程内临时映射**：`getGroupId`（`:888-897`）用 `AtomicLong` 从 1 开始自增，
注释也承认"跨重启会变化"（`:886`）。后果：`msg_seq`/被动窗口在重启后失效，
`StatsCollector` 的群维度统计跨重启不可比。

### 4.4 消息类型与被动回复

发送前 `splitMessage`（`:1368-1390`）按 3 500 字符切分并优先在换行处断开；
`enrichGroupPassive`（`:1160-1184`）/ `enrichC2cPassive`（`:1190-1213`）补充 `msg_id / msg_seq / event_id`，
`msg_seq` 由 `LastMsg.replySeq`（`AtomicInteger`，`:182`）在本端递增——类注释（`:166-180`）明确记录了这个历史 bug
（曾从入站事件读 `msg_seq`，恒为 0，导致回复被平台批量去重），是本层**注释质量最高的一处**。

不足：`MAX_PASSIVE_REPLIES=5`（`:95`）超限时**只 `log.warn` 仍然发送**（`:1178-1181`）；
超出被动窗口时同样只 warn 然后不带 `msg_id` 直接发（`:1164-1169`），必然被平台拒绝，
用户侧表现为"机器人不回话"。

按钮（消息交互）：`buildKeyboard/buildButton`（`:1289-1336`）生成 `type=2` 回调按钮，
点击后 `INTERACTION_CREATE` → `handleInteractionCreate`（`:822-865`）→ `ackInteraction`（`:868-873`）
→ 把 `button_data` 当指令串补 `/` 前缀重新走分发。这条链路设计干净。

### 4.5 Webhook 模式（`qq/QqWebhookServer`，229 行）

实现质量**明显高于本层平均水平**：

- 端口白名单 `Set.of(80,443,8080,8443)`（`:41`），`start()` 前校验（`:83-87`）；
- 签名：`Base64(HMAC-SHA256(appSecret, timestamp+"\n"+nonce+"\n"+body))`（`:182-192`），
  `MessageDigest.isEqual` 常量时间比较（`:195-199`）；
- AppId 比对（`:135-139`）、时间戳新鲜度（`:202-210`，秒/毫秒自适应）；
- 4 线程固定池（`:90-94`）。

缺陷：① `eventHandler.accept(payload)`（`:166`）在 webhook 线程池里同步跑完整业务链，
而业务链内部又要同步 HTTP 回调腾讯 API —— 4 个线程被 4 个慢请求占满即全局阻塞；
② 无 nonce 去重缓存，同一 `(timestamp,nonce,body)` 在 5 分钟窗口内可重放（`maxSkewMillis` 默认 300 s，`:321`）。

`MinecraftAdapter`（307 行，单例 `getInstance()` `:22-26`）：

- UUID：正版模式查 Mojang API（`resolveFromMojang` `:246-270`，`HttpURLConnection` 超时 5 s），
  否则 `UUID.nameUUIDFromBytes("OfflinePlayer:"+name)`（`:243`）——**在玩家 join 时同步执行**（`:75`）；
- 分发：`handleMcCommand`（`:108-141`）**无权限校验**（见 3.3），`dispatchMcCommand`（`:143-172`）有 10 次/60 s 限流（`:146`）；
- `StringCollector`（`:284-306`）把回复收集成字符串供 REST 返回。

### 5.3 玩家身份直连（`MinecraftPlayerAdapter` + `MinecraftClient`）

`MinecraftClient`（**1 221 行**）是一个手写的 MC 协议客户端：

- `McProtocolMapper`（430 行）按协议号提供包 ID 与版本特性开关（`isLegacyChat / hasConfigPhase / hasLoginAck /
  componentsAreNbt / plainChatCommand / chatAckV2` 等，`McProtocolMapper.java:33-60`）；
- 支持 1.20.2+ 配置阶段（`runConfigPhase` `:249`）、`/reload` 触发的重新配置（`:621-626`）、
  压缩（`readPacket` `:999-1059` / `sendPacketRaw` `:1065-1108`，含 `Inflater` 循环解压的细节注释）、
  26.2 的 NBT 聊天组件与 ChatType 注册表私聊识别（`chatTypeIds` `:65`、`isIncomingTell` `:944`）；
- 读循环 `run()`（`:521-551`）与 `playReadLoop`（`:576-591`）在独立线程；
- `awaitPlayReady(15s)`（`:564-574`）用 `CountDownLatch` 等 PLAY 就绪，避免配置阶段发错包。

`MinecraftPlayerAdapter`（489 行）在此之上实现：自动 `/reg`、`/l` 登录（`performAutoAuth` `:153-177`，
首次登录状态记在 `config/mc-player-logins.json`）、只处理 `/tell` 私聊（`:195-197`）、
自己的一份 pending 会话与指令分发（`:270-345`）。

`MinecraftClient.readPacket` 存在**网络驱动的无上限内存分配**：
`int dataLen = VarInt.readVarInt(in); byte[] decompressed = new byte[dataLen];`（`:1013,1030`）——
服务端（或中间人）返回一个超大 `dataLen` 即触发 OOM，无任何上限校验（对比 MOTD 侧有 `MAX_PACKET_BYTES`）。
`readString` 的 `new byte[len]`（`:1111-1113`）同样无上限。

### 5.4 agent 与 Bukkit 插件：如何与主服务通信

两者是**同一个思路的两个实现**——把 `/xiuxian <子命令>` 通过 HTTP POST 转发到
`http://localhost:8080/api/mc-command`，主服务返回 `{ok, response|error}`，再回显给玩家。

**`agent/XiuxianAgent`（295 行）** —— `-javaagent` 方式，无插件依赖：

- `premain` 起守护线程，最多 80 次 × 3 s 轮询（`:27-40`）；
- `injectCommand`（`:42-96`）用反射找 `MinecraftServer` 实例（先静态字段、再遍历 `Thread.getAllStackTraces()`
  的 key，`:247-260`）→ `getCommands().getDispatcher()` → 用 `Proxy` 实现 `com.mojang.brigadier.Command`
  （`:69-78`）→ `LiteralArgumentBuilder.literal("xiuxian").executes(handler)` → `dispatcher.register(...)`；
- `handleCommand`（`:99-174`）从 `CommandContext.getSource()` 反推玩家名/UUID，再 `getInput()` 切子命令与参数；
- 通信：`postCommand`（`:176-206`）手拼 JSON 字符串、`parseResponse`（`:209-225`）用 `indexOf("\"response\":\"")`
  手工截取 —— **JSON 全靠字符串切割**，回复里含 `\"` 或换行即解析错乱。

**`plugin/XiuxianBridgePlugin`（120 行）** —— Bukkit 插件（`plugin.yml:3` 声明 `main`）：

- `onEnable` 里 `getCommand("xiuxian").setExecutor(this)`（`:38`）；
- `onCommand` 用 `getServer().getScheduler().runTaskAsynchronously(...)`（`:67`）异步转发，避免卡主线程 —— 方向正确；
- 但**在异步线程里直接 `player.sendMessage(...)`**（`:77,86,88`），违反 Bukkit 的线程约束（发送应回主线程调度）。

两条路径都把 URL **硬编码为 `localhost:8080`**（`XiuxianAgent.java:18`、`XiuxianBridgePlugin.java:33`），
主服务改端口即失联；且主服务侧对应端点 `McCommandResource` 无鉴权（见 3.3）。

## 8. 改进建议

### P0（安全 / 正确性，建议立即处理）

1. **给 OneBot WS 加鉴权**：在 `OneBotWebSocketServer.onConnect` 校验 `Authorization: Bearer <token>`
   （token 从 `adapters.json` 的 `access_token` 读取），不匹配直接 `close`；同时把监听地址改为可配置，
   默认 `127.0.0.1`（`AdapterManager.java:332`）。
2. **`/api/mc-command` 必须鉴权**：从 `JwtAuthFilter.java:25` 的白名单中移除，改为
   预共享密钥（HMAC 头）或独立 `admin` token；`mcUuid` 必须由服务端校验其来源可信，
   且在 `MinecraftAdapter.handleMcCommand` 内补齐与 `MinecraftPlayerAdapter.dispatchCommand` 等价的
   `privateOnly` + `permission` + 模块门控检查。
3. **修 `AdapterConfig` 缺失 `equals/hashCode`**：否则 `AdapterManager.reloadAll` 每次全量重启
   （也顺带把 1.5 节的"重启即断线"问题放大）。

   （有界队列 + 拒绝策略），QQ 网关侧在 `onText` 里同样 offload，`postApi` 改 `sendAsync`。
