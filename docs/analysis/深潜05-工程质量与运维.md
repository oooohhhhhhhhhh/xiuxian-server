## 0. 一句话结论

**"运维与部署"的完成度远高于"工程纪律"的完成度。**
这个项目的部署资产（systemd unit、Docker 多阶段构建、优雅停机、双路径基准说明）写得比大多数商业项目更细，注释里连"为什么必须 `Restart=always`"都解释了；但**构建流水线几乎没有质量门（无静态分析、无覆盖率、无依赖治理）**，测试虽然真实存在且质量不低（352 个用例、全绿、含并发与不变量测试），却**只覆盖了游戏服务层**——REST / WebSocket / QQ / 插件 GUI / 指令层合计约 **3.8 万行（占主代码 46%）处于零覆盖或近零覆盖**；CI 只有一个 workflow、无容器发布、无版本标签联动；仓库里仍躺着被跟踪的构建产物与 IDE 配置。

## 1. 构建系统

### 1.1 总体形态

- 单模块、无父 pom、无 `<dependencyManagement>`、无 `pluginManagement`。
- `pom.xml` 290 行，含 **35 行 XML 注释（12.1%）**，注释质量罕见地高——例如 `pom.xml:209-211` 解释为什么必须钉 `propertiesEncoding=UTF-8`（否则中文注释在非 UTF-8 机器上被写成乱码），`pom.xml:184-185` 解释为什么 `build-info.properties` 必须先从默认 resource 里排除再单独过滤。
- 坐标 `com.mtxgdn:main:0.1.0`（`pom.xml:7-12`），版本号被明确声明为**唯一来源**：资源过滤写 `build-info.properties`、shade 写 manifest、运行时由 `com.mtxgdn.util.BuildInfo` 读取（`pom.xml:9-11`）。这条"单一版本来源"有专门的回归测试守护（`src/test/java/com/mtxgdn/util/BuildInfoTest.java:11-19`）。

### 1.3 Java 23 的取舍

- `maven.compiler.release=23` 与 `source/target=23` 同时存在（`pom.xml:15-20`），实际以 `release` 为准，`source/target` 是冗余。
- **没有 `maven-enforcer-plugin` 的 `requireJavaVersion`，也没有 toolchain**。于是"必须 JDK 23"这条硬要求只体现在：`install.sh:40-42`、`install.bat:34-37`、`Dockerfile:16`、`.github/workflows/build.yml:31` 四个地方各写一遍。用 JDK 21 直接 `mvn package` 会得到 javac 的 `invalid target release: 23`，而不是一句可读的"需要 JDK 23"。
- 选 Java 23 的合理性：项目大量使用 `var`、`record`、文本块、`List.of` 等现代语法；真正收益主要来自"能写新语法 + 无 LTS 包袱"。**风险**：Java 23 是**非 LTS**版本，官方支持窗口短，`eclipse-temurin:23-jre` 基础镜像终将失去补丁；对一个要长期开服的 MUD 服务端，21 或 25(LTS) 更稳妥。

### 1.4 shade 打包与资源过滤

- 资源三段式（`pom.xml:181-203`）：
  1. `src/main/resources` 全量拷贝但**排除** `build-info.properties`；
  2. `src/main/resources` 只含 `build-info.properties` 且 `filtering=true`（版本号注入）；
  3. `src/main/java` 下的 `**/*.json` 作为资源（游戏数据与语言包与源码同目录）。
  这个"先排除再单独过滤"的顺序是正确的，注释也解释了为什么（`pom.xml:184-185`）。构建日志可佐证生效：`Copying 36 resources from src\main\resources` + `Copying 1 resource` + `Copying 2 resources from src\main\java`（`target/build-test.log:21-23`）。
- shade（`pom.xml:249-287`）：`ServicesResourceTransformer`（合并 SPI，关键）+ `ManifestResourceTransformer`（`mainClass=com.mtxgdn.Main` + 版本条目）+ 过滤签名文件。
- 实测产物体积：`target/main-0.1.0.jar` = **30.07 MB**，`target/original-main-0.1.0.jar` = **1.76 MB**（自研代码仅 1.76MB，**94% 是第三方依赖**）。其中 Jackson + jersey-client 是纯冗余（见 §1.2），粗略可回收 6-8MB。
- shade 会在仓库根写出 `dependency-reduced-pom.xml`（6,459 B）。该文件**被 git 跟踪**（见 §7.4），且内容已过期——缺少 `pom.xml:244-245` 新增的 `player-data.dir` / `wilderness.dir` 两个 `systemPropertyVariables`（对比 `dependency-reduced-pom.xml:54-56` 只有 `xiuxian.plugins.config`），其 mtime（2026-10-20 21:30）比 `pom.xml`（2026-10-21 21:47）早一天，正好印证"最后一次改 pom 后没有重新生成"。这正是"提交构建产物"的典型后果：它永远慢源码一步，且会误导后来者。

### 1.5 插件配置的缺口

| 缺失插件 | 缺失后果 |
|---|---|
| `maven-enforcer-plugin` | JDK 23 / Maven 3.9 版本要求不校验，新人首次构建体验差 |

| `jacoco-maven-plugin` | **无覆盖率数字**；"哪些包没测"只能靠人工比对（本报告 §2.5 就是这么手工做出来的） |

| `maven-javadoc` / `maven-source` | 发布到 GitHub Packages 的是无源码无文档的二进制，对"二次开发"定位的项目是减分 |
| `maven-release-plugin` | 发版流程手写（见 §3.3） |

### 1.6 profile 与特殊构建路径

- 唯一 profile `github`（`pom.xml:167-178`）只做 `distributionManagement`，URL 取自环境变量 `${env.GITHUB_REPOSITORY_URL}`。
- **Bukkit 插件源码被排除在 Maven 编译之外**（`pom.xml:222-226`：`<exclude>**/minecraft/plugin/**</exclude>`），改由 `build-mc-plugin.bat` 手工 `javac` 编译（`build-mc-plugin.bat:30-32`）。后果：
  - 该 1 个文件（120 行）**从不参与任何编译验证**，CI 与本地 `mvn package` 都不会发现它编译不过；
  - 构建脚本把 `MC_SERVER_JAR` 写死为 `mc_server\server.jar`（`build-mc-plugin.bat:13`），并要求 `lib\*` 存在，而仓库里没有 `lib/`；
  - 该脚本是 `.bat` 单平台，Linux 服务器（README 首推部署方式）无对应脚本。

### 2.3 测试风格判定

**不是"单元测试为主"，而是"以真实 SQLite 为载体的服务层集成测试"为主。**

- 42 个测试类中 **21 个继承 `TestBase`**（`TestBase.java:15-28`：`DatabaseManager.init(...)` 真实建库 + `I18nManager.load()` + `JwtUtil.init(true)`），另有 `MultiPlayerFullTest:102`、`CombatServiceTest:31` 各自独立 `DatabaseManager.init`。
- **Mockito 只出现在 1 个类**（`rest/LanguageRequestFilterTest.java:17-18,122-133`）。也就是说，全仓 352 个用例里只有 9 个用了 mock。设计意图很清楚：不做"测 mock"的假测试，而是"喂真库跑真逻辑"。
- 三种非典型但**很有价值**的手法：
  1. **反射静态分析**（`EndpointAlignmentTest:44` 收集全部 HTTP 路由 → method → 权限码；`AdminWritePermissionTest:23-40` 把"只读权限码不得门控写端点"变成可执行断言；`CommandNameConflictTest` 扫指令名唯一性）。这类测试没有运行时依赖，是纯架构护栏。
  2. **源码扫描**（`CommandMetaI18nTest:119` 用 `Assumptions.assumeTrue` 判断 `src/main/java` 是否存在后逐文件扫字面量）。它依赖**源码树在场**，在只跑 `test-classes` 的环境（如某些容器化测试）会静默跳过。
  3. **注入固定随机源**（`BreakthroughPityTest:38-39` 用 `RealmService.setRandomForTest`）。这是把"概率玩法"变成可断言逻辑的正确做法，避免了 `while(retry<1000)` 式的撞运气测试。
- **并发测试是真并发**（`TradeServiceConcurrencyTest:272-324`：2/4 个线程同时撤单与抢购，断言"只有 1 个成功"且"物品恰好退回一次"）。在 SQLite 单写者模型下用事务写锁串行化来验证守恒，是这套测试里技术含量最高的部分。

### 2.4 测试质量评价

**优点**

- **断言是行为断言，不是"跑通即通过"**。例如 `TradeServiceConcurrencyTest:293-294` 断言物品守恒（`撤单退回 + 买家获得 == 10`），`TradeServiceConcurrencyTest:243-244` 断言灵石守恒（`买家支出 == 卖家所得 + 抽成`）。这类不变量断言能抓住"普通功能测试发现不了的经济漏洞"。
- **每个测试类的 Javadoc 都写清了"为什么需要这个测试"**（历史 bug 编号、线上现象、曾长期红灯的原因）。例如 `PluginSwitchTestSupport.java:13-20` 完整记录了"探针插件开关残留在共享 `plugins.yml` 里 → 单独跑通过、全量跑失败"的假失败根因。这在开源项目里属于上游水平。
- **测试写文件的地方全部重定向**：surefire 把 `xiuxian.plugins.config` / `player-data.dir` / `wilderness.dir` 三个系统属性指向 `target/`（`pom.xml:236-246`），`TestBase.testDbFile()` 把库文件钉在 `target/test-db/`（`TestBase.java:38-42`）。工作区不会被污染，`mvn clean` 能带走全部测试产物。
- **契约型测试防"清单漂移"**：`BuiltInModuleSetTest`（插件清单 ↔ 配置键）、`MapWildernessTest`（采集配置里的物品 key 必须真实存在）。

**问题**

1. **存在 2 个空测试**：`PlayerServiceTest.java:41-51` 两个方法体都是 `Assertions.assertTrue(true)`，`@DisplayName` 却写着 `getFinalAttack should apply title bonus` / `addGold should increase player gold`。这类"假绿"比没有测试更糟——它会让覆盖率与用例数的统计虚高，也会让人误以为称号加成与金币增加已被覆盖。
2. **共享数据库 + 顺序耦合**。`TestBase` 的 `@BeforeAll` 会删除共享库文件，但 `LegacySchemaUpgradeTest.java:27-30` 自己承认：**Windows 上因连接池仍持有文件句柄，删库会失败**，于是前一个测试类插入的夹具行会污染后一个类——"曾导致 `MapServiceTest` 断言『15 个地点』时读到 16 个"。这是一个**已被记录、但未根治**的确定性隐患：它让"单独跑绿、全量跑红"成为可能，也让测试顺序变化可能改变结果。
3. **`@TestMethodOrder` 剧本式测试**（`MultiPlayerFullTest:47`、`CombatServiceTest:19`）依赖前序用例的副作用（前一个 `@Order` 建的角色被后一个用）。这类测试一挂就是连锁挂，且失败信息指向最后一个用例而非根因。
4. **"环境未就绪就 return"式跳过**：`TradeServiceConcurrencyTest.java:252,306` 等处有 `if (!ready) { System.out.println("  跳过（环境未就绪）"); return; }`。它**不会**记为 skipped，而是记为**通过**——并发测试最关键的几条断言可能在无人察觉的情况下被静默放弃。
5. **`MultiPlayerFullTest` 里有反射兜底**（`MultiPlayerFullTest:378-420` 用 `getDeclaredField("id")` 逐级找父类字段），一旦字段改名，测试不报错而是打印一行 `○`。这是把"失败"降级成"提示"。
6. **无覆盖率度量**，因此"哪些代码没被测"只能人工比对（本报告 §2.5 即是人工产物）。

### 2.7 surefire 配置评估

```xml
<!-- pom.xml:228-248 -->
<includes><include>**/*Test.java</include></includes>
<systemPropertyVariables>
  <xiuxian.plugins.config>${project.build.directory}/test-config/plugins.yml</...>
  <player-data.dir>${project.build.directory}/test-data/players</...>
  <wilderness.dir>${project.build.directory}/test-data/wilderness</...>
</systemPropertyVariables>
```

- ✅ 命名约定 `**/*Test.java` 与 42 个类的命名完全一致（无漏跑）；三个系统属性把写盘目录全部拨进 `target/`。
- ❌ **没有 `forkCount` / `reuseForks` / `parallel` / `argLine` / `excludedGroups` / `trimStackTrace`**。默认 `forkCount=1, reuseForks=true` → **全部 42 个类跑在同一个 JVM 里**，静态状态（`DatabaseManager` 单例、`BuiltInPluginRegistry` 单例、`CommandRegistry` 单例、`I18nManager`）跨类共享。这正是 §2.6 顺序耦合的根因。
- ❌ `TestBase.java:12-13` 的注释写"`surefire forkCount=0`"——**与 pom 不符**（pom 没有该项，实际是默认 fork=1）。注释与实际配置不一致，会误导后来者。
- ❌ 没有 `<excludes>` 把 `Mc26LiveSmokeTest` 之类环境依赖类排除，只靠 `@EnabledIfSystemProperty`（可接受，但 CI 里那个 `Skipped: 1` 就是它）。
- ❌ 无 `jacoco`，无 `argLine` 挂 agent，未来要接覆盖率需要改这块。
- ⚠️ `run_tests.sh:42-44` / `run_tests.bat:33-41` 仍在删除**仓库根目录**的 `test_combat.db` / `test_full.db` / `xiuxian_test.db`——这些文件自 `TestBase` 迁到 `target/test-db/` 后已不会产生，脚本的"清理"步骤已是**空动作**（历史遗留），会让人误以为清理生效。

**`build`（`.github/workflows/build.yml:47-85`）**
- `needs: test` + `if: github.event_name == 'push'` → PR 不发布；
- 用 `echo` 生成 `~/.m2/settings.xml` 写入 `GITHUB_TOKEN`（`:64-70`）；
- 版本改写：`BASE_VERSION`（`0.1.0`，**不含 `-SNAPSHOT`**）→ `NEW_VERSION=0.1.0-<sha>` → `mvn versions:set` → `mvn clean deploy -DskipTests -B -P github`（`:72-79`）；
- 上传 `target/*.jar` 为 `game-server-jar` 制品（`:81-85`）。

### 3.2 "是否真的会跑测试"——会，但只有一层

- ✅ **测试确实会跑**，且是发布的前置条件。workflow 注释本身记录了历史：`build.yml:18-20` "以前这里没有 test 阶段，deploy 直接 `-DskipTests` 打包装车，346 个用例在任何一次合并里都不会被执行"。这条注释是**这次改进的直接证据**（对应 `.git/logs/HEAD:210` 那条 `chore: 修工程质量类风险——CI 测试门禁、迁移可观测、测试不再污染工作区`，时间戳 `1792592472` = 2026-10-21 22:21）。
- ✅ `permissions` 是最小化的（`contents: read` + `packages: write`，`:9-11`）。
- ❌ **不用项目自带的 wrapper**（用 `mvn -B`），而本地/文档一律推荐 `./mvnw`；Maven 版本在 CI 与本地可能不同（`.mvn/wrapper/maven-wrapper.properties:7` 钉的是 3.9.9，CI 用 ubuntu-latest 预装版本）。
- ❌ **`mvn versions:set` 依赖未声明的插件**：`versions-maven-plugin` 不在 pom 中，CI 每次从中央仓库拉最新版 → 构建不可复现。
- ❌ **没有容器构建/发布**：仓库明明有 `Dockerfile` + `docker-compose.yml`，CI 却从不 `docker build`。而 Dockerfile 自己也承认"未在本机做过 docker build 验证（开发机没有 Docker）"（`Dockerfile:10-11`）——**这意味着镜像从未被任何机器验证过**，是本次分析里最"高危"的工程结论之一。
- ❌ **没有 tag / GitHub Release 流程**：`build.yml` 不创建 tag，不写 Release Notes，不联动 `CHANGELOG.md`。
- ❌ **没有 Windows 构建**：项目是 Windows 优先的（`.bat` 脚本、`.gitattributes` 给 `*.bat` 指定 CRLF、开发机是 Windows），但 CI 只有 ubuntu。`install.bat` / `run_tests.bat` / `start-low-memory.bat` / `build-mc-plugin.bat` **从未被自动验证**。
- ❌ **没有依赖/安全扫描**：无 Dependabot、无 CodeQL、无 `dependency-check`、无 `mvn dependency:tree` 差异门禁。
- ❌ **没有 MySQL 集成测试**：项目支持双库（SQLite/MySQL），CI 只跑 SQLite 路径。方言分支（`getForUpdateClause()` 等）在 CI 中永远走 SQLite 分支。
- ❌ **没有并发/顺序稳定性检查**：不重跑、不随机化顺序，`@TestMethodOrder` 之外的顺序耦合不会被发现。

### 3.3 发布流程现状（还原出来的实际流程）

1. 本地改代码 → 手动改 `pom.xml` 的 `<version>`（唯一来源）；
2. 手动更新 `CHANGELOG.md` 的 `[未发布]` 段（该段目前 **729 行**，`CHANGELOG.md:38-766`）；
3. `git push origin main` → CI 跑 352 个用例 → 通过后以 `0.1.0-<完整 sha>` 发布到 GitHub Packages + 上传 jar 制品；
4. **没有 tag、没有 Release、没有镜像、没有部署**——"发布"止步于"制品可下载"。

也就是说：**CI 到"制品"为止，CD 完全手工**（`deploy/xiuxian-server.service` 顶部 20 行就是人工升级手册）。

### 4.2 Dockerfile 逐段评价

**做得好的地方**

- 依赖层与源码层分离：先 `COPY mvnw .mvn/ pom.xml` 再 `dependency:go-offline`，再 `COPY src/`（`Dockerfile:22-29`），改代码不重下依赖。
- **用项目自带 wrapper 编译**，镜像内无需预装 Maven（`:25,29`）。
- 非 root 运行：`useradd --system --uid 10001`（`:62-63`）、`USER xiuxian`（`:79`）。
- `JAVA_OPTS` 默认面向小内存（`-Xmx512m -XX:MaxMetaspaceSize=256m`，`:42-44`），并在注释里给出原因（"本项目历史上多次出现 hs_err『out of physical RAM or swap space』"）。
- 把"两套路径解析基准"这个坑写进了注释并给出解法（`:51-58`）：jar 目录 == 工作目录 == `/app`，与 `Main.reportDeploymentPaths()` 的规则对齐。

**问题**

1. **从未被构建验证**（`Dockerfile:10-11` 自述）。CI 无 `docker build`，本地无 Docker → 这个文件目前是"看起来对"的。
2. **健康检查语义偏弱**：`HEALTHCHECK ... curl -s -o /dev/null http://127.0.0.1:${XIUXIAN_PORT}/api/game/status || exit 1`（`:76-77`）。注释说"未登录时返回 401 属正常，curl 不加 `-f` 时 401 仍退出 0"——这是**刻意利用 401 判定存活**。后果：进程活着但数据库断了、插件系统崩了、游戏逻辑挂了，容器依然 `healthy`。它只能发现"端口没监听"。
3. **`XIUXIAN_PORT` 与 `server.port` 双写**（`:44`、`:75`、`docker-compose.yml:43`）。改端口要改两处，注释已警告但无自动化校验。
4. **运行镜像装 `curl` 仅为健康检查**（`:47-49`），增加攻击面。
5. **`VOLUME ["/app"]` + 启动时覆盖 jar**（`:68` + `entrypoint.sh:24`）：jar 落进数据卷，虽然每次启动都会被覆盖（`entrypoint.sh:12` 解释了原因），但**卷里出现一个 30MB 的 jar** 会让"备份卷"变得笨重。
6. 基础镜像未按 digest 固定，`23-jre` 是非 LTS 标签。
7. 无 `STOPSIGNAL`（默认 SIGTERM 已正确，因为 `entrypoint.sh:33` 用 `exec`，信号能直达 JVM）——这点其实是对的。

### 4.3 docker-compose

- 单服务 + 命名卷 `xiuxian-state:/app` + `restart: unless-stopped` + `mem_limit: 1g`（`docker-compose.yml:25-63`）。
- **MySQL 只有注释级指引**（`:65-86`）：需要手工 `docker run` 一个 MySQL 并用 `--network container:xiuxian-server` 共享 localhost，再手改卷内 YAML。没有 `depends_on`、没有 mysql service 定义 → **"生产推荐配置"其实不可一键复现**。
- 安装向导的远程开关需要手工 `printf` 追加 YAML 再重启（`:8-12`），且这一步在 README 里也重复了一遍（`README.md:116-123`）——两处文档一致（好），但流程本身是"运维要手改配置文件才能完成安装"的脆弱设计。
- `mem_limit` 是 compose v2 字段，`1g` 上限 vs `-Xmx512m` + metaspace 256m，余量合理。

### 4.4 systemd 单元（本项目的运维亮点）

`deploy/xiuxian-server.service` 是全仓质量最高的一份运维资产：

| 行 | 配置 | 点评 |
|---|---|---|
| `:23-29` | `WorkingDirectory=/opt/xiuxian-server`（== jar 目录） | 直击"两套路径基准"问题，注释解释清楚 |
| `:46-48` | `StartLimitIntervalSec=10s` / `StartLimitBurst=5` | 防重启风暴，配置写错时不会无限拉起 |
| `:66-72` | `Restart=always` + `RestartSec=5s` | 注释解释为什么不能 `on-failure`（安装向导与 `/重启` 都是 exit 0） |
| `:74-78` | `KillSignal=SIGTERM` / `TimeoutStopSec=120` / `SuccessExitStatus=143` | 优雅停机 120s，与 `ServerShutdownHook` 呼应 |
| `:80-83` | `MemoryHigh=768M` / `MemoryMax=1G` | 双阈值，超限先限流后杀 |
| `:85-86` | `LimitNOFILE=65535` | 为 WebSocket 长连接准备 |
| `:88-108` | `ProtectSystem=strict` + `ReadWritePaths=/opt/xiuxian-server` + `NoNewPrivileges` 等 10 项 | 安全加固扎实 |
| `:110-112` | `StandardOutput=journal` + `SyslogIdentifier` | 日志归 journald，天然有轮转 |

- ⚠️ 与容器路径不同（systemd 用 `/opt/xiuxian-server`，容器用 `/app`），两套部署文档都要各自维护"路径基准"的解释。
- ⚠️ `ExecStart=/usr/bin/java $JAVA_OPTS -jar ...`（`:57`）依赖 systemd 的变量分词，`JAVA_OPTS` 里有引号/空格时行为与 shell 不同（默认值恰好安全）。

### 4.6 配置释放机制

- `AppConfig.java:36-62`：启动时若 `jarDir/config/application.yml` 不存在，则从 classpath 释放模板（打印 `[Config] 已自动释放配置文件`）。
- `YamlFileEditor.java:35-47,106-116`：写配置前若目标不存在也先释放模板，避免"无父节的裸缩进行"（对应 `AppConfigInsertTest`）。
- **风险**：释放是"只增不改"——已存在的配置文件**永远不会**被补充新版本新增的键。新版本加了 `world_boss.*`、`breakthrough.*`、`market.*` 等 20+ 个新键，老部署的 `config/application.yml` 里一个都不会出现，只能靠代码里的默认值兜底（`AppConfig.get(path, default)`）。这解释了为什么 `AppConfigSystemPropertyTest.java:18-21` 要专门守护"带默认值的重载也必须支持覆盖"——因为绝大多数调用点走的就是带默认值的那个。
- 配置升级是**单向**的：`deploy/xiuxian-server.service:36-37` 明确警告"数据库结构升级是单向的，跨大版本回滚前请先备份"。

### 4.7 日志

- 自研 `GameLogger`（`util/GameLogger.java`，262 行），**每次启动新建一个文件** `log/server-yyyyMMdd-HHmmss.log`（`GameLogger.java:41`），另有 200 条内存环形缓冲供 WebUI 实时日志（`:48-50`）。
- ❌ **无轮转、无大小上限、无保留策略**。工作区实测：`log/` 下 **62 个文件、10,696,629 B（约 10.2 MB）**，全部来自 2026-10-18 一天的调试。
- ❌ 默认级别 `DEBUG`（`application.yml:168`），生产环境会持续输出调试信息并快速堆盘。
- ✅ 容器/systemd 部署时输出同时进 stdout（systemd 走 journald 有轮转），只有裸跑时依赖文件日志。
- ✅ 日志里有启动路径报告 `Main.reportDeploymentPaths()`（`Main.java:263,495`），用于发现"两套基准不一致"，这是很好的可观测性设计。

### 4.8 备份

- 手工备份：`AdminResource.java:1999-2021` 提供 `GET /backup`（导出 DB，`Content-Disposition: attachment; filename="xiuxian_backup_..."`）与 `POST /backup/import`。

- ❌ **没有自动定时备份任务**（无 cron/无内置 scheduler 做 DB dump），没有保留代数、没有备份校验脚本。运维手册（`deploy/xiuxian-server.service:36-37`、`README.md:204-216`）只说"备份数据库与配置"，具体靠人。

### 4.9 健康检查与优雅停机

**优雅停机：做得相当完整。**

- `server/ServerShutdownHook.java:30-60`：注册 JVM shutdown hook，`createDefault()` 挂了 7 个任务（插件停用、文件监听、PlayerService、Formation、Farm、Cave、Buff）。
- `Main.java:86-119` 再补 8 个：`AdapterManager.stopAll()`、WebSocket `shutdownGracefully()`、MOTD server、坊市回收器、拍卖结算、玩家数据同步、内置模块停用、**数据库连接池关闭**。共 **15 个收尾任务**，顺序上"先停业务任务、最后关连接池"是正确的。
- 与 systemd 的 `TimeoutStopSec=120` 匹配；与容器 `exec java` + 默认 SIGTERM 匹配。
- ⚠️ 无测试覆盖（`server` 包 0 测试），且任务执行异常只 `LOG.warn`（`ServerShutdownHook.java:40-42`）——一个任务抛异常不会阻断后续任务（好），但也不会让停机"失败可见"。

**健康检查：偏弱。**

- 只有 `/api/game/status` 被当作探针，且**401 也算健康**（`Dockerfile:72-75`）。
- 没有分层探针（liveness vs readiness）、没有 metrics 端点、没有"数据库可用性"自检。
- 无 `docker-compose.yml` 里的 `healthcheck` 覆盖（`:52-59` 是注释掉的模板）。

### 5.3 默认值风险清单（按严重度）

1. **`admin.password_hash` = admin123**（`application.yml:103`）：安装向导会要求改密，但"直接编辑 YAML 跳过向导"的路径没有拦截。

### P0（一周内，风险最高）
