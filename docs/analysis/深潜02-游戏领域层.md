一个必须先说清的**全局口径问题**（贯穿全文，是本文发现的最大一类缺陷）：本层同时存在两套 id 语义 ——

* `players.id`（**playerId**，角色主键）
* `players.user_id`（**userId**，账号/绑定用户主键）

二者在 `PlayerService` 里分别对应 `getPlayerById(long playerId)` / `getPlayerInfoById(long playerId)` 与
`getPlayerRaw(long userId)`（`PlayerService.java:165`，SQL 是 `SELECT * FROM players WHERE user_id = ?`）。
**三个方法名里只有 `getPlayerRaw` 的形参叫 `userId`，其余都叫 `playerId`，且它们返回不同实体（`Player` vs `PlayerInfo`），
签名上完全无法区分。** 结果见 §6.1：**5 处把 playerId 传给了 userId 形参**（学技能 ×2、秘境 ×2、心魔 ×1），
**9 处把 userId 传给了 playerId 形参**（全部集中在遗留的 `onebot/command/pvp/PvpCommand`）。

## 2. 领域模型（entity）

### 2.1 数据模型总体形态

**没有 ORM，没有注解，没有任何 `@Entity`/`@Table`/JPA/MyBatis。** 全部持久化靠裸 JDBC：

* 表结构由 `com.mtxgdn.db.DatabaseMigration` 手工建表/迁移（本层不参与）。
* 每个 service 内部手写 `mapXxx(ResultSet)` 把行映射成对象。全层共 **19 个** 这类映射器：
  `PlayerService:1015 mapPlayerInfo`、`:1058 mapPlayer`、`SectService:2323/2346/2360/2372`（Sect/Member/Application/WarehouseItem）、
  `FarmService:949 mapPlot`、`WorldBossService:338 mapBoss`、`:745 mapDamage`、`TradeService:620 mapListing`、
  `SkillService:348 mapSkill`、`TechniqueService:426/451`、`CraftingService:357 mapRecipe`、`CaveService:341 mapCave`、
  `FormationService:338 mapFormation`、`RedeemCodeService:322`、`DailyService:407 mapDaily`、`RealmService:333 mapPlayerFromResultSet`。
* 写库同样手写：`PlayerService.updatePlayer:280` 一条 21 列的 UPDATE、`RealmService.updatePlayerWithConn:401` 一条 15 列的 UPDATE、
  `FarmService.persistSettledPlot:730` 一条 9 列的 UPDATE。**同一张 `players` 表被至少 4 个 service 各自写一套列清单**
  （`PlayerService:280`、`RealmService:401`、`PlayerService.addStat:761`、`PlayerService.addExperience:878`），列清单一旦漂移就会静默丢字段。

### 2.2 命名与约定

| 约定 | 现状 | 评价 |
|---|---|---|
| 包内分层 | `entity` 只放数据，`service` 放行为 | 基本遵守，但 `Monster.random/createBoss`（`Monster.java:73-113`）、`SpiritualRoot.drawRandom`、`CropConfig` 静态注册表把**生成逻辑/注册逻辑塞进了 entity** |
| 字段风格 | 私有字段 + getter/setter，无 Lombok | 一致 |
| 常量位置 | 领域常量放 entity（`Sect.MIN_LEVEL_CREATE`、`SectMember.ROLE_*`、`Cave.MAX_LEVEL`） | **好**：本层 28 个 `public static final` 领域常量集中在 entity，是少见的亮点 |
| 枚举 vs 字符串 | 角色（`SectMember.ROLE_LEADER="LEADER"`）用 String 常量，地块状态用真枚举 | 不一致；`sect_members.role` 靠字符串字面量在 6 处 SQL 里重复出现（`SectService:299, 1339, 1445`…） |
| 时间 | 全部 `long` epoch **毫秒** | 一致；但 `MapService.travel` 用 **秒**（`MapService.java:820`），`players.last_travel_time` 与其余列语义相反 |
| 金额 | `gold` 用 `long`，灵石用**分级物品表**而非列 | 合理，但导致"灵石余额"必须走 `players_items` 聚合，`ItemService.getSpiritStoneCount` 成为超级热点 |

### 2.3 DTO / 实体混用（本层最明显的建模债）

* `com.mtxgdn.entity.Player`（包外）是**可写业务实体**，`game/entity/PlayerInfo` 是**只读视图 DTO**，两者字段 90% 重合（各 ~25 字段），
  且 `PlayerService` 同时提供 `getPlayerById→Player` / `getPlayerInfoById→PlayerInfo` / `getPlayerByUserId→PlayerInfo` 三套读法。
  调用方经常随手选一个，于是同一处逻辑里 `Player` 与 `PlayerInfo` 混用（例：`SectService.createSect:205` 用 `Player`，
  `SectService.approveApplication:408` 附近用 `PlayerInfo`）。
* `MapService` 内部还有第三个影子类型 `RawPosition`（`MapService.java:799`）专为 CAS 保存"库里原值"，
  说明 `PlayerInfo` 无法表达 `current_location_id IS NULL` 这一状态 —— 领域模型没有为"位置未知"建模。
* `TeamService.Team`（`TeamService.java`）是**纯内存 POJO**，`memberIds` 是裸 `LinkedHashSet`，既非实体也无持久化，
  与其它 30 个"DB 实体"放在同一层，语义完全不同的两类模型混在一层。

### 2.4 关键的模型级问题

1. **`RealmConfig` 名称双口径**：`getName()` 走 i18n（`RealmConfig.java:176-178`），`getFullName()` 返回**原始 name 字段**（`RealmConfig.java:49-51`）。
   于是 `SectService:214`、`RealmService:302`、`RealmService:318` 展示给玩家的是**未本地化**名字，而别处是本地化名。
2. **`RealmConfig.isMaxRealm()` 硬编码 `id == 10 && subRealm == 0`**（`RealmConfig.java`），与配置驱动的设计目标相悖：加一个境界就必须改代码。
3. **`CurrencyEffect` 常量重复定义**：`SPIRIT_STONE_KEY` 与 `SPIRIT_STONE_LOW` 同为 `"mtxgdn:spirit_stone_low"`（`CurrencyEffect.java:8-13`）；
   `MAX_HOLD_PER_GRADE = {0, 999999, 9999, 99}`（同级）—— 下标 0 是占位、数值差两个数量级，属于典型的"魔法数组"。
4. **`Monster.random` 用 `random.nextLong(bound)`**（`Monster.java:73-113`）—— 该方法要求 Java 17+ 的 `Random.nextLong(long)`；
   项目声明 Java 23 所以能编译，但这把 entity 绑死在 JDK17+，且生成公式是纯魔法数：`hp = 5 + realm*12`、`attack = 30 + realm*35` 之类。
5. **`FarmPlot` 的品质只在结算瞬间掷一次**（`FarmService.settlePlot:669` 注释明确"只在此刻掷一次"），但 `determineQuality`
   读的是**旧水分**（`:666-668` 注释解释了原因）—— 这是正确的，但也意味着 `crop_quality` 是一个**不可重现的历史快照**，
   任何"重算品质"的管理台操作都会与线上值不一致。模型上应当把"品质掷骰种子"一并落库。

## 4. 玩法系统梳理

### 4.1 境界 / 修炼

* **配置驱动**：`realm_config.json` → `RealmConfigFile` → `GameConfigLoader`（`:240` 行，含缓存）。
  大境界 `realm` 0~10（凡人…金仙，见 `SecretRealmService.getRealmName:483-498` 的硬编码 switch —— 与配置重复），
  小境界 `subRealm` 0~N，`isMaxRealm()` 硬编码 `id==10 && subRealm==0`。
* **修炼收益**：`PlayerService.cultivationMultiplier:424` 八重连乘，`calculateCultivationExp:415` 全程 double 累乘、最后一次性取整
  （`:410-413` 注释解释了"每秒取整会吞掉 1.05 倍率"的问题）—— 这是正确的做法。
* **突破**：`RealmService.tryBreakthrough:123` → 冷却 → 成功率（基础 + 灵根 + 天劫属性 + 渡劫丹 + 保底）→ 天劫随机类型 → 成功/失败惩罚。
  成功率夹在 `clampRate:604`。
* **巩固（consolidation）**：`consolidate:211`，层数上限 `consolidateMaxLayers()`，每层降低突破率 `consolidateRatePenalty()`，
  失败时额外惩罚 `consolidatePunishBonus()` —— 常量全部走静态访问器（便于测试注入），是好实践。
* **闭关**：`beginCultivation:462` 有"脏数据自愈"分支（`:470-482`：`is_cultivating=1` 但 `cultivation_start_time=0` 时按重新闭关处理并记日志）。

    资源扣减下沉到 `WildernessChunk.consume/refund/restock/markExplored` 的**分片级 `synchronized`**（`:106, 118, 129, 169`）——
    粒度比整表锁更细，且 `markExplored` 置 `pinned=true` 保证"已探索的永不回收"（`:169-180`）。
  * 采集：`MapService.gather:1742` 从**玩家当前所在野外节点**取第一个可用资源 → `chunk.consume` 扣库存 → `chunkStore.save` →
    `addItem` 发物品；发物品或写 `last_gather_time` 失败时 `chunk.refund` + 再存盘回滚（`:1792-1810`）。
* **缺陷**：`MapService` 的 `locationCache`/`wildernessCache`/`wildernessStubCache` 三个缓存**全部无同步**（§6.4）；
  `WildernessChunkStore.load` 是**全局 `synchronized`**，分片装载串行化（单锁瓶颈，但比错更好）。

## 6. 质量问题清单

> 严重度：**高** = 功能失效/数据错乱/资损；**中** = 性能/可维护性显著受损或有潜在风险；**低** = 风格/一致性。

### 6.1 【高】playerId / userId 语义混用 —— 5 处把 playerId 传给 userId 形参

`PlayerService.getPlayerRaw(long userId)`（`PlayerService.java:165`）按 `user_id` 查询，但以下调用点传入的是 **playerId**：

| 调用点 | 传入 | 后果 |
|---|---|---|
| `SkillService.java:143`（`learnSkill(playerId, skillId)` 内） | playerId | 境界/金币/灵石校验读到**另一个角色**，或 `null` → 一律回"角色不存在" → **花钱学技能整条链路失效** |
| `SkillService.java:225`（`learnSkillFromBook` 内） | playerId | 技能书无法使用 |
| `SecretRealmService.java:501`（`enterRaid(leaderId, ...)` 内） | playerId | 团队副本入口失效（调用方 `GameResource:2550` 传 `player.getId()`、`TeamCommand:122` 传 `p.getId()`） |
| `SecretRealmService.java:532`（团队逐成员） | playerId | 同上 |
| `HeartDemonService.java:38`（`processCultivationWithCave(playerId, ...)` 内） | playerId | 心魔结算取不到人 → 直接返回原经验（调用方 `OfflineRewardService:88`、`CaveService:239` 传的都是 playerId） |

反向问题（把 userId 当 playerId 用）集中在**遗留 PVP 指令** `onebot/command/pvp/PvpCommand.java`，共 **9 处**：
`:95 acceptChallenge(userId)`、`:103 rejectChallenge(userId)`、`:115 createChallenge(userId, ...)`、
`:139 pveFight(userId, ...)`、`:153 pveFight(userId, ...)`、`:164 playerIds.add(userId)`（随后传给 `raidBossFight`）、
以及 `:128/144/158 getPlayerInfoById(userId)` —— 只要 `players.id != players.user_id`，**整条指令族全部失效**
（`getPlayerInfoById` 取不到人，先回"你还没有角色"）。

**根因**：三个方法名（`getPlayerById` / `getPlayerInfoById` / `getPlayerRaw`）在签名上无法区分 id 域，且返回类型不一致。
**建议**：引入 `PlayerId` / `UserId` 值对象（record），或在方法名上强制前缀（`getPlayerByPlayerId` / `getPlayerByUserId`），并在 `getPlayerRaw` 上加 `@Deprecated` 拆分。

### 6.2 【高】`new XxxService()` 绕过 `ServiceRegistry` → 内存态服务被切成多份

全层 **54 处** `new XxxService()`，其中**有状态**的服务是真正的 bug：

* `CombatService` 的 `pendingChallenges` 是实例字段（`CombatService.java:82`），
  而 `onebot/command/pvp/PvpCommand.java:52` 持有 `new CombatService()`，
  `onebot/command/combat/PvpCommand.java:25/35/71` 与 `rest/GameResource.java:83` 用 `ServiceRegistry.getCombatService()`。
  → **A 指令发出的挑战，B 指令永远收不到**（同一玩家也可能因路由不同而"挑战丢失"）。
* `DailyService` 的 `todayPhenomenon` 是实例字段（`DailyService.java:30-41`），
  而 `new DailyService()` 出现在 `OfflineRewardService:19/20`、`CombatService:99/121`、`ExplorationService:178`、`SkillService:205`、`SecretRealmService` 多处 →
  **不同路径看到的"今日天象"不同**（§6.7）。
* 无状态服务（`PlayerService`、`ItemService`、`SkillService`…）被 `new` 只是浪费对象，但放大了 §6.1 的爆炸半径。

### 6.3 【高】`EnhanceService.unequipItem` 碎装不回滚材料化属性、不返还物品

`EnhanceService.java:264-271`：装备碎裂时执行裸 `DELETE FROM players_equipment WHERE player_id=? AND slot=?`，**只删装备行**。
对比正确实现 `ItemService.equipItem:642-656`（换装时 `playerService.addAttack(conn, ..., -bonus)` 回滚材料化属性）。
→ 玩家把强化到 +N 的装备打碎后，**加在 `players.attack/defense/speed/spirit` 上的数值永久保留**，
且物品本体不回到背包（`BuffEffect` 材料化的部分同样不回滚）→ 可持续刷属性。

这条 bug 尤其隐蔽，因为 `DurabilityService` 的类注释（`:20-35`）明确把"装备属性已物化进 `players`"作为设计前提，
并靠"读取时扣减耐久惩罚"（`PlayerService.getFinalAttack`）+ "损坏不可卸下"两条规则维持可逆性；
而 `EnhanceService.unequipItem` 是**第三条绕过路径**：它既不回滚物化属性，也不经过 `ItemService.unequipItem` 的"损坏不可卸下"校验。
