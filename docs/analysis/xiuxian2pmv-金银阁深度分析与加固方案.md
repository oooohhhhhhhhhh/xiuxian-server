# 金银阁深度分析与加固方案

> 本文件是《金银阁系统分析报告》的续篇。前一份报告基于**静态代码审读**；本文件基于**可执行实验**——用 Python 1:1 复刻 `dufang_` 的结算逻辑，跑 20 万次/场景，对前一份报告的结论做**证伪与证实**，并给出可直接替换的加固实现。
>
> **一句话结论**：实测推翻了初稿的一个关键判断——"余额不足仍结算"**不是印钞机（EV 恒为 0）**，而是**无抵押信贷 + 约 50% 概率的负余额制造器**。真正的印钞机在经济系统的炼金/银行，不在赌场。
>
> 实验代码：`docs/analysis/tools/dufang_replica.py`（复刻验证）、`docs/analysis/tools/verify_hardened.py`（加固验证）、`docs/analysis/tools/dufang_hardened.py`（加固实现）
> 环境：Python 3.14.3，`random.seed(20240607)`，每场景 200,000 次

## 二、实测结果与结论修正

### 2.1 实测一：正常路径（余额 1000，下注 100）—— **证实 EV = 0**

| 玩法 | 次数 | 单次期望 | 期望/下注额 | 标准差 | 胜率 | 负余额率 | 赢但无骰子率 | 余额范围 |
|------|------|---------|------------|--------|------|---------|-------------|---------|
| 押大 | 200,000 | +0.03 | +0.0003 | 100.0 | 0.5001 | 0.00% | 0.00% | 900~1100 |
| 押小 | 200,000 | −0.32 | −0.0032 | 100.0 | 0.4984 | 0.00% | 0.00% | 900~1100 |
| 押奇 | 200,000 | +0.10 | +0.0010 | 100.0 | 0.5005 | 0.00% | 0.00% | 900~1100 |
| 押偶 | 200,000 | −0.05 | −0.0005 | 100.0 | 0.4998 | 0.00% | **49.98%** | 900~1100 |
| 猜3 | 200,000 | −0.10 | −0.0010 | 223.5 | 0.1665 | 0.00% | **16.65%** | 900~1500 |

> 标准差 100 → 标准误 = 100/√200000 ≈ **0.22**。所有期望值都落在 ±0.5 内，**统计上不可区分于 0**。
> 胜率：押大小奇偶 50.0%，猜点数 16.65%（≈1/6）。与理论完全一致。

**结论**：✅ 证实"零庄家优势"。原版赌场**不抽水**，无法承担货币回收职能。

### 2.2 实测二：致命缺陷路径（余额 0，下注 100 万）—— 🔴 **推翻初稿"印钞"结论**

| 玩法 | 次数 | 单次期望 | 标准差 | 胜率 | **负余额率** | 余额范围 |
|------|------|---------|--------|------|------------|---------|
| 押大 | 200,000 | +850 | 999,999.6 | 0.5004 | **49.96%** | −100 万 ~ +100 万 |
| 押小 | 200,000 | +1130 | 999,999.4 | 0.5006 | **49.94%** | −100 万 ~ +100 万 |
| 押奇 | 200,000 | +3560 | 999,993.7 | 0.5018 | **49.82%** | −100 万 ~ +100 万 |
| 押偶 | 200,000 | +4300 | 999,990.8 | 0.5021 | **49.79%** | −100 万 ~ +100 万 |
| 猜3 | 200,000 | −1150 | 2,235,038.9 | 0.1665 | **83.35%** | −100 万 ~ +500 万 |

> 标准差 ≈ 100 万 → 标准误 ≈ **2236**。所有期望值（最大 +4300）都远小于 2 倍标准误，**证实期望值仍为 0**。
> 但 **约一半的尝试会把玩家余额打成负数**；猜点数因胜率只有 1/6，负余额率高达 **83.35%**。

#### 🔴 结论修正（重要）

| 项目 | 初稿判断 | 实测结论 | 修正后定级 |
|------|---------|---------|-----------|
| 是否凭空产生货币 | ❌ 是（期望 +50% 单注） | ✅ **否**，EV 恒为 0 | 从"致命印钞"→ **高危（不变量击穿）** |
| 真实危害 | 无限灵石 | **无抵押信贷**（下注额无上限）+ **约 50% 概率负余额** + 双消息矛盾 | 仍需 P0 修复 |
| 对经济系统的通胀贡献 | "纯通胀源" | **0**（既不印钱也不回收） | 通胀责任在炼金/银行 |

**为什么"无抵押信贷"仍是高危**（详见 §七）：
1. 赌注额无上限（`:91` 无校验），0 余额可押任意金额；
2. 输掉的"债务"没有任何系统惩罚，一次炼金（60 万~670 万）或几天签到即可抹平 → **债务是软约束**；
3. 负余额会**击穿其它模块的不变量**——已实测 `偷灵石` 会因此抛 `ValueError` 崩溃（§七）。

### 2.3 实测三：修复后对照（余额不足即返回）

| 玩法 | 次数 | 单次期望 | 标准差 | 胜率 | 负余额率 | 余额范围 |
|------|------|---------|--------|------|---------|---------|
| 押大（已修） | 200,000 | 0.0 | 0.0 | 0.0 | 0.00% | 0~0 |
| 猜3（已修） | 200,000 | 0.0 | 0.0 | 0.0 | 0.00% | 0~0 |

**结论**：补上 `finish()` 后，余额不足的请求完全不产生任何结算——2 行代码即可根除此缺陷。

## 四、输入解析边界（正则穷举实测）

原版正则（`:29-34`）：

```python
r"(金银阁)\s?(\d+)\s?([大|小|奇|偶|猜])?\s?(\d+)?"
```

| 输入 | 匹配 | 捕获组 `(price, mode, num)` | 实际后果 |
|------|------|---------------------------|---------|
| `金银阁10大` | ✅ | `('10', '大', None)` | 正常 |
| `金银阁 10 大` | ✅ | `('10', '大', None)` | 正常（`\s?` 只允许 1 个空格，但 `\s?` 可选，中间多空格其实靠 search 容错） |
| `金银阁100` | ✅ | `('100', None, None)` | 提示"请输入正确的指令" |
| `金银阁10猜3` | ✅ | `('10', '猜', '3')` | 正常 |
| `金银阁 10 猜 3` | ✅ | `('10', '猜', '3')` | 正常 |
| `金银阁10猜` | ✅ | `('10', '猜', None)` | 提示"请输入正确的指令" |
| `金银阁10猜7` | ✅ | `('10', '猜', '7')` | 提示"请输入正确的指令"（校验生效） |
| `金银阁0大` | ✅ | `('0', '大', None)` | ⚠️ 走 `price==0` 分支但**仍结算**（§3.4） |
| **`金银阁10\|`** | ✅ | `('10', '\|', None)` | 🔴 **字符类误匹配**：`mode='\|'` → 落入"输"分支 → **白扣 10 灵石** |
| **`随便说说金银阁10大`** | ✅ | `('10', '大', None)` | 🔴 **未锚定**：夹在长文本中也会触发，可能与其它 matcher 抢消息 |
| **`金银阁99999999999999999999大`** | ✅ | `('99999999999999999999', '大', None)` | 🔴 超出 int64 → 赢时 `sqlite3` 抛 `OverflowError` |
| `金银阁10大5` | ✅ | `('10', '大', '5')` | ⚠️ `5` 被静默忽略（大/小不需要点数，但不报错） |
| `金银阁 10 小 ` | ✅ | `('10', '小', None)` | 正常（尾部空格被 `\s?` 吃掉） |
| `金银阁` | ❌ | — | 无响应 |

**三个必须修的问题**：
1. `([大|小|奇|偶|猜])` 是**字符类**，`|` 是普通字符 → `金银阁10|` 能匹配并白扣钱；
2. 无 `^...$` 锚定 → 任意长文本里夹一句就能触发；
3. 金额无上限 → 超大整数触发数据库溢出。

## 五、赌徒破产推演（零期望 + 有限本金）

| 条件 | 结果 |
|------|------|
| 本金 1000，每局押 100（10%），押大，最多 200 局 | **200 局内破产率 48.7%** |

**理论解释**：零期望随机游走 + 有吸收壁（余额 < 最小下注额）→ 长期破产概率**趋近 100%**。

这是"零抽水赌场"最反直觉的地方：
- 它不创造货币（EV=0），所以**对经济无害**；
- 但它会把玩家的资产变成随机游走，**长期看所有玩家都破产**——赌场既不回收货币，又消灭玩家的资产，是纯粹的"体验税"。

> 对比：真实赌场 2.7%~5.3% 抽水会更快消灭玩家，但至少**回收了货币**。本模块两头都不占。

## 六、冷却机制分析（`lay_out.py:104-233`）

| 机制 | 实现 | 评价 |
|------|------|------|
| 强制冷却 | `running[key]` 计数 + `loop.call_later(cd_time, increase)` | ✅ 精度正确，`cd_time` 秒内确实无法再次进入 |
| 隔离级别 | 默认 `CooldownIsolateLevel.USER` → 按 `user_id` 隔离 | ✅ 同一用户全局（跨群）共享 CD |
| 并发数 | `parallel=1` → 同一 key 只允许 1 个实例 | ✅ 正常情况有效 |
| 剩余时间提示 | `time_sy[key] = int(loop.time())` 截断到整数秒；`time = int(cd_time - (loop.time() - time_sy[key]))` | ⚠️ 最多**高估 1 秒**；且 `if time <= 1: time = 1` 强制最小显示 1 秒 → 10 秒 CD 会出现"还有 1 秒"的抖动 |
| 提示门槛 | `if cd_time >= 1.5` 才提示剩余时间，否则静默 `finish()` | ⚠️ CD < 1.5 秒时玩家收不到任何反馈（本项目 `dufang_cd=10`，不受影响） |
| 长任务重叠 | 若 handler 执行时间 > `cd_time`，`increase` 已触发恢复 `running[key]=1`，可能放行第二个实例 | ⚠️ 理论存在；但 `update_ls` 用相对更新（`stone = stone ± ?`），**不会丢失更新、不会重复发放**，风险低 |

**结论**：冷却机制本身没有可利用漏洞。`dufang_cd` 在装饰器求值时读取（`:53`），改配置需重启——属于配置体验问题，不是安全漏洞。

## 七、负余额的连锁后果（实测）

### 7.1 直接触发其它模块崩溃

`base/__init__.py:1127-1128`（偷灵石）：

```python
get_stone = random.randint(int(XiuConfig().tou_lower_limit * steal_user_stone),   # 0.01 × stone
                           int(XiuConfig().tou_upper_limit * steal_user_stone))   # 0.50 × stone
```

实测：

| 被偷者余额 | 计算结果 | 结果 |
|-----------|---------|------|
| 0 | `randint(0, 0)` | 返回 0，正常 |
| **−100** | `randint(−1, −50)` | 🔴 `ValueError: empty range in randint(-1, -50)` |
| **−1,000,000** | `randint(−10000, −500000)` | 🔴 `ValueError: empty range in randint(-10000, -500000)` |

> 即：**只要有人在金银阁把余额刷成负数，任何人对他说"偷灵石"都会让 handler 崩溃**。这是负余额从"个人状态"扩散成"公共故障"的路径。

| 路径 | 位置 | 是否有余额校验 |

## 八、加固实现

完整代码：`docs/analysis/tools/dufang_hardened.py`（已通过 `py_compile` 语法检查与逻辑验证）

### 8.1 七项结构性改造

| # | 改造 | 对应的原版缺陷 |
|---|------|--------------|
| 1 | **卫语句 + 单一出口**：7 个 `if … await dufang.finish()` 卫语句，全部 `return` 语义 | 修 §3.2/§3.4 的漏 `finish()` |
| 2 | **保证金模型**：先扣本金，中奖返还「本金 + 净赔付」 | 结构上根除"无本金下注"与"负余额" |
| 3 | **限额体系**：`MAX_BET=100万`、`DAILY_MAX_BET=2000万`、`MAX_BET_RATIO=50%` | 修 `:91` 金额无上限 |
| 4 | **全量流水表** `dufang_records`：每笔下注写 12 个字段（含 `balance_before/after`） | 修"无流水、无法审计" |
| 5 | **庄家抽水 5%**：赔率表 `ODDS` 显式化 | 让赌场真正成为货币水槽 |
| 6 | **正则锚定 + 正确字符集**：`^金银阁\s*(\d+)\s*([大小奇偶]\|猜)\s*(\d+)?\s*$` | 修 `\|` 误匹配与未锚定 |
| 7 | **消息统一出口**：`_reply()` + 固定发骰子 | 修 8 处复制粘贴与骰子缺失 |

### 8.2 关键代码

```python
ODDS = {
    "大": (0.95, 0.5), "小": (0.95, 0.5), "奇": (0.95, 0.5), "偶": (0.95, 0.5),
    "猜": (4.75, 1/6),          # 净赔付倍率, 中奖概率
}

# ---- 卫语句：任何一条不满足就 finish，绝不往下走 ----
if not ENABLED:                        await _reply(...); await dufang.finish()
if not is_user:                        await _reply(...); await dufang.finish()
if not check_user_type(user_id, 0)[0]: await _reply(...); await dufang.finish()
if not (1 <= stake <= MAX_BET):        await _reply(...); await dufang.finish()
if stake > balance:                    await _reply(...); await dufang.finish()
if stake > int(balance * 0.5):         await _reply(...); await dufang.finish()
if used_today + stake > DAILY_MAX_BET: await _reply(...); await dufang.finish()

# ---- 保证金结算：先扣后返，余额永不为负 ----
sql_message.update_ls(user_id, stake, 2)                  # 先扣本金
roll = random.SystemRandom().randint(1, 6)                # 非 MT19937
win  = _judge(mode, guess, roll)
net  = _payout(stake, mode) if win else 0
sql_message.update_ls(user_id, stake + net, 1)            # 返还本金 + 净赔付
_write_record(...)                                        # 先写流水
await bot.send_group_msg(..., f"[CQ:dice,value={roll}]")  # 所有分支都发骰子
```

## 十、结论

1. **玩法数学无需改动**：三种玩法零期望、无漏洞，赔率本身没错——错的是**没有庄家优势**（无法承担水槽职能）。
2. **必须修的是工程实现**：漏 `finish()`（2 行）、空指针（3 行）、金额上限（5 行）、骰子一致性（3 行）、正则锚定（1 行）——**合计不到 15 行改动**即可消除全部高危缺陷。
3. **初稿的关键判断已修正**：该模块**不是通胀源**（实测 EV=0）。它的问题是"无抵押信贷 + 负余额扩散 + 体验割裂"。真正需要优先处理的经济问题在炼金（`back:865`）与银行利息（`bankconfig.py`）。
4. **若要让它承担经济职能**，按 `dufang_hardened.py` 上线即可获得 2.5%~4.17% 的稳定抽水，同时保留完整的审计流水。
5. **合规仍是最终决定因素**：作者在帮助文案里自己写了"封群的，不建议玩"。加固版默认 `ENABLED = False`，把是否开启的决定权交还运营方。
