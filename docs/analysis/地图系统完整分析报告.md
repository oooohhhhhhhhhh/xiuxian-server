## 一、地图系统在做什么

地图系统承载"玩家在哪、能去哪、去了有什么"三件事，并把它们与境界门槛、危险度、PVP 判定、探索进度、资源产出耦合在一起。

它**不是一个纯数据模块**，而是多条业务链的公共依赖：

| 依赖方 | 用地图做什么 |
|---|---|
| `CombatService` / PVP | `isSafeZone(locationId)` 决定能不能私斗；`getDangerLevel` 决定掠夺多少灵石 |
| `ExplorationService` | `getEventBias(locationId)` 调事件权重；`getExplorationBonus(locationId)` 乘游历收益 |
| `CultivationService` | `getCultivationBonus(locationId)` 乘闭关收益 |
| `TeleportCommand` / 传送符 | `teleportToLocation` 无视路径传送 |
| `DailyService` / 任务 | 位置相关的日常判定 |
| 管理台 | 增删地点、连线、调事件偏置、野外补货与统计 |

因此地图的任何数值错误都会外溢。本报告第十三节那个 P0 缺陷就是典型：它本身只是"境界门槛算错"，但后果是**最危险的地带对所有人开放**。

## 三、两套世界：存储模型为什么不同

这是整个子系统**最重要的设计决策**，也是理解其余代码的前提。

| 维度 | 已知世界 | 野外 |
|---|---|---|
| 地点数量 | 固定 15 个 | 无限（`maxChunksFromOrigin=256` 片 × 16 节点 ≈ 100 万节点） |
| 地形真相源 | 数据库 `map_locations` | **生成器纯函数**（不入库） |
| 状态存哪 | 数据库（探索记录在 `player_map_exploration`） | 分片 JSON 文件（探索记录在 `exploredBy`） |
| 能否增删 | 管理台可增删改 | 不能，坐标即身份 |
| id 来源 | 自增 / 手工指定 | `ID_BASE + chunkKey × 64 + slot` 纯函数 |
| 缓存 | `locationCache`（全量常驻） | `wildernessCache`（LRU 1024） |

### 为什么野外不入库

这是正确且有价值的决策，理由链完整：

1. **地形是纯函数**，本来就不需要存储。`WildernessTerrain.generate(seed, cx, cy, config)` 不读库、不用 `ThreadLocalRandom`、不依赖系统时间，同一坐标任意次生成逐字节一致。
2. **只有"可变状态"值得落盘**：谁探索过、资源剩多少、下次补货时间。这三样加起来通常 1~3 KB。
3. **数据库不会随世界扩张膨胀**。若入库，100 万节点就是 100 万行 `map_locations` + 数百万行 `map_connections`，且每次改 `chunkSize` 都要迁移。
4. **不可能与存档走样**。地形没有第二份副本，分片文件被回收后重新走到，地形与原来逐字节一致。

### 代价

- 野外节点不能走"查表"路径，`getLocation(long)` 对野外 id 必须现算。这是 `resolveWilderness` 存在的理由。
- 分片文件的一致性靠 `.tmp` + `ATOMIC_MOVE` 保证，不享受数据库事务。
- 回收逻辑必须自己判断"这片还有没有人"，而数据库版本可以用 `DELETE ... WHERE NOT EXISTS` 一条语句解决。

### 这个取舍是否成立

**成立**，但有一个前提被违反了——见 [问题 P0-1](#p0-1-野外境界门槛算错导致最危险地带对所有人开放)：野外节点的境界门槛算错，导致"无限扩张被境界门槛自然约束"这个设计目标失效。设计意图是对的，实现没接上。

`loadFromDb()` 在加载后会**补齐出厂数据**：

- 地点不存在 → 插入

## 五、野外无限世界

### 5.1 id 编码

```
chunkKey = (cx + 2^20) × 2^21 + (cy + 2^20)
id       = 1_000_000 + chunkKey × 64 + slot
```

三条性质，每条都有具体用途：

| 性质 | 用途 |
|---|---|
| `id ≥ 1_000_000` 即野外 | `isWildernessId` 一次比较即可分流，已知世界（1~15）永远不冲突 |
| 同分片 id 连续（64 个槽位） | "这片有没有玩家"是一次 range scan，不必逐个比对 |
| id 可由坐标纯函数算出 | 分片重建后 id 不变，探索记录、玩家位置、外键全部无需改动 |

**`SLOT_STRIDE` 固定 64 而非 `chunkSize²`** 是个关键细节。若写成 `chunkSize²`，管理员把 `chunkSize` 从 4 改到 8 会让每个分片的 id 整体平移，**全部探索记录与玩家位置瞬间失效**。固定 stride 的代价只是每片多留空槽位，可以忽略。

### 5.2 地形生成

```
elevation = valueNoise(seed,           cx, cy, elevationScale=24)
moisture  = valueNoise(seed^SALT_MOIST, cx, cy, moistureScale=17)
biome     = pickBiome(elevation, moisture)   // 按声明顺序取第一个命中
danger    = max(biome.danger, distance/dangerPerChunks)   // 夹在 1~4
```

两个低频值噪声场决定地形带，做了平滑插值，所以相邻分片地形相近、不会一格一景。

危险度取"地形基础"与"离原点距离"的**较大者**，于是越往深处走越险。这是"无限扩张被境界门槛自然约束"的实现——**但门槛算错了，见 P0-1**。

### 5.3 连通性

片内用 **Kruskal 求生成树**（洗牌后 union-find），保证任意两点连通、绝无孤岛；再按 25% 概率把剩余网格边加回去形成回路，避免"全是死胡同"。

跨片边由 `borderEdges` 按 45% 概率生成。`neighborIds` 需要查四个来源：

```java
chunkAt(seed, cx, cy)              // 本片片内边
borderEdges(seed, cx, cy)          // 本片向右/下
borderEdges(seed, cx - 1, cy)      // 左片向右
borderEdges(seed, cx, cy - 1)      // 上片向下
```

为什么要查前三片：一条跨片边只由"左/上"那一片生成一次，所以要找全一个节点的跨片邻居，必须问自己和左、上两个邻居。这个细节容易漏，漏了就会出现"边界节点单向连通"。

### 5.4 命名

```
name = prefix + suffix + "·" + tag1 + tag2
```

尾缀两字由坐标派生（65 字表 → 4 225 种组合）。注释说得很清楚：**地名是 `/地图 go <地名>` 唯一的解析键，重名会让玩家走到错误的地方**。

这个设计有效但不彻底——见 [P1-2](#p1-2-野外地名仍可能与已知世界重名)。

## 六、关键算法逐段拆解

### 6.1 值噪声

`valueNoise(seed, cx, cy, scale)` 用 `scale` 把坐标降频（除以 scale），在低频网格上取哈希值，再双线性插值。所以 `scale=24` 意味着约 24 片才走完一个噪声周期，地形带很宽。

### 6.2 危险度公式

```java
public static int dangerFor(BiomeSeed biome, int distance, WildernessMapConfig config) {
    int distanceDanger = distance / Math.max(1, config.getDangerPerChunks());
    return Math.max(MIN_DANGER, Math.min(MAX_DANGER, Math.max(biome.getDanger(), distanceDanger)));
}
```

`distance` 是**切比雪夫距离**（`max(|cx|, |cy|)`）。`dangerPerChunks=12` 意味着每 12 片危险度 +1，但被夹在 1~4，所以距离 36 片之后一律 4 级。

### 6.3 境界门槛

```java
minRealm = danger * config.getMinRealmPerDanger();   // 3
```

`danger ∈ [1,4]`，所以 `minRealm ∈ {3, 6, 9, 12}`。

**这里就是 P0 缺陷所在**——游戏最高大境界是 10（金仙），12 不存在。

## 七、玩家移动与并发控制

### 7.1 校验顺序

`travel()` 的校验顺序是有讲究的，每一步都在"便宜的检查"前面：

```
1. 目标地点存在？          （内存/生成器）
2. 玩家存在？
3. 境界够不够？
4. 读当前位置（一次查询）
5. 已经在目的地？
6. 当前位置有效？
7. 是否相邻？（内存邻接表）
8. 冷却到了没？
9. CAS 写回
```

### 7.2 CAS 是唯一可靠做法

```java
UPDATE players SET current_location_id = ?, last_travel_time = ?
WHERE id = ? AND <位置谓词> AND COALESCE(last_travel_time, 0) = ?
```

注释把理由写透了：

> `SELECT ... FOR UPDATE` 在本项目的 SQLite 方言下被降级为空串（无锁），"先读后写"会让两个并发请求双双通过校验、各自移动一次并各自回复成功。

**期望位置用库里的原值而非回落后的有效值**——位置失效时两者不同，拿回落值比对会永远匹配不上，玩家就再也动不了。这是个容易被"优化"掉的细节。

### 7.3 冷却

```java
cooldownSeconds = effectiveTravelSeconds(travelSeconds)
  = max(MIN_TRAVEL_SECONDS=5, travelSeconds 或 TRAVEL_COOLDOWN_SECONDS=30)
```

路程下限 5 秒，即使连接被配成 0 也不允许瞬移。展示给玩家的秒数与实际冷却用**同一个函数**，`MapServiceTest` 有一条测试专门守"说几秒就等几秒"。

## 八、探索、首达奖励与传送

### 8.1 首达判重

两类世界用不同机制，但都避免了"先查后插"：

| 世界 | 机制 | 为什么 |
|---|---|---|
| 已知世界 | `INSERT OR IGNORE` + `UNIQUE(player_id, location_id)` | 先查后插会让两个并发请求双双判为首次、各发一份奖励 |
| 野外 | 分片对象 `synchronized markExplored` | 文件没有唯一键，锁下沉到对象 |

### 8.2 奖励公式

```
stones = (base + perDanger × danger) × (wilderness ? wildernessMultiplier : 1)
exp    = 同理
```

全图探索完成时额外发 `completionBonusSpiritStones`。野外不参与完成度计算（野外是无限的，无法"走完"）。

### 8.3 两种传送的区别

| | 传送符 `teleportToLocation` | 付费直传 `teleportByUnlock` |
|---|---|---|
| 触发 | 物品效果 | `/地图 传送` |
| 能否去没去过的地方 | 能 | **不能**（必须已探索） |
| 花钱 | 不花 | 花（基础 + 危险度×每级 + 野外附加） |
| 境界校验 | 有 | 有 |
| 冷却 | 重置 | CAS 校验 |

**付费直传必须"到过才能传"**，否则花钱直传会抹平探索的意义。这个设计判断是对的。

扣费与写回的顺序也处理了：先扣费，CAS 失败就**退款**，不会"既收钱又不办事"。

## 九、采集与资源经济

### 9.1 并发扣减

```java
public synchronized int consume(int slot, String itemKey, int amount) {
    ...
    int taken = Math.min(amount, resource.remaining);
    resource.remaining -= taken;
    return taken;
}
```

`WildernessChunk` 对象由 store 统一缓存、全进程共享同一份，所以 `synchronized` 天然实现了"读余量 → 扣减"的互斥。数据库版本靠 `UPDATE ... WHERE remaining >= ?`，文件版本没有那层条件判断可用，于是把锁下沉到对象——粒度比整张表更细。

### 9.2 失败回滚

顺序是**先扣库存并落盘 → 再发物品 → 发失败就加回去**，不允许"库存扣了、东西没到"。`refund` 方法就是为此存在。

### 9.3 资源抽取

`rollChunkResources` 按资源池权重给每个节点抽资源，结果直接写进分片文件。用 `resourcesRolled` 标志而非"resources 为空"来判断是否抽过——资源池全空时也该只抽一次。

## 十一、管理台

### 11.1 已有校验（质量不错）

```java
// 安全区与危险度不能同时成立
if (safeZone && dangerLevel > 0) throw new IllegalArgumentException(...);

// 地点名不能重名
if (countLocationsByNameExceptId(conn, name, excludeId) > 0) throw new IllegalArgumentException(...);
```

重名校验的注释说清了理由："重名会导致其中一个无法通过 `/地图 go` 抵达（`getLocationByName` 只返回第一个）"。

更新场景的校验更细：`checkDangerConsistencyOnUpdate` 会读出现有行，把 update 合并进去，校验**改完之后**的组合是否自洽，而不是只看传入字段。

### 11.2 缺失的校验

- `minRealm` 没有上限校验（可以填 999，玩家永远进不去）
- `dangerLevel` 有 0~4 校验 ✅
- 加成倍率没有下限校验（可以填 0 或负数）

### 测试缺口

这一节是本报告最重要的部分之一——**P0-1 能长期存在，原因就在这里**。

1. **测试助手绕过了业务路径**。`MapWildernessTest.movePlayer` 直接用 SQL 写 `current_location_id`，绕过了 `travel()` 的全部四层校验（境界、邻接、冷却、CAS）。于是野外相关的 21 个测试实际上在验证"一个玩家本不该处于的状态"，`checkRealm` 从未被执行过。这个模式值得警惕：**为快速构造状态而绕过业务入口，会连带绕过该入口的所有校验**。

3. **采集冷却的并发没有测试**。现有测试是单线程连续两次调用，测不出 P1-1 的竞态。

4. **`/地图` 邻居渲染没有测试**。`MapCommandRenderTest` 只测了 `list` 分支，`execute` 的邻居列表（P2-1 地名重复所在处）完全没有覆盖。

## 十三、问题清单

### P0-1 野外境界门槛算错，导致最危险地带对所有人开放

**严重度：P0（设计目标失效 + 数值外溢）**

**证据**（两轮临时探针实测，探针均已删除）：

第一轮，确认数值越界：

```
PROBE minRealmPerDanger = 3
PROBE 游戏最高大境界 id = 10
PROBE 危险度4 → minRealm = 12
PROBE gate > maxRealm ? true
PROBE getRealmConfig(12, 0) = null
PROBE chunk(48,0)  biome=snow    danger=4 node.minRealm=12
PROBE chunk(100,0) biome=plain   danger=4 node.minRealm=12
```

第二轮，确认影响面——5 个出入口分片本身是可达的（`danger=1` → 门槛 3，金丹期），但**深处的 `danger=4` 分片全部不可达**：

```
PROBE gateway[0] chunk(1,0)   biome=plain danger=1 minRealm=3   ← entry#0 (loc 5)
PROBE gateway[1] chunk(1,1)   biome=plain danger=1 minRealm=3   ← entry#1 (loc 7)
PROBE gateway[2] chunk(0,1)   biome=plain danger=1 minRealm=3   ← entry#2 (loc 8)
PROBE gateway[3] chunk(-1,1)  biome=plain danger=1 minRealm=3   ← entry#3 (loc 12)
PROBE gateway[4] chunk(-1,0)  biome=plain danger=1 minRealm=3   ← entry#4 (loc 15)
PROBE chunk(48,0)  danger=4 minRealm=12   *** 超过最高境界，永久不可达 ***
PROBE chunk(100,0) danger=4 minRealm=12   *** 超过最高境界，永久不可达 ***
```

第三轮，确认哪些地形被锁死——`volcano` 是唯一的 `danger=4` 地形，而距离增量（`dangerPerChunks=12`）会让 `distance ≥ 36` 的所有分片也变成 `danger=4`：

```
marsh   danger=3   snow   danger=3   volcano danger=4
desert  danger=2   forest danger=2   plain   danger=1
```

**根因**：

```java
// WildernessTerrain.buildNode
return new Node(..., danger * config.getMinRealmPerDanger(), ...);   // danger∈[1,4], ×3 = {3,6,9,12}
```

`danger=4` → `minRealm=12`，而 `realm_config.json` 最高只到 `id=10`（金仙）。

**后果链**：

1. `getRealmName(12)` 走 `GameConfigLoader.getRealmConfig(12, 0)` 返回 `null`，兜底值是 **"凡人"**。
2. 于是玩家看到"需要≥凡人"，而 `player.getRealm() >= 12` 永远为假。
3. **看起来是"凡人可进"，实际谁都进不去**——最危险的地带成了死区。

更糟的是 `MapCommand` / `WildernessCommand` 的渲染会显示成：

```
🔒 需要≥凡人 [境界不足]
```

玩家会以为是 bug（"我都是大乘了还说境界不足"），GM 也很难从这句话定位到"门槛是 12"。

**同时 `danger=1` → `minRealm=3`（金丹期）**，意味着新手刚出青云村（realm 0）**连最外圈的野外都进不去**。而野外是主要资源产地，这直接掐断了新手的资源获取路径。

**这是设计意图与实现脱节的典型**：注释写着"无限扩张被境界门槛自然约束，而不需要一堵硬墙"，但门槛本身算错了，约束变成了"要么全锁死、要么全开放"。

**影响面有多大**（按出厂配置估算）：

| 情形 | 门槛 | 可达性 |
|---|---:|---|
| 出入口分片（5 个，`danger=1`） | 3（金丹） | 可达，但新手进不来 |
| `volcano` 地形全部分片（`danger=4`） | 12 | **永久不可达** |
| `distance ≥ 36` 的全部分片（距离增量使 `danger=4`） | 12 | **永久不可达** |
| `marsh` / `snow`（`danger=3`） | 9 | 可达（真仙） |
| `desert` / `forest`（`danger=2`） | 6 | 可达（合体） |
| `plain`（`danger=1`） | 3 | 可达（金丹） |

`maxChunksFromOrigin=256`，而 `danger` 在 `distance ≥ 36` 后恒为 4。也就是说**半径 36 片以外的整个世界（占可用面积的 98% 以上）全部不可达**——"无限野外"实际只剩一个半径 35 片的圆盘。

这个估算让缺陷的严重度从"某个地形进不去"升级为"核心卖点失效"。

**修复建议**：

```java
// WildernessTerrain.buildNode
int minRealm = Math.min(danger * config.getMinRealmPerDanger(), MAX_REALM_ID);
```

但更根本的是**门槛曲线本身需要重新设计**。`{3,6,9,12}` 这个等差数列对 10 级境界系统不合适：

- 危险度 1 就要求金丹（3），跳过炼气筑基两个境界，太陡
- 危险度 4 要求 12，超过上限

建议改成 `{1, 3, 5, 7}` 或做成配置项 `minRealmByDanger: [1,3,5,7]`，让管理员能调。同时 `getRealmName` 的兜底不该是"凡人"，应当返回 `"境界 " + realm`，让越界值一眼可见。

**顺带**：应当补一条测试断言 `minRealm` 必须是 `realm_config` 里真实存在的 id。

**为什么这个缺陷能长期存在**（这是最值得记的部分）：

现有测试**全部绕过**了境界校验，而不是验证它：

```java
// MapWildernessTest 的测试助手 —— 直接改库，不走 travel()
private void movePlayer(long playerId, long locationId) throws SQLException {
    // UPDATE players SET current_location_id = ? ... 
}
```

测试用 `createPlayer(9, node.getId())` 造一个 realm=9 的角色，再 `movePlayer` 直接把位置写进库。**`travel()` 从未被调用**，所以 `checkRealm` 从未执行。

于是唯一相关的断言是：

```java
assertTrue(node.getMinRealm() >= 0, "境界门槛不应为负");
```

它只排除了负数，而 `12` 完全满足 `>= 0`。

这是个有普遍性的教训：**测试助手为了"快速到达某状态"而绕过业务路径，就会连带绕过那条路径上的所有校验**。此处 `movePlayer` 绕过了境界、邻接、冷却、CAS 四层校验——不只是境界。野外相关的测试因此实际上是"在测试一个玩家本不该处于的状态"。

若要真正守住，需要两条测试：

1. **值域测试**：`minRealm` 必须在 `realm_config` 的 id 集合内（纯函数，不需要数据库）。
2. **路径测试**：让一个 realm=0 的新角色走 `travel()` 进入野外，断言被拒绝且提示文案正确——这条会同时验证"门槛存在"和"门槛可读"。

### P1-1 采集冷却检查不是原子操作，并发可绕过

**严重度：P1**

**证据**：

```java
// MapService.gather
long lastGather = readLastGatherTime(playerId);          // 读
if (cooldown > 0 && (now - lastGather) < cooldown) {     // 校验
    return GatherResult.rejected(...);
}
// ... 扣库存、发物品 ...
MAP_DAO.updateLastGatherTime(conn, playerId, now);       // 写
```

`gather()` **没有** `synchronized`（`travel()` 也没有，但 `travel()` 有 CAS 兜底）。

**后果**：两个并发请求可以同时读到旧的 `lastGatherTime`、双双通过校验、各自扣一次库存并发一份物品。而 `consume` 的 `synchronized` 只能保证**库存不会被超扣**，不能保证**冷却不被绕过**——两次扣的是不同物品或同一物品的不同份额时，两次都成功。

对比 `travel()` 的做法：它用 CAS 把"校验 + 写回"合成一个原子操作。`gather()` 没有对应机制。

**修复建议**：把冷却写回也做成 CAS：

```java
UPDATE players SET last_gather_time = ?
WHERE id = ? AND COALESCE(last_gather_time, 0) = ?
```

`affected == 0` 即说明并发竞争，回滚库存并拒绝。这与 `updateTravelIfUnchanged` 是同一个模式，已有先例可循。

### P1-2 野外地名与已知世界共用一个命名空间，管理台无从校验

**严重度：P1（低概率、后果有限，但属于"设计上没想清楚"）**

**证据**：

- 野外地名 = `prefix + suffix + "·" + tag1 + tag2`，例如 `青松岭·甲乙`
- 已知世界地名 = `青云村`、`落霞山` 等
- `getLocationByName` 只在 `locationCache`（已知世界）里找，**找不到野外节点**

**分析**：

`AdminMapResource.checkMapLocationNameAvailable` 只校验 `map_locations` 表内的重名，而野外节点不在表里。所以管理员新建一个叫 `青松岭·甲乙` 的地点，会与某个野外节点同名，**且管理台不会报错**。

不过要修正一个容易写错的判断：这**不会**让玩家"走到错误的地方"。因为 `getLocationByName` 只查已知世界，所以 `/地图 go 青松岭·甲乙` 会稳定命中那个管理员新建的地点；野外节点本来就不通过名字导航。

`WildernessTerrain` 里那句注释——

> 重名会让玩家走到错误的地方

——是**过度担忧**。`·` 后缀 + "只查已知世界"的查找逻辑已经把这个问题消解了。野外唯一可靠的导航方式是 id，代码在 `WildernessCommand` 里也写明了：

> `/地图 go <id>` 因此是野外唯一的导航方式

**真正的小瑕疵**：管理台不知道野外命名空间的存在。管理员若真的用 `·` 建了地点，那个名字看起来会像野外节点，造成运维困惑。这是**可读性问题，不是正确性问题**。

**修复建议**：优先级低。若要彻底，在 `checkMapLocationNameAvailable` 里拒绝含 `·` 的地点名（`·` 是野外专用分隔符），让两个命名空间在形式上不可混淆。

### P2-2 `connections` 字段除日志外没有任何读取方

**严重度：P2（死数据）**

**证据**：

```java
private final List<long[]> connections = new CopyOnWriteArrayList<>();
```

全文件引用点：

| 行 | 用途 |
|---:|---|
| L182 | `LOG.info("... " + connections.size() + " 条连接")` ← **唯一读取** |
| L201, L225 | `clear()` |
| L387 | `add(...)` |

**严重度：P2（内存缓慢增长）**

### P2-6 加成倍率没有下限校验

**严重度：P2**

`cultivation_bonus` / `exploration_bonus` 可以填 0 或负数。填 0 会让该地点的修炼/游历收益归零（`ExplorationService` 用 `if (locationMult > 1.0)` 判断，所以 0 只是"没有加成"，不会变负）；填负数同理被 `> 1.0` 挡掉。

所以**实际危害很小**，但数据本身是脏的，且 `MapCommand` 会渲染出 `灵气×0.0` 这种明显不对的文案。

**修复**：管理台加 `> 0` 校验。

### P2-7 `MapService` 仍有 4 处自开连接

**严重度：P2（已知的技术债，有注释说明）**

`MapService` 类注释里自己写明了：

> 仍在本类里开连接的地方只有四处，且都是"多条语句必须共用同一条连接"的场景（整段地图加载、探索记录 + 首达奖励、一轮分片扫描、发物品 + 采集冷却）。

这四处确实是**真需要事务**的场景，不是偷懒。但它们绕过了 `MapDAO`，`MapDaoExtractionTest.serviceLayerHasNoJdbc` 是靠 allowlist 放行的。属于**可接受的债务**，不建议强行消除。

## 十四、修复优先级建议

| 优先级 | 问题 | 工作量 | 理由 |
|---|---|---|---|
| **1** | P0-1 境界门槛 | 小 | 设计目标失效，且新手无法进入野外 = 核心玩法断链 |
| **2** | P1-1 采集冷却 | 小 | 有现成 CAS 模式可抄，是明确的刷资源漏洞 |
| **3** | P2-1 地名重复 | 极小 | 一行删除，每个玩家都会看到 |
| **4** | P2-3 stub 缓存上限 | 极小 | 三行代码，防长期内存增长 |
| **5** | P2-2 `connections` 死字段 | 小 | 删字段 + 改日志 |
| **6** | P2-4 悬空 Javadoc | 极小 | 一句话 |
| **7** | P2-5 / P2-6 管理台校验 | 小 | 防脏数据 |
| **8** | P1-2 重名 | 极小 | 加一条 `·` 检查 |

**P0-1 的修复需要设计决策**，不只是改个 `Math.min`。建议改成可配置的 `minRealmByDanger` 数组，让管理员能按自己的境界系统调曲线。若坚持用乘法，至少要：

1. `Math.min(danger * perDanger, 最高境界)`
2. `getRealmName` 的兜底从"凡人"改成 `"境界" + realm`，让越界一眼可见
3. 补一条测试断言 `minRealm` 必须在 `realm_config` 的 id 集合内

## 十五、总体评价

### 做得好的地方

1. **两套世界的存储模型分离**是本子系统最有价值的设计。纯函数生成器 + 只存可变状态，让"无限世界"在工程上真正可行。`MapWildernessTest` 用"数据库行数一动不动"把这条承诺变成了可执行断言，这是很少见的测试写法。

2. **注释解释"为什么"而不是"是什么"**。几乎每个非显然的决策都写了理由：为什么 `SLOT_STRIDE` 固定 64、为什么 CAS 而不是 `FOR UPDATE`、为什么用文件而不是数据库、为什么 `resourcesRolled` 而不是判空。这类注释的维护成本远低于它的价值。

3. **并发控制选对了工具**。`travel` 用 CAS、`consume` 用对象锁、`markExplored` 用对象锁——三处都是对应场景下的正确选择，而不是统一套 `synchronized`。

4. **"只补不覆盖"的出厂数据补齐策略**。让老库升级、管理员自定义、出厂默认三者能共存。

5. **失败回滚意识**。采集发物品失败会 `refund`、传送 CAS 失败会退灵石。这类"一半成功"的路径都处理了。

### 做得不好的地方

1. **P0-1 是典型的"设计意图对、实现没接上"**。注释说"无限扩张被境界门槛自然约束"，门槛公式却算出了不存在的境界。这类缺陷最难发现——因为代码本身"看起来对"，错误只在数值与配置交叉时出现，而配置在另一个文件里。

2. **测试断言偏弱**。`assertTrue(node.getMinRealm() >= 0)` 只排除了负数，没排除"12 这种不存在的境界"。测试应该断言**语义正确**而不是**符号正确**。

3. **入口层覆盖不一致**。传送没有 HTTP/WS 通道，Web 端玩家用不了付费直传。各通道按需实现是合理的，但没有一张"能力矩阵"来暴露差异，容易在加新通道时漏功能。

4. **几处"慢慢失真"的遗留**：`materializeArea` 悬空引用、`connections` 死字段、地名渲染重复。这些都不影响运行，但都是重构后没清理干净。

### 一句话总结

**地图子系统的架构判断是高质量的**（两套世界分离、纯函数生成器、CAS 并发控制都是正确且不平凡的选择），**工程实现也基本到位**（注释、回滚、补齐策略都考虑到了）。**主要问题是一个数值缺陷（P0-1）和若干测试断言太弱**——前者让"越远越险"的设计目标失效，后者正是前者能长期存在的原因。

修掉 P0-1 之后，这个子系统的质量在本项目中属于上乘。
