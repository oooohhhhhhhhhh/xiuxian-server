> **本报告的所有数字均来自代码或配置，并附 `文件:行号` 证据**；估算值均标注"估算"并给出假设。
> **结论一句话**：这不是一个"经济系统"，而是**六个各自独立调参、互不相通的货币子系统被强行拼在一起**——它能在当前形态下"跑得动"，纯粹是因为存在两个数量级失控的意外印钞机（炼金、银行利息）和一个数量级失控的后期产出（悬赏令），三者掩盖了其余全部数值失衡。

### 1.2 方法

1. **入口穷举**：全项目 grep `update_ls(`、`stone=stone+`、`stone=stone-`、`update_stone_num`、`update_sect_used_stone`、`donate_update`，确保不漏任何一个货币写入点。

## 二、货币体系结构：4 个货币池 + 3 种伪货币

这是理解本经济系统的**第一把钥匙**：所谓"灵石"其实是 4 个互不相通的池子。

### 2.1 四个独立货币池

| 池 | 存储位置 | 读写方法 | 能否与个人灵石互换 |
|----|----------|----------|--------------------|
| **个人灵石** | `user_xiuxian.stone`（SQLite，`xiuxian2_handle.py:71`，`integer DEFAULT 0`，**无 CHECK 约束**） | `update_ls` | — |
| **宗门灵石** | `sects.sect_used_stone`（SQLite，`:105`） | `update_sect_used_stone`、`donate_update` | ⚠️ 单向：个人 → 宗门（捐赠），**无法取回** |
| **传承结晶** | `xiuxian_impart.stone_num`（SQLite，`:1696`） | `update_stone_num` | ❌ 完全不通用，独立玩法货币 |
| **银行存款** | `data/xiuxian/players/<uid>/bankinfo.json`（**JSON 文件，不在数据库里**） | `bank/__init__.py:235-254` | ✅ 双向（存/取），但**无任何数据库留痕** |

### 2.2 三种伪货币

| 伪货币 | 存储 | 与灵石关系 |
|--------|------|-----------|
| 修为（exp） | `user_xiuxian.exp` | 灵石 → 修为：仅"修炼"一条路，**10 灵石 = 1 修为**（`buff/__init__.py:650`），且受"下个境界修为 × 1.5"上限约束（`:618-621`） |
| 体力（stamina） | `user_xiuxian.user_stamina` | 灵石 → 体力：**不存在**（体力只能自然恢复，1 点/分钟，上限 360，`xiuxian_config.py:97-98`） |
| 宗门建设度/资材 | `sects.sect_scale`、`sect_materials` | 灵石 → 建设度：`donate_update` 中 `sect_scale += stone_num × 1`（`xiuxian2_handle.py:891-894`）**1:1 转换** |

### 2.3 结构性缺陷

🔴 **缺陷 A：银行资产不在数据库里**（`bank/__init__.py:235-254`）
```python
def readf(user_id):
    FILEPATH = PLAYERSDATA / user_id / "bankinfo.json"
    with open(FILEPATH, "r", encoding="UTF-8") as f: ...
```
调用处（`:90-97`）：
```python
try:
    bankinfo = readf(user_id)
except:
    bankinfo = {'savestone': 0, 'savetime': now, 'banklevel': '1'}
```
→ **文件损坏/权限异常/并发写坏 = 玩家存款静默归零**，且无任何审计痕迹可恢复。这是全项目风险最高的资产存储设计。

🔴 **缺陷 B：宗门灵石只进不出**
`sect_used_stone` 只有 `donate_update`（+）和 `update_sect_used_stone(key=2)`（-，用于宗门改名等系统消耗）。玩家投入的灵石**没有任何取回途径**，属于"沉淀型"资金池——从货币总量看是有效的，但玩家会把它视为"黑洞"而拒绝捐赠。

🟡 **缺陷 C：三个池之间的汇率完全未设计**
宗门建设度 1:1、传承结晶独立计价、修为 10:1（且受上限截断）。三者没有任何统一的价值锚点。

**这张表说明了一个致命的设计事实**：所有门槛都是按"银行/炼金级产出"定价的，**按正常玩法产出（签到 3 万/天）计算全部不可达**。也就是说——

> 这个经济系统在数值上是**依赖那两个印钞机才成立**的。删掉炼金和银行利息，游戏立刻变得不可玩（什么都买不起）；保留它们，货币就失去意义。这是本报告最核心的结构性结论。

### 6.2 缺陷

🟠 **`送灵石` 的"道号赠送"路径完全失效**
```python
stone_num = re.findall(r"\d+", msg)   # 灵石数
nick_name = re.findall(r"\d+", msg)   # 道号 ← 复制粘贴错误，同样是提取数字
```
`base/__init__.py:959-960`：两个正则**完全相同**，所以 `nick_name[0]` 永远等于金额数字，`get_user_info_with_name("100")` 必然查不到 → "对方未踏入修仙界，不可赠送"。按道号送灵石这条路是死的。

🟠 **`偷灵石` 成功时零成本**
失败罚 10 万（`base:1118-1119`），成功则**白拿对手 1%~50% 灵石**（`config:94-95`），没有任何前置成本或冷却惩罚。在有多个小号的群里，这是稳定的"搬运"工具。

🟡 **`抢劫` 无手续费**
10% 转移不抽税（`base:1496-1497`），与 `送灵石` 的 10% 手续费形成套利差：**大额转移应该"被抢"而不是"被送"**。理性的玩家会互相配合用抢劫转移资产以避税。

🟡 **`送灵石` 把字符串当金额传入 SQL**
`base:1001` `update_ls(user_id, give_stone_num, 2)`，其中 `give_stone_num = stone_num[0]` 是**字符串**。SQLite 会做隐式数值转换所以能跑，但这是脆弱依赖：任何非纯数字输入都会静默变成 0。

## 七、银行系统专项

### 7.1 完整机制

| 项目 | 值 | 位置 |
|------|-----|------|
| 时利率 | 0.20% ~ 0.30%（按会员等级） | `bankconfig.py:12-18` |
| 存储上限 | 100 万 → 6400 万（7 级） | 同上 |
| 升级费用 | 20 万 / 40 万 / 80 万 / 160 万 / 320 万 / 640 万 | 同上 |
| 计息公式 | `give_stone = int(savestone × timedeff × interest)`，`timedeff` = 距上次结算的小时数（`round(...,2)`） | `bank/__init__.py:223-232` |
| 结算时机 | 存款时、取款时、`灵庄结算` | `:121,147,211` |
| 复利 | ❌ 无（利息进钱包，需手动再存入） | — |
| 上限 | ⚠️ `timedeff` **无上限** | `:227-228` |

### 7.2 收益表（满仓、线性计息）

| 会员等级 | 存储上限 | 升级花费 | 时利率 | **日利息（封顶）** | 累计升级成本 | 回本天数 |
|---------|---------|---------|--------|------------------|-------------|---------|
| 1 普通 | 1,000,000 | — | 0.20% | 48,000 | 0 | — |
| 2 小会员 | 2,000,000 | 200,000 | 0.21% | 100,800 | 200,000 | — |
| 3 大会员 | 4,000,000 | 400,000 | 0.22% | 211,200 | 600,000 | — |
| 4 优质 | 8,000,000 | 800,000 | 0.23% | 441,600 | 1,400,000 | — |
| 5 黄金 | 16,000,000 | 1,600,000 | 0.24% | 921,600 | 3,000,000 | — |
| 6 钻石 | 32,000,000 | 3,200,000 | 0.25% | 1,920,000 | 6,200,000 | — |
| 7 终极 | 64,000,000 | 6,400,000 | 0.30% | **4,608,000** | **12,600,000** | **2.73 天** |

### 7.3 数学结论

1. **年化收益率（单利）** = 0.30%/小时 × 8760 小时 = **2628%/年**。
2. **回本周期 2.73 天**：投入 1260 万升满级，2.7 天后开始净赚 460 万/天。
3. **`timedeff` 无上限** → 存满 6400 万挂机 1000 小时（41.7 天）→ 利息 `64M × 1000 × 0.003 = 1.92 亿`，是本金的 **3 倍**。
4. **与签到对比**：460.8 万 / 3 万 = **154 倍**。签到这个"每日产出"在银行面前完全是噪音。
5. **取整放大漏洞**：`timedeff = round(hours, 2)`，最小计息粒度 0.01 小时（36 秒）。`灵庄结算` 的 CD 是默认 0.5 秒（`bank/__init__.py:48` `Cooldown(at_sender=False)`），因此理论上可以每 18~36 秒结算一次，每次都被 `round` 向上取到 0.01 小时 → **实际利率最多可放大 2 倍**。属于低危但确实存在的浮点取整套利。
6. **关于"复利"的精确界定**（避免高估）：利息进**钱包**而非本金（`:229` 只读 `savestone`，`:125` 才改本金），因此**不是自动复利**，需要玩家手动"结算→再存入"。而且 `savemax` 把本金锁死在 6400 万，所以复利有硬天花板：
   - 倍增期 = `ln2 / 0.003 ≈ 231 小时 ≈ 9.6 天`；
   - 从 100 万复投到 6400 万需 6 次倍增 ≈ **58 天**；
   - **到顶后收益退化为线性 460.8 万/天，永久不变**。

   → 真实产出上界是"约 2 个月后每天 460.8 万"，**不是**指数爆炸。这一点很重要：它意味着银行是"稳定的高息水龙头"，而不是"一个月毁掉全服"的核弹——真正瞬间毁掉全服的是 §16.1 拍卖与 §16.2 BOSS 越权。

### 7.4 缺陷清单

| 级别 | 缺陷 | 位置 |
|------|------|------|
| 🔴 | 存款存放在 JSON 文件而非数据库，读失败静默归零 | `bank/__init__.py:90-97,235-254` |
| 🔴 | 时利率 0.2%~0.3% 严重过高（等价年化 2628%），且无 `timedeff` 上限 | `bankconfig.py`、`:227` |
| 🟠 | 升级成本 1260 万 vs 满级日息 460 万 → 回本 2.7 天，投资回报率失衡 | `bankconfig.py:12-18` |
| 🟡 | `round(timedeff,2)` 取整可被高频结算放大 2 倍 | `:227` |
| 🟡 | 存取款无流水、无利息明细、无法审计 | 全文件 |
| 🟡 | `取灵石` 结算的是**全部存款**的利息，即使只取 1 枚 | `:147-151` |

## 八、炼金套利闭环（头号漏洞）

### 8.1 代码事实

`xiuxian_back/__init__.py:865`：

```python
price = int((convert_rank('江湖好手')[0] + 5) * 100000 - get_item_msg_rank(goods_id) * 100000) * num
```

其中 `convert_rank('江湖好手')[0]` 在 `xiuxian_config.py:40` 的定义是：

```python
rank_number = len(ranks) - ranks.index(rank_name) - 1   # 江湖好手 → 58 - 0 - 1 = 57
```

**`'江湖好手'` 是硬编码字符串**，与玩家当前境界毫无关系。所以：

```
炼金收益 = (57 + 5 − item_rank) × 100,000 × num = (62 − item_rank) × 100,000 × num
```

### 8.2 全物品收益表（items.json 实测 rank 分布）

| 物品 rank | 条目数 | 单件炼金收益 |
|-----------|--------|-------------|
| −5 | 80 | **6,700,000** |
| 1 | 24 | 6,100,000 |
| 2 | 1 | 6,000,000 |
| 8 | 4 | 5,400,000 |
| 11 | 11 | 5,100,000 |
| 16 | 4 | 4,600,000 |
| … | … | … |
| 56（最贵） | — | **600,000** |

**全游戏 115+ 件物品，没有一件的炼金收益低于 60 万灵石。** 对比：签到 3 万/天 → **一件最低档物品 = 20 天签到**；一件 rank −5 物品 = **223 天签到**。

### 8.3 套利闭环

```
坊市上架（最低价 50 万，back:717）
   → 买家 50 万买入（卖家得 45 万，5 万手续费销毁，back:469-471）
   → 买家炼金 → 得 60 万~670 万（back:865）
   → 净利润 +10 万 ~ +620 万 / 件，循环次数仅受物品供给限制
```

单次循环系统净增货币 = 炼金产出 − 手续费 ≈ **+55 万 ~ +665 万**。

更简单粗暴的版本：**玩家背包里任何已有物品（悬赏令奖励、BOSS 掉落、秘境宝物、炼丹产物）直接炼金即可**，不需要任何前置交易。配合 `炼金 <物品> <数量>` 支持批量（`back:861-864`），一次指令可以变现上千万。

### 8.4 附带缺陷

🟠 **`炼金` 数量越界会崩**（`back:860-864`）
```python
try:
    if 1 <= int(args[1]) <= int(goods_num):
        num = int(args[1])
except:
        num = 1
price = ... * num     # ← 若上面 if 不成立，num 从未被赋值 → NameError
```
`炼金 物品 9999`（超过持有量）或 `炼金 物品 0` → `num` 未定义 → `NameError` 崩溃。

🟠 **`强制炼金`（`diy_goods_re_root`）用同一公式**（`back:2327`），且 `price<=0` 时兜底为 1000。虽为 GROUP 权限（`back:57`），但**没有 SUPERUSER 限制**——任何群成员都能用"强制炼金"。需要确认这是否是设计意图。

### 8.5 修复方向

```python
user_rank = convert_rank(user_info['level'])[0]     # 用玩家真实境界
base = (user_rank + 5) * 10_000                      # 基准值降 10 倍
price = int(max(base - get_item_msg_rank(goods_id) * 10_000, 1_000)) * num
if daily_alchemy_total(user_id) + price > DAILY_CAP:   # 日上限
    拒绝
```
关键点：**收益必须随境界变化**（否则高低境界玩家的货币效率完全一样），**必须有日上限**（否则没有水槽能吸收），**基准值必须降 1~2 个数量级**（否则物品就是硬通货）。

### 9.2 三画像对比

### 9.3 模型结论

1. **新手期完全靠签到活着**（悬赏令 20 灵石/次是纯噪音），且**任何门槛都不可达**（宗门创建 500 万 = 167 天）。
2. **中期靠银行**，银行收益是玩法的 3.5 倍以上。
3. **后期靠悬赏令超难档**，一单 270 亿，把银行（460 万/天）和炼金（670 万/件）都变成噪音。
4. **三个阶段的主导产出完全不同，且相互之间没有平滑过渡**——这不是一条成长曲线，而是**三段互不相干的直线**。

## 十、通胀诊断

### 10.1 净增率估算

| 来源 | 量级 | 是否可无限重复 |
|------|------|---------------|
| 炼金 | 60 万~670 万/件，**冷却 0.5 秒、无上限** | ✅ 完全无限 |
| 银行利息 | 460 万/天（满级） | ✅ 无限（时间线性） |
| 悬赏令（后期） | 2.7e10/次 | ✅ 每 4 小时一次 |
| 签到 | 3 万/天 | ❌ 每日一次 |
| 仙途奇缘 | 30 万（一次性） | ❌ |

**诊断结论：货币净增率完全由炼金决定，且不受任何上限约束。**

- 一个中期玩家每天炼金 10 件 → 日入 **6000 万**，是签到产出的 **2000 倍**；
- 没有对应的水槽（宗门 500 万、改名 5000 万都是一次性的），**通胀是必然且不可逆的**；
- 唯一的"伪约束"是物品供给量，但物品来自悬赏令/BOSS/秘境/炼丹——**这些玩法本身又在源源不断地产出物品**，所以供给也不是真约束。

### 10.2 通胀的主要来源排序

1. **炼金**（数量级失控，硬编码常量）
2. **银行利息**（利率失控 + 无 `timedeff` 上限）
3. **悬赏令超难档**（疑似多打一位，100 倍断层）
4. **秘境负值产出**（`riftmake.py:192-194` 可返回负灵石，反向破坏余额）
5. **签到**（合理，非问题）

### 10.3 为什么"通胀"在这里没被玩家感知

因为**灵石与成长解耦**（见 §十一）：玩家不需要灵石也能升级，所以通胀不会造成"卡关"，只会造成"灵石没意义"。这是最坏的组合——**既没有经济压力，也没有经济乐趣**。

## 十一、灵石与成长的耦合分析（关键设计问题）

### 11.1 事实

| 成长动作 | 消耗 | 位置 |
|----------|------|------|
| 突破（`突破`/`直接突破`/`渡厄突破`/`渡厄金丹突破`） | **体力 6~12 + 修为惩罚**，**无灵石** | `base:491,561,652,775` |
| 闭关 | 无（免费产修为） | `buff` |
| 修炼（灵石→修为） | 10 灵石 = 1 修为，上限 = 下境界修为 × 1.5 | `buff:650-667` |
| 灵根洗练 | 100,000（`remake`） | `xiuxian2_handle.py:348-353` |
| 功法/装备 | 物品 + 灵石（部分） | 各模块 |

### 11.2 量化

境界曲线（`data/xiuxian/境界.json`，58 级）：
- 修为需求：100 → 2,150,392,299,048（**2.15e10 倍**）
- 最大单级跳变：搬血境初期 **10 倍**；祭道境初期 **4.42 倍**（后期异常）
- `spend`（战力倍率）：1 → 14,439，且**祭道境中/圆满两级完全相同（14,439）**——疑似复制粘贴

**"修炼"买进度划算吗？**
- 闭关：60 修为/分钟，**免费**
- 修炼：1 修为/10 灵石 → 600 灵石/分钟
- 结论：**修炼的经济效率是闭关的 0（免费）**。唯一的价值是"更快撞到 1.5× 上限"，而一旦撞到上限就完全无效。
- 要用灵石买完祭道境圆满需要 **2.15e13 灵石**，而银行满级日产 460 万 → **需要 12,800 年**。

### 11.3 设计判断

🔴 **灵石在本游戏里是"装饰性货币"**：
- 不能加速成长（闭关免费且够用）；
- 不能买突破（突破不要灵石）；
- 只能买"锦上添花"的东西（丹药、装备、宗门、赌场、秘境门票）。

后果：
1. 玩家**没有必须花灵石的压力** → 货币只进不出；
2. 设计者**无法用通胀做平衡杠杆**（因为通胀不影响进度）；
3. 水槽只能做成"一次性巨额门槛"（宗门 500 万/改名 5000 万），而这类门槛又必须靠印钞机才能达到 → 形成 §5.3 的死循环。

## 十五、对 Java 版主项目（`E:\xiuxiangame\main`）的建议

### 15.1 必须避免的坑（按优先级）

1. **绝不要在公式里硬编码境界常量**。`convert_rank('江湖好手')` 这种写法（`back:865`）是本次审计最严重的缺陷。Java 里等价错误是 `RankConst.JIANG_HU` 写死在收益公式里。
2. **货币写入必须单一入口 + 非负约束**。DB 层 `CHECK (stone >= 0)` + 服务层 `deduct()` 前置校验 + 事务。禁止任何模块直接 `UPDATE ... stone = stone - ?`。
3. **任何"物品→货币"的变现口必须有日上限**。炼金是本项目最大的漏洞，Java 版若做"回收/出售/分解"，务必设计 `dailyCap`。
4. **存款/资产不要放文件**。JSON 存储 + 静默兜底 = 资产蒸发。用数据库 + 乐观锁。
5. **利率必须算清年化**。0.3%/小时 = 2628%/年，这是"复利陷阱"的典型。Java 版建议把利率定义成"日利率"，并在注释里写明年化。
6. **避免数值跳变 100 倍**。悬赏令的 48 档奖励跨越 9 个数量级，其中至少一处是输入错误。建议用**公式生成 + 少量手工覆盖**，而不是全手工填表。

### 15.2 值得借鉴

1. **`update_ls(user_id, price, key)` 这种"单一读写函数"思路是对的**（只是缺校验）。Java 版做成 `CurrencyService.add/deduct` 并强制走它。
2. **三档转移税（10%/10%/30%）的设计很实用**：送灵石 10%、坊市 10%、拍卖 30%，能随交易量自动回收货币。建议保留并在 Java 版中显式化。
3. **体力系统作为"软性产出上限"**：突破消耗 6~12 体力、上限 360、恢复 1/分钟 → 天然限制了每日突破次数。这是一个比"每日次数限制"更优雅的节奏控制手段。
4. **境界表用 JSON 驱动**（`境界.json` 58 条）：数据与代码分离，便于平衡调整。Java 版可沿用（YAML/JSON + 热重载）。

### 15.3 主项目现状对照

已检索 `E:\xiuxiangame\main\src`：无 `赌`/`博彩`/`gamble`/`casino` 相关模块。本报告与《金银阁系统分析报告》的价值在于提供一份**完整的反面清单**，供主项目在实现经济系统时逐条对照规避。

## 十六、补充审计：实测核实的高危漏洞（本节为增量，严重度高于前文多数条目）

> 本节汇总并行审计中**经主代理逐行复核确认**的漏洞。凡未经我本人读源码确认的，一律标注「未核实」。等级：🔴 致命（可无限产出货币/越权）｜🟠 高危（资损或数据不一致）。

### 16.1 🔴 致命-A：拍卖结算——余额不足仍给卖家打款并销毁拍品 → **无限印钞**

**证据**：`xiuxian_back/__init__.py:283-302`

```python

    end_msg += "...灵石不足，流拍了\n"                            # :288 只写一句文案
else:
    sql_message.update_ls(user_id, int(final_price) * quantity, 2)  # :290 扣款
    sql_message.send_back(...)                                     # :291 发货
    end_msg += "...成功拍下\n"

user_auction_info = get_user_auction_price_by_id(auction_id)       # :294 ★ 在 if/else 之外

    seller_id = user_auction_info['user_id']
    auction_earnings = int(final_price) * quantity * 0.7           # :297 ★ float！
    sql_message.update_ls(seller_id, auction_earnings, 1)          # :298 ★ 卖家照收 70%
remove_auction_item(auction_id)                                    # :300 ★ 拍品照删
```

**攻击链**：
1. 小号上架任意廉价物品，起拍价 `1`；
2. 另一个 0 余额小号（或自己）出价 **10 亿**；
3. 结算时 `:287` 判定余额不足 → 只写"流拍了"，**不 `continue`**；
4. `:294-300` 继续执行：**卖家收到 7 亿灵石，拍品被删除，买家一分钱没花**。

**这是本插件最严重的经济漏洞**——它不需要任何运气、不需要成本（一个廉价物品），每场拍卖会（`back:110` 定时触发）可执行多次，直接产出任意数量灵石。

**附带缺陷**：`:297` 的 `0.7` 使结果为 **float**，`update_ls` 会把 REAL 写进 `stone` INTEGER 列 → **出现小数灵石**（同文件 `:1679` 的同类代码有 `int()`，此处漏了）。

**修法**：把 `:294-302` 整体移入 `else` 块，`:288` 分支加 `continue`，`:297` 补 `int()`。

### 16.7 中危-G：宗门创建实际免费（SQLite 实测定论）

**证据**：`xiuxian_sect/__init__.py:1449` 校验 `stone >= sect_create_cost`（5,000,000），`:1462` 却执行：

```python
sql_message.update_ls(user_id, XiuConfig().sect_min_level, 2)   # sect_min_level = "铭纹境圆满"
```

**实测定论**（SQLite 3.50.4，`tools/probe2.py`，与运行时同版本）：

| 绑定参数 | 结果 | 说明 |
|---------|------|------|
| `"铭纹境圆满"` | **s = 1000（不变）** | 非数字文本在算术中被当作 0，**无异常** |
| `"100"` | s = 900 | 数字文本正常转换 |
| `"1000000"` | s = −999000 | 正常扣减 |
| `"5000000.0"` | s = −4999000 | 浮点文本正常转换 |
| `"  100  "` | s = 900 | 自动去空格 |
| `"1e3"` | s = **1000**（未扣） | ⚠️ 科学计数法文本**不被**转成数字，同样当 0 |
| `""` | s = 1000（未扣） | 空串当 0 |
| STRICT 表 + `"铭纹境圆满"` | s = 1000（不变） | 即使 STRICT 表也不报错 |

> **重要辨正**：曾有审计意见认为此处会抛 `sqlite3.OperationalError: datatype mismatch`，从而"创建宗门崩溃"。实测**不成立**——`datatype mismatch` 只在把文本写入 `INTEGER PRIMARY KEY`（rowid）时触发（本报告已一并实测复现），而 `stone` 是普通 INTEGER 列，算术中的非数字文本被静默当作 0。
>
> **结论**：`:1449` 的门槛检查通过后，`:1462` 的扣款为 **0**，宗门创建**实际免费**且不崩溃。

**后果**：5,000,000 的门槛检查形同虚设（"有校验、无扣费"），这是最隐蔽的一类资损——日志里看不出任何异常。

### 16.8 中危-H：仙途奇缘每日重置，可领 4 次

### 16.11 🟠 高危-I：装备合成调用不存在的方法 → 全系统最大的灵石水槽实际不存在

**证据**：`xiuxian_fusion/__init__.py:144`

```python
sql_message.update_user_stone(user_id, required_stone, 2)   # ← 该方法在全项目中不存在
```

**核实方式**：对整个 `nonebot_plugin_xiuxian_2` 全树 grep `update_user_stone` → **仅此 1 处匹配**，既无 `def update_user_stone`，也无任何赋值定义。项目里真正的扣款方法是 `update_ls(user_id, price, key)`（`xiuxian2_handle.py:383-394`）。

**执行顺序分析**（`:132-147`）：

| 行号 | 动作 | 是否执行 |
|------|------|---------|
| `:132-143` | 检查材料是否足够，不足则提示并 `finish()` | ✅ |
| **`:144`** | **`update_user_stone(...)` → `AttributeError`** | 🔴 **必崩** |
| `:146` | 扣材料 `update_back_j` | ❌ 永不执行 |
| `:147` | 发放装备 `send_back` | ❌ 永不执行 |

**结论**：`装备合成` 是一条**100% 失败的死功能**——每次调用都在 `:144` 抛 `AttributeError`，材料未扣、装备未发。**好在异常发生在任何状态变更之前，因此不产生资损**（这一点与"材料已扣装备未发"的猜测相反，已按行号顺序核实）。

**经济含义（比 bug 本身更重要）**：
- 法器表里最贵的合成需求是 **10,000,000,000（100 亿）灵石**（`data/xiuxian/装备/法器.json:884,908`）；
- 这是全系统**量级最大的单笔灵石水槽**，比"宗门攻修 0→50 级 442 亿"之外的一切消耗都大；
- 而它**根本无法触发** → 报告 §五"水槽清单"里最大的那个出口是纸面上的，真实水槽只剩 10%/10%/30% 三档手续费与银行（银行还是反向的）。
