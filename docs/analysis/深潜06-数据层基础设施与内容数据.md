## 1. 数据层总览

### 1.1 无 ORM 的取舍

项目完全没有 ORM，也没有任何 SQL 生成框架。数据访问全部是手写 JDBC：

| 事实 | 数值 | 取证 |
|---|---|---|
| `DatabaseManager.getConnection()` 调用点 | **307 处** | 全库 grep 汇总 |
| 其中位于 `com.mtxgdn.game`（业务服务层） | **201 处** | 同上 |
| `DatabaseManager.runTransaction(...)` 调用点 | **72 处** | 同上 |
| `DatabaseManager.executeInTransaction(...)` 调用点 | **0 处**（定义了但无人使用） | 同上 |
| 真正手写 `conn.setAutoCommit(false)` | **仅 7 个文件 / 9 处** | 见 §3.3 |
| `SELECT *` 出现次数 | 51 处（`PlayerService` 8、`EconomyService` 7、`FarmService` 5…） | grep |
| 表名/列名拼进 SQL 字符串的位置 | 65 处 | grep |

`getConnection` 的包级分布：`com\mtxgdn\game` 201、`com\mtxgdn\onebot` 22、`com\mtxgdn\permission` 22、`com\mtxgdn\service` 16、`com\mtxgdn\rest` 15、`com\mtxgdn\minecraft` 8、`com\mtxgdn\qq` 8、`com\mtxgdn\util` 5、`com\mtxgdn\playerdata` 4、`com\mtxgdn\db` 3、`data\mtxgdn\explorationevent` 2、`com\mtxgdn\plugin` 1。

**收益**：零反射开销、SQL 完全可控、无 N+1 隐式查询、可针对 SQLite/MySQL 写不同语句。
**代价**（实测到的）：

1. **没有 DAO 层**。`com.mtxgdn.db` 里唯一的 DAO 是 `PlayerActionLogDAO`（134 行）。其余 40+ 张表的读写 SQL 全部散落在 `com.mtxgdn.game.service.*` 的 Service 类里——`PlayerService` 1391 行、`SectService`、`EconomyService`、`ItemService` 962 行都同时承担"业务逻辑 + 持久化 + 事务"三重职责。
2. **同一张表被映射成两个 Java 模型**。`players` 一行同时被 `com.mtxgdn.entity.Player`（46 处引用，含 `mapPlayer()`）和 `com.mtxgdn.game.entity.PlayerInfo`（486 处引用，含 `mapPlayerInfo()`）映射，`PlayerService.java:45-99` 三个方法 `getPlayerByUserId / getPlayerById / getPlayerInfoById` 发出几乎相同的 `SELECT * FROM players WHERE ...`，只是返回不同的映射结果。`PlayerService.java:81-87` 的注释直言"为它单独查一遍库不划算"。
3. **`com.mtxgdn.entity` 是个残留包**：只有 `Player.java`(338 行) 与 `User.java`(79 行)，而 31 个真正的领域模型在 `com.mtxgdn.game.entity`（`Sect`/`Skill`/`Technique`/`WorldBoss`/`FarmPlot`…）。

### 1.2 DatabaseManager 初始化流程

`DatabaseManager.init(url, user, password)`（`DatabaseManager.java:37-67`）：

```
1. IS_SQLITE = url.startsWith("jdbc:sqlite:")      // 唯一方言判据，只看 URL 前缀
2. DIALECT   = IS_SQLITE ? SQLiteDialect : MySQLDialect
3. Class.forName(驱动)
4. 构造 HikariConfig → new HikariDataSource
5. getConnection()   // 探活（连接异常直接冒泡）
6. initTable()       // 建 46 张表 → executeMigrations → 建 5 个索引 → PermissionService.initDefaultData()
```

`initTable()`（`:132-214`）的**顺序有明确设计意图**并带回归测试标注：建表（`CREATE TABLE IF NOT EXISTS`）→ 迁移补列（`:192`）→ 建索引（`:202-206`）。注释解释了为什么索引必须在迁移之后：老库的 `trade_listings.expires_at` 由迁移补上，索引若先建会直接 `no such column` 导致服务起不来（`DatabaseManager.java:194-201`）。

上游调用方 `Main.initializeDatabase()`（`Main.java:516-546`）：`database.type=sqlite` 时拼 `jdbc:sqlite:<sqlite_path>` 且用户名密码传空串；否则读 `database.url`，若判定为本地地址则先调 `MySqlLauncher.ensureMySqlRunning()` 拉起 mysqld。

> ⚠ **配置默认值不一致**：`application.yml:24` 默认 `database.type: sqlite`，而代码里 `AppConfig.get("database.type", "mysql")`（`Main.java:501/517`）的兜底是 `mysql`。配置文件丢失时（`AppConfig` 会尝试从 classpath 释放，理论上不会丢）行为会与文档相反。

每次 `getConnection()`（`:69-81`）还做两件额外工作：

- `conn.setTransactionIsolation(TRANSACTION_READ_COMMITTED)`——MySQL 默认是 `REPEATABLE_READ`，这里显式降级；
- `DIALECT.initConnection(conn)`——**SQLite 分支每次取连接都执行 3 条 PRAGMA**（`SQLiteDialect.java:97-107`）：`foreign_keys=ON`、`busy_timeout=5000`、`journal_mode=WAL`。其中 `PRAGMA journal_mode=WAL` 是写操作（需获取数据库级锁），把它放在每连接路径上是明显的位置错误——它应该只在建库/启动时执行一次。

`HikariCP` 连接池 4 个连接，而 `application.yml:297-299` 的 Grizzly worker 线程是 `4~8`，加上 `PlayerService`（自动回血，10 秒）、`EconomyService`、`TradeService`、`PlayerDataService`（30 秒）、`MapService` 等多个独立调度线程，池容量与并发度不匹配，是"高并发下偶发 `connectionTimeout`"的合理嫌疑点。

### 1.4 读写路径

**读路径**（无缓存层）：Service → `DatabaseManager.getConnection()` → `PreparedStatement` → `ResultSet` → 手工 `mapXxx(rs)` → 领域对象 → 返回。全程无二级缓存，唯一的内存缓存是：

- `PermissionService` 的权限组缓存（`refreshGroupCache()`）；
- `MapService` 的野外分片（`WildernessChunkStore`，文件 + 内存）；
- `TokenBlacklist` 的内存 Map；
- `I18nManager.bundles`（语言包）。

**读路径带写**：`PlayerService.touchActive()`（`:150-163`）在**每次**读玩家后按 1 小时节流写 `UPDATE players SET last_active_time`（`ACTIVE_TOUCH_INTERVAL_MS = 60*60*1000`，`:135`）。也就是热读路径上每玩家每小时多一次写 + 一次连接借还。设计上可接受，但它把"读"和"写"耦合在同一个 mapper 调用点（`:53`、`:71`、`:96` 三处），意味着任何调用方都无法获得"纯只读"的语义。

### 2.3 命名规范

整体相当一致，可预测性好：

- 表名全小写蛇形；玩家维度表统一 `player_*` / `players_*` 前缀（但**两种前缀混用**：`players_items`、`players_equipment`、`players_skills`、`players_techniques` 用复数，`player_daily`、`player_economy`、`player_buffs`、`player_titles`、`player_bank`、`player_energy` 用单数，无规则可循）。
- 列名蛇形；时间列统一 `*_time`（毫秒 BIGINT）或 `*_at`（TIMESTAMP），**两种混用**：`last_secret_realm_time`(BIGINT 毫秒) 与 `created_at`(TIMESTAMP) 并存；`expires_at` 在 `trade_listings` 是 TIMESTAMP，在 `formations`/`world_bosses`/`map_locations` 是 BIGINT 毫秒，`auction_listings` 则叫 `end_time`(TIMESTAMP)。**同一个列名三种语义**，是最容易写错的地方。
- 布尔列：`is_*` 前缀（`is_equipped`、`is_cultivating`、`is_safe_zone`、`is_wilderness`），但 `formations.active` 例外。
- 主键：绝大多数 `id` + `AUTO_INCREMENT`/`AUTOINCREMENT`；少数用业务键直接做 PK（`player_daily.player_id`、`player_economy.player_id`、`player_energy.player_id`、`map_locations.id`、`schema_migrations.version`）。

### 2.4 索引现状（重点问题）

全库只有 **5 个显式二级索引**（`DatabaseSchema.java:285/306/311/326/719`，由 `DatabaseManager.java:202-206` 的 `createIndexQuietly` 创建）：

```
idx_trade_price_item_time          trade_price_history (item_key, sold_at)
idx_trade_listings_status_expires  trade_listings (status, expires_at)
idx_trade_listings_seller_status   trade_listings (seller_player_id, status)
idx_player_buffs_expire            player_buffs (expire_time)
idx_world_bosses_scope_expires     world_bosses (scope, expires_at)
```

加上 21 个 UNIQUE 约束的隐式索引，实际可用的索引约 26 个，覆盖 49 张表中的约 20 张。**以下高频查询完全没有可用索引**：

| 查询 | 位置 | 问题 |
|---|---|---|
| `ORDER BY level DESC, experience DESC LIMIT ? OFFSET ?` | `PlayerService.java:889` | 排行榜全表扫 + filesort |
| `WHERE player_name LIKE '%x%' ... ORDER BY created_at DESC LIMIT ? OFFSET ?` | `PlayerActionLogDAO.java:41-61` | 前导通配符 + 无索引 + 无保留策略 |
| `WHERE sect_id = ?` | `SectService` 成员列表 | `sect_members` 只在 `player_id` 上有唯一索引 |
| `WHERE status='active' AND end_time <= ?` | 拍卖结算调度 | `auction_listings` 无索引 |
| `WHERE player_id = ? AND plot_index = ?` | `FarmService.java:798` | `farm_plots` 无任何索引，且**无唯一约束**（可能出现重复地块） |
| `WHERE player_id = ? OR friend_player_id = ?` | `PlayerService.java:1282`、`PlayerDataService.java:482/820` | 复合唯一索引对第二列无效，OR 条件只能半命中 |
| `WHERE channel = ?` / `WHERE receiver_player_id = ?` | `ChatService` | **SQLite 上这两个索引根本不存在**（见下） |

**SQLite 索引缺口**：`SQLiteDialect.supportsIndexInCreateTable()` 返回 `false`（`SQLiteDialect.java:135-137`），而 `chat_messages` 的两个索引是**直接写进 `CREATE TABLE` 语句**的（`DatabaseSchema.java:463-465`）。结果：**SQLite 部署下 `chat_messages` 一个索引都没有**，而 `application.yml` 的默认配置正是 SQLite。

### 2.5 类型选择

- **时间戳语义混乱**（同上）：游戏内计时（冷却、到期）用 `BIGINT` 毫秒，审计用 `TIMESTAMP`。混用导致 `PlayerActionLogDAO` 里 `created_at >= ?` 传的是 `String`（`PlayerActionLogDAO.java:52-58`），而 `VerificationCodeService` 传的是 `Timestamp`（`:34`）。字符串与时间戳比较在 MySQL 上隐式转换、在 SQLite 上按文本比较，跨方言行为不一致。
- **货币**：`gold` / `spirit_stones` / `prestige` / `treasury` 全部 `BIGINT`，正确（避免 INT 溢出）。
- **`players_items.quantity`** 是 `BIGINT`，而 `sect_warehouse.quantity`、`trade_listings.quantity`、`auction_listings.quantity`、`recipes.result_quantity` 都是 `INT`，同类语义不同宽度。
- **`user_permissions.user_id`** 是 `INTEGER`（`PermissionService.java:810`），而所有其它表的 `user_id` 都是 `BIGINT`。SQLite 无所谓，MySQL 上若用户 id 超过 21 亿会截断/报错。
- **布尔**：MySQL 用 `BOOLEAN`（即 `TINYINT(1)`），SQLite 用 `INTEGER DEFAULT 0`（`MySQLDialect.java:28-30` / `SQLiteDialect.java:27-30`）。JDBC `setBoolean` 两边都能处理，但 `formations.active BOOLEAN DEFAULT 0` 是**硬编码 `BOOLEAN`**（`DatabaseSchema.java:845`），绕过了 `boolType` 参数——SQLite 接受该类型名（弱类型），不报错但破坏了方言抽象的完整性。
- **`players.lang VARCHAR(16) DEFAULT ''`** 空串表示"未设置"，与 `NULL` 语义重复，读取方需要同时判两种空值。

### 2.6 字符集 / 编码

- **MySQL**：无 `CHARACTER SET` 子句，完全依赖连接串参数 `?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_unicode_ci`（`application.yml:25`）。这意味着：
  - 建表时的字符集由**服务器默认**决定，而不是由连接参数决定——若 MySQL 服务器默认是 `latin1`，表仍会建成 `latin1`，写入中文会坏；
  - 更安全的做法是在 `CREATE TABLE` 末尾显式 `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`，或至少在建库脚本里指定。
- **SQLite**：天然 UTF-8，无问题。
- **文件侧**：`YamlFileEditor`（`:96-98`）、`PlayerActionLogger`（`:50-51`）、`BuildInfo`（`:56`）、`PlayerDataService`（`:203`）都显式指定 UTF-8 并写了注释说明"避免中文 Windows 默认 GBK 乱码"——说明踩过坑，修复到位。

### 2.7 迁移机制（`DatabaseMigration`，546 行）

**版本模型**：24 个步骤，字符串版本号 `001_verification_codes_sent_at` ~ `024_players_language`（`DatabaseMigration.java:88-115`），按数组顺序执行，无依赖图。

**关键设计决策（写在类注释 `:14-32` 里，且是有意识的取舍）**：

> **不做"记录过就跳过"**。迁移的幂等性同时是自愈能力——运维手工删了列、从备份恢复了缺列的表，重启就能补回来。引入跳过逻辑后，结构被外部改动就再也不会被修复。

这个选择是**合理且经过论证的**，代价是每次启动都跑 24 条 `ALTER TABLE`（每条失败在 `tryAlter` 里被 `isAlreadyExists` 判定为"预期内"并吞掉，`:194-203`）。判定条件只认 `duplicate column / duplicate field / duplicate key name / duplicate index / already exists` 六种消息（`:211-217`），其余一律抛出——这修掉了历史上"所有错误都 `catch (SQLException ignored)`"的老毛病，并有单测 `MigrationHistoryTest` 钉住这条边界。

**版本表**：`schema_migrations(version PK, name, status, applied_at, detail)`（`:128-140`）。每条步骤执行后先 `DELETE` 再 `INSERT` 记录状态（`:142-165`），注释解释为什么不用 upsert："SQLite 老版本没有 `ON CONFLICT DO UPDATE` 的通用写法，删插最省心"。`detail` 截断到 250 字符以适配 `VARCHAR(255)`。

**失败策略**：默认 `strict=false`，失败只 `System.err.println` + 记入历史表，服务继续启动（`:63-72`）；`database.migration.strict=true` 时抛异常中断启动。可观测性接口 `readHistory(conn)`（`:168-182`）供管理后台读取。

**问题**：

1. **`System.err.println` 而非 `GameLogger`**（`:66`、`:75`、`:138`、`:163`）——迁移失败这种关键事件不进日志文件、无时间戳、无级别，重启后即丢。而迁移恰恰是最需要留痕的环节。
2. **迁移与建表职责重叠**：`player_buffs`、`farm_plots` 两张表**不在 `initTable()` 里建**，而是靠迁移步骤 009/010。也就是说"新库建表"和"老库升级"走了两条不同路径，新库也必须跑迁移才能拿到这两张表。这解释了为什么迁移不能跳过——但更干净的方案是把它们并入 `initTable`。
3. **`executeMigrations` 用单连接、默认 autoCommit**（`:52-79`），每条 DDL 各自成事务。MySQL 的 DDL 本就隐式提交，SQLite 的 DDL 支持事务但这里没用。半途失败会留下部分完成的 schema（这正是 `schema_migrations` 要记录状态的原因）。
4. **`readHistory` 是 `static` 却接收 `Connection`**（`:168`），而 `record` 是实例方法——API 风格不统一。

### 2.8 MySQL / SQLite 方言差异处理

**抽象层质量评估：接口设计完整，但业务代码大面积绕过它。**

`DatabaseDialect`（74 行）定义了 26 个方法，覆盖：主键/时间戳/布尔类型片段、标识符引用、元数据读取、CRUD 语句构造、DDL 构造、外键/索引能力标志、`FOR UPDATE` 子句、连接初始化、表/列元数据查询。两个实现各 169/180 行，质量不错：

- `getForUpdateClause()`：MySQL 返回 `FOR UPDATE`，SQLite 返回 `""` 并附注释"SQLite 不支持 FOR UPDATE，但在事务内 UPDATE/DELETE 会自动加写锁，返回空字符串，调用者需要确保在事务内执行"（`SQLiteDialect.java:174-179`）——诚实标注了契约。
- `getTableNamesQuery()` / `getTableColumnsQuery()`：`SHOW TABLES` vs `sqlite_master`，`DESCRIBE` vs `PRAGMA table_info`，正确。
- `getColumnNameFromMetadata()`：`rs.getString("Field")` vs `rs.getString("name")`，正确。
- `supportsForeignKeysInCreateTable()` 两边都 `true`；`supportsIndexInCreateTable()` MySQL `true` / SQLite `false`。

**但只有 2 个能力真正被业务代码用到**：

| 能力 | 业务代码调用点 |
|---|---|
| `getForUpdateClause()` | 9 处（`CaveService:153`、`ExplorationService:73`、`ItemService:878`、`RealmService:128/214/377`、`SecretRealmService:71`、`TradeService:146`、`WorldBossService:532`） |
| `DatabaseManager.isSqlite()`（静态布尔，非接口方法） | **27 处**内联分支 |

`DatabaseManager.isSqlite()` 的 27 处调用点分布：

```
CaveService:327  CombatService:124  DailyService:102,158  DurabilityService:180,265,277
EconomyService:123,766,1069  EnergyService:114,169  FarmService:38,508  FriendService:251
ItemService:107,665  MapService:1220  PlayerService:624,688,777,1376
SectService:725,1135,1973  PermissionService:34  TokenBlacklist:98
```

典型的内联分支（每处都是两份 SQL 字符串）：

- `PlayerService.java:777-779`：`MIN(...)` vs `LEAST(...)`
- `PlayerService.java:1376-1380`：`MIN(hp + CAST(CEILING(max_hp*0.01) AS INTEGER), max_hp)` vs `LEAST(hp + CEIL(max_hp*0.01), max_hp)`
- `DailyService.java:157-166`：`ON CONFLICT(player_id) DO UPDATE` vs `ON DUPLICATE KEY UPDATE`
- `TokenBlacklist.java:98-100`：`ON CONFLICT(token_hash) DO NOTHING` vs `INSERT IGNORE`
- `PermissionService.java:34-35`：`INSERT OR IGNORE` vs `INSERT IGNORE`（**类级 `static final` 常量，在类加载时求值**——若 `DatabaseManager.init()` 晚于 `PermissionService` 类加载，`IS_SQLITE` 会固化成 `false`，方言判断永久错误。`Main` 的启动顺序目前是安全的，但这是个隐式时序依赖。）

**结论**：方言抽象停在"接口定义了但没人用"的阶段。真正的方言分支散落在 10 个业务类的 27 处 `if` 里，新增第三种数据库（如 PostgreSQL）需要改 10 个文件而不是加 1 个实现类。

### 3.2 SQL 拼接与参数化现状

**值一律参数化，标识符一律拼接。** 65 处拼接按风险分三档：

**A 档 — 内部常量，安全**（约 50 处）：

- `DatabaseSchema` 里 17 处 `"updated_at " + tsUpdate` 是建表模板，不是查询。
- `PlayerService.java:1274`、`:1353`、`PlayerDataService.java:613`：表名来自**代码内 `String[]` 常量数组**。

**B 档 — 列名拼接，语义正确但无白名单校验**（约 13 处）：

`table` 来自 **JSON 快照文件里的 key**（`data.tables.entrySet()`，`PlayerDataService.java:602`），即**用户可上传的数据**。`restorePlayer` 的调用链是管理员导入 → `data.tables` 由上传的 JSON 反序列化而来。这里没有任何白名单校验，`table` 直接拼进 `DELETE FROM` / `INSERT INTO`。虽然入口受 `admin` 权限保护，但"从文件读出的表名直接拼 SQL"是这个代码库里**唯一真正的注入面**。同一段逻辑在 `insertRow`（`:765`）里同样拼接列名（`row.keySet()` 来自 JSON）。

### 3.3 事务边界

**三种事务写法并存**：

1. **`DatabaseManager.runTransaction(SQLFunction)`**（`:110-129`）：72 处使用，最规范。
   ```
   conn.setAutoCommit(false);  →  body  →  conn.commit();  →  finally setAutoCommit(true)
   catch: rollback() + throw RuntimeException
   ```
   使用分布：`EconomyService` 12、`FarmService` 10、`SectService` 9、`ItemService` 6、`BuffService` 5、`TradeService` 4、`FormationService` 4、其余 1~3。

2. **手写 `setAutoCommit(false)` + try/catch/finally**：仅 7 个文件 9 处
   ```
   DatabaseManager.java:93,113（内部实现）
   PlayerService.java:1267     deletePlayer —— 17 张表级联删除
   PlayerDataService.java:593  restorePlayer —— 快照回灌
   PermissionService.java:645,734  deleteGroup / setGroupPermissions
   AdminResource.java:1020     deleteUser
   DebugCommand.java:144       调试指令沙箱
   ```

3. **`executeInTransaction(SQLRunnable)`**（`:91-108`）：**定义了但 0 处使用**——死代码。

**跨 Service 的事务传播靠手工重载 `Connection` 参数**：`ItemService.addItem(conn, ...)`、`PlayerService.addStat(conn, ...)`、`PlayerService.addExperience(conn, ...)` 等都有一对重载（无 conn 版自建连接，有 conn 版加入调用方事务）。这是没有 ORM/事务模板时的必然做法，但**极易漏**——而确实漏了：

> **`BuffEffect.execute(Connection conn, ...)`（`BuffEffect.java:113-149`）接收了 `conn`，但 `durationSeconds > 0` 分支里调用的是 `buffService.addBuff(playerId, ...)`（`:119`），而 `BuffService` 只有一个 `addBuff(long playerId, ...)` 签名（`BuffService.java:163`，无 Connection 重载）——即 `conn` 参数被完全忽略，Buff 写入落在另一个连接、另一个事务里。**丹药使用的事务无法覆盖 Buff 授予。

**`DebugCommand` 的"事务沙箱"是假的**（`DebugCommand.java:143-150`）：

```java
try (Connection conn = DatabaseManager.getConnection()) {
    conn.setAutoCommit(false);
    try { targetCmd.execute(debugCtx); }   // ← 目标命令内部各自 getConnection()
    finally { conn.rollback(); }            // ← 只回滚这个空连接，什么也没撤销
}
```

被测试的指令通过 `ServiceRegistry` 拿到的 Service 会从池里取**另外的连接**，提交自己的事务。这个 rollback 不撤销任何东西，却给了运维"调试是安全的"的错误预期。

**连接泄漏面**：`leakDetectionThreshold` 未设置，而 `getConnection()` 有 307 个调用点。绝大多数写成 `try (Connection conn = ...)`，形态正确；但 `PermissionService.initDefaultData()`（`:805-865`）在循环内反复 `try (Connection conn = ...)`（73 个权限码 → 73 次借还，加上 5 个组 × 各自权限码约 250 次），启动期数百次连接借还是不必要的开销。

### 3.4 批量操作

- **有 Batch 的地方**：`PermissionService.java:744-751`（`addBatch` + `executeBatch`，设置组权限）；`PlayerDataService` 的导入/还原是逐行 `insertRow`（**未 batch**）。
- **无 Batch 的批处理**：`ItemService.addItems/removeItems`（`:224-258`）在单事务内**逐条** `addItem(conn, ...)` / `getItemCount(conn, ...)`——一次 N 物品的批量操作 = 2N 次 round trip。
- **`players_items` 的 upsert**：`addItem` 依赖 `UNIQUE(player_id, item_key)` + 方言分支的 upsert，是正确做法。
- **`PlayerDataService.restorePlayer`**（`:592-634`）对整个玩家快照执行 "逐表 `DELETE` + 逐行 `INSERT`"，全部在单事务内且无 batch。一个玩家若有 500 行物品，就是 500 次 round trip——这是导入/还原操作的性能瓶颈，但因为是低频管理操作，优先级不高。

### 3.5 N+1 与重复查询

**没有 ORM 意义上的 N+1**（不存在懒加载）。但存在三类等价浪费：

1. **同一次业务动作里对同一行重复查询**。`PlayerService` 的 `addGold`/`addExperience`/`addAttack`… 全部是"一条 UPDATE"，而调用方往往刚刚 `getPlayerById` 过。
2. **`ServiceRegistry` 每次调用都新建 Service**（见 §7.3），`new BuffService()`（`BuffEffect.java:79`、`:117`）在**每次使用丹药时**创建一个新对象。
3. **列表渲染逐个查**：`PlayerActionLogDAO.queryPlayerActionLogs` 的 `LIMIT/OFFSET` 分页正确，但配套的 `countPlayerActionLogs` 是独立第二次全表扫描（`:89-133`），两次查询的过滤条件代码完全重复（约 25 行 × 2）。

## 4. 持久化策略

### 4.1 双层结构：DB 是唯一真相源，文件是快照

`PlayerDataService`（827 行）在**数据库之外**为每个玩家维护一份 JSON 快照：`data/players/<playerId>.json`。

关键点：**文件不是主存储，DB 才是**。证据：

- 所有写入路径先写 DB（`PlayerService.updatePlayer` 等），成功后调 `markDataDirty(playerId)`（`PlayerService.java:321/344`，`markDataDirty` 定义在 `:325-327`）——**只是把 id 放进一个 `Set<Long>`**，不做任何 I/O。
- `flushDirty()`（`:120-143`）由独立调度线程每 `player-data.auto-sync-seconds`（默认 30 秒）执行，对每个脏玩家调 `exportPlayer(id)` → 读 DB 全表 → 写文件。
- 文件 → DB 的回流只有一条路径：管理员/玩家自助 `restorePlayer`（`:592-634`），且默认 `self-restore: false` 防刷。

所以准确的说法是：**DB 单写 + 定期文件快照备份**，不是"双写"。

`PlayerData`（57 行）定义快照结构：`schemaVersion`（当前 `SCHEMA_VERSION = 1`）、`playerId`、`exportedAt`、`rowCount`、`checksum`、`tables: Map<String, List<Map<String,Object>>>`。

### 4.2 快照的工程质量（做得相当扎实）

`exportPlayer`（`:168-266`）有三道保障，注释（`:155-167`）明确列出：

1. **读失败即导出失败**：`queryRowsByColumn`（`:463-478`）任何一张表读不出来都 `throw RuntimeException`，不产出"缺表的完整快照"。
2. **写后回读校验**：写 tmp → 立刻读回反序列化 → 重算 `rowCount` + `checksum` → 再写一遍 → 再回读 `verifySerialized` 比对。`checksum` 是 `tables` 的 SHA-256。
3. **保留上一版**：覆盖前把旧文件复制为 `<id>.json.bak`（`:242-249`）。

还原侧同样有校验：`checksum` 不匹配 → 拒绝；`rowCount` 不一致 → 拒绝；玩家在线 → 默认拒绝（`:585-589`）；`user_id` / `id` / `created_at` / `updated_at` 列在还原时被强制跳过（`:743-746`），防止快照把角色挂到他人账号。

一个值得称道的细节（`:199-203`）：摘要必须算在"解析后的规范形态"上，因为 JDBC 取出的 `Long` 在 JSON 里读回会变成 `Double`（`123` vs `123.0`）。注释直言"这正是最初版本每次导出都报摘要不一致的原因"。

### 4.3 缓存一致性

**没有缓存层，因此没有缓存一致性问题**——除了三个例外：

| 缓存 | 位置 | 失效方式 |
|---|---|---|
| 权限组/权限 | `PermissionService`（`refreshGroupCache()`） | 每次写操作后主动刷新 |
| 野外地图分片 | `MapService` + `WildernessChunkStore`（文件 + 内存） | 到期惰性重建；管理端改偏置后"热重载" |
| JWT 吊销名单 | `TokenBlacklist.blacklist`（ConcurrentHashMap） | 写内存 + 落库；读时先内存后 DB 并回填 |

`TokenBlacklist` 的双层设计（`TokenBlacklist.java:14-33`）是这份代码里最规范的一处：`invalidate()` 先写内存（保证当次进程内立即生效，不依赖 DB 可用性）再落库；`isBlacklisted()` 内存命中短路，未命中查 DB 后回填；启动时 `loadFromDatabase()`（`Main.java:542`）。DB 只存 token 的 **SHA-256 摘要**而非明文，`expires_at` 用于清理（`Main.java:298` 每 5 分钟清理过期项）。

### 4.4 宕机丢数据窗口

逐条列出真实风险窗口：

| 场景 | 数据损失 | 严重度 |
|---|---|---|
| **进程被 kill -9 / 断电** | **DB 层零丢失**——所有业务写入是同步 JDBC 写入，不存在内存脏页。SQLite 在 WAL 模式下已提交事务也是持久的。 | 无 |
| **文件快照丢失** | 最多丢 `auto-sync-seconds`（默认 30 秒）+ 调度抖动。但快照只是备份，**不丢真实数据**。 | 低 |
| **`PlayerDataService` 的 `dirtyPlayers` 集合** | `flushDirty()` 先 `dirtyPlayers.clear()` 再逐个导出，导出失败才重新 `add` 回去（`:129-141`）。若此时进程崩溃，这批 id 就丢了——下次快照要等到该玩家再次产生写入。仍是"备份延迟"，不是数据丢失。 | 低 |
| **`PlayerService.tickAutoHeal`** 每 10 秒批量 `UPDATE players SET hp = ...` | 无风险（幂等计算）。 | 无 |
| **`MySqlLauncher` 关闭钩子杀 MySQL** | **真实风险**：`killPreviousProcess()`（`MySqlLauncher.java:465-478`）在 JVM shutdown hook 里对 mysqld 执行 `destroy()`，5 秒后 `destroyForcibly()`。若 JVM 在 mysqld 尚未把 InnoDB 缓冲池刷盘时被强制终止，MySQL 需要崩溃恢复；`destroyForcibly` 更是直接 SIGKILL。见 §5.5。 | **中** |
| **`TokenBlacklist.persist` 失败** | 内存已写、DB 未写，日志告警；进程重启后该 token 复活（注释 `:23-24` 明确说明这个取舍）。 | 低 |
| **`GameLogger` / `PlayerActionLogger` 未 flush 的部分** | 每行 `println` + `flush()`（`GameLogger.java:242-243`、`PlayerActionLogger.java:196`），损失 ≤ 1 行。 | 无 |

**结论**：持久化策略的真实风险不在"丢数据"，而在 `MySqlLauncher` 的进程生命周期管理。

### 5.3 RateLimiter（145 行）

内存滑动窗口，`ConcurrentHashMap<String, RateWindow>`。V11 修复的三重保护（`:8-28` 注释）：

1. `MAX_ENTRIES = 100_000` 容量上限；
2. `maybeSweep()` 每 1024 次调用惰性清扫；
3. `evictIfOversized()` 超限时先清过期、再按 `windowStart` 淘汰到 90%。

`allow()` 用 `windows.compute(...)` 重建窗口，再 `synchronized (window)` 递增——**双层锁**，`compute` 内部对 bin 加锁、`synchronized` 对窗口对象加锁。存在一个正确的细节：`synchronized` 块内发现窗口已过期会 `windows.put(key, new RateWindow(...))` 并重新 `get`，避免了"在已淘汰的对象上计数"的竞态。

**已声明的设计限制**（`:24-27` 注释）：状态在单进程内存，重启清零，多实例部署阈值被放大为"单实例阈值 × 实例数"。诚实标注，但仍是生产部署的真实约束。

**21 个调用点**，覆盖：聊天（`ChatService:28/60`）、MC（`MinecraftAdapter:146`、`MinecraftPlayerAdapter:286`）、OneBot（`OneBotWebSocketServer:327/357/875`）、QQ 官方（`QqOfficialAdapter:940/964/1793`）、管理登录（`AdminResource:110/129`，含全局 20/60s + 单用户 5/60s 双层）、验证码（`Auth:134/137/140`，含 IP/邮箱/全局三层）、登录（`Auth:246/255`）、WS（`GameWebSocketApp:295`）、MC 指令 API（`McCommandResource:50`）。覆盖面完整。

### 5.5 MySqlLauncher（483 行）——嵌入式启动 MySQL 的做法与风险

**做法**：`ensureMySqlRunning()`（`:50-82`）

```
1. 从 database.url 解析 host:port
2. isPortOpen(host, port) → 已开则直接返回
3. Windows：搜索 mysqld.exe（多个候选路径 + PATH）→ startWithRetry（3 次重试，延迟 1s/3s/6s，最多等 30s）
4. Unix：先试 systemctl / service，失败则直接拉 mysqld 二进制
5. 启动后轮询端口，直到就绪或超时
```

**风险清单**：

1. **【高】关闭钩子会杀掉 MySQL**。`registerShutdownHookOnce()`（`:456-463`）注册的钩子调用 `killPreviousProcess()`：`destroy()` → 等 5 秒 → `destroyForcibly()`（`:465-478`）。`Main` 的 `DatabaseManager.shutdown()` 在钩子任务链的**倒数第二位**（`Main.java:115-118`），而 MySQL 进程的钩子是**独立注册的另一个钩子**——JVM 中多个 shutdown hook 并发执行、顺序不确定。因此完全可能出现"连接池还在关 → mysqld 已被 SIGKILL"。InnoDB 需要崩溃恢复；若同一台机器上还有别的应用在用这个 MySQL，等于被这个游戏服务器连带杀死。
2. **【中】没有凭据/参数控制**。启动 mysqld 时没有传 `--datadir`、`--port`、`--socket`、`--defaults-file`，完全依赖系统默认配置。若系统 MySQL 有自定义 `my.ini`，启动参数与游戏配置的 host/port 可能不匹配。
3. **【中】Unix 下 `systemctl` 几乎必然失败**（普通用户无权启服务），随后 fallback 到直接拉 `mysqld` 二进制——以当前用户身份运行，`datadir` 权限通常不够，失败后只有日志。
4. **【中】它假设"端口开着 = MySQL 可用"**。`isPortOpen` 只做 TCP 连通性检查，3306 上跑着别的服务（或 MySQL 但库不存在）时，`ensureMySqlRunning` 返回成功，随后 `DatabaseManager.init` 才炸。
5. **【低】只在 `database.type != sqlite` 且地址判定为本地时触发**（`Main.java:528-535`），默认配置是 sqlite，因此大多数部署不走这条路。但一旦启用 MySQL，上述风险全部生效。

### 5.6 StatsCollector（168 行）

内存统计单例（`getInstance()`），8 个 `ConcurrentHashMap`/`AtomicLong`：

- 消息：`totalMessages`、`byUser`(QQ→count)、`byGroup`、`byHour`；
- 指令：`totalCommands`、`byCmd`、`byGroup`、`byHour`。

查询侧输出 Gson `JsonObject`，`byUser`/`byGroup` 取 Top 20、`byCommand` 取 Top 30、`byTime` 固定 24 小时槽（`buildHourlyArray`，`:151-167`，无数据填 0）。时区硬编码 `Asia/Shanghai`（`:34`）。

**问题**：
- `messageByUser` / `messageByGroup` / `commandByCmd` / `*ByHour` **永不淘汰**。`byHour` 每小时新增一个 key（约 8760/年，可忽略）；`byUser` 以 QQ 号为 key，理论上界是用户数，可接受。整体内存风险低。
- 重启清零（`:15` 注释自认），无持久化，无法做跨重启趋势分析。
- `buildHourlyArray` 用 `Instant.now().toEpochMilli() / 3600000 * 3600000` 反推整点，与 `hourKey()` 的 `HOUR_FMT.format(Instant.now())` 走两条不同路径生成 key——若两者因时区/DST 出现偏差会静默丢数。

### 5.7 YamlFileEditor（368 行）——手写 YAML 编辑的风险

**为什么手写**：`AppConfig.update()` 需要"改值但保留注释、空行与缩进结构"，而 SnakeYAML 的 `dump()` 会丢掉全部注释。于是实现了一个行级编辑器（`update(Path, Map)`，`:42-103`）：

```
读全文 → 按 \r?\n 切行（保留末尾空元素）→ 第一遍删 null 值 → 第二遍替换/追加
→ 无变化则不写盘 → 临时文件 + UTF-8 写入 → Files.move(ATOMIC_MOVE)
```

写盘方式（`:92-99`）是**正确且专业**的：显式 UTF-8、临时文件、原子 rename。

**风险清单**：

1. **【中】没有写后校验**。`parse()` 方法存在（`:280+`，注释"写盘前校验用"），但**全项目 0 个调用点**（grep 确认）。写入后不重新解析验证，语法错误只会在下次启动时暴露。
2. **【中】不支持 YAML 全部语法**。编辑器只处理 `key: value` 标量行。以下全部会坏：
   - 块标量 `key: |` / `key: >` 的多行内容——`replaceValue` 只改第一行，后续缩进内容变成孤儿；
   - 列表项 `- item`——`findKeyLine` 会跳过，但 `insertKeyWithParents` 可能把新键插进列表中间；
   - 流式映射 `{a: 1}`、锚点 `&x` / 别名 `*x`、文档分隔符 `---`、tab 缩进。
   - 当前 `application.yml`（356 行）里确实用了多行列表（`allowed_domains:`，`application.yml:128`）和多行注释块，属于"暂时没被写坏"的运气区间。
3. **【中】缩进硬编码 2 空格**。`insertKeyWithParents` 假定每层 2 空格；改成 4 空格缩进的配置文件会被写出混合缩进。
4. **【低】引号判定靠启发式**。`isPlainSafe()`（`:343-367`）逐字符判断是否需要加引号，覆盖了首字符特殊符号、`#` 前有空格、`:` 后有空格、结尾空格等情形——写得相当细致，但 YAML 标量规则远比这复杂（例如 `y`/`yes`/`on`/`null`/`~` 在 YAML 1.1 里是布尔/null）。
5. **【低】`synchronized` 只保护单次调用**。`update()` 是 `static synchronized`，但 `AppConfig.update` 与 `PluginSwitches` 的两次调用之间不互斥，两个不同文件并发写各自安全。

**调用点仅 3 处**：`AppConfig.java:235`、`PluginSwitches.java:284`、`PluginSwitches.java:341`。影响面窄，风险可控。

### 6.1 语言包加载

两套语言包文件（**同一份数据被两套加载器读取**）：

1. classpath `data/mtxgdn/lang/<lang>.json`（jar 内置基线）
2. 外部 `config/lang/<lang>.json`（运维可改，`reload()` 或重启生效）
3. 插件 jar 内 `lang/<lang>.json`（运行时 `mergeFromStream` 注入）

加载顺序有硬约束：`Main.java:185-188` 明确 `I18nManager.load()` 必须在插件系统初始化**之前**，否则内置基线会覆盖插件词条（`putAll` 后来者胜）。`load()` 用 `loaded` 标志保证幂等。

`mergeFromStream`（`:104+`）**只增不删**：插件能覆盖同名 key，但停用插件后它的词条仍留在内存——注释（`:100-102`）自认这是"既有 LangManager 的语义，保留以不破坏现有插件"。

### 6.3 回退机制

三级回退链（`I18nManager.java:31-32` 注释）：

```
目标语言 → GameLanguage.fallback()（= ZH_CN）→ 原样返回 key 并记 WARN
```

`GameLanguage.fallback()`（`GameLanguage.java:49-51`）刻意**只回退一层**，注释解释："当前只有两门语言，级联只会让'某个 key 到底哪层补上'变得难查"。这个取舍在当前规模下正确。

`I18n.t(key)` 缺 key 时返回 key 本身（暴露漏翻译，便于测试发现），`I18n.tOr(key, fallback)` 返回人畜无害的兜底文案。`I18n.tOr` 还额外处理 `key == null || key.isBlank()`（`I18n.java:47-49`），注释说明不加这个判断会让"任何一处漏调 `setI18nKeys` 的命令在 `getDescription()` 里 NPE"。

`GameErrorCode.getLocalized()`（`GameErrorCode.java:109-113`）在语言包缺 key 时回落到枚举里硬编码的 zh_cn 文案，注释明确理由："不会把 `error.xxx` 这类 key 露给玩家"。

**线程安全**：`I18nContext` 用 `ThreadLocal<GameLanguage>`（`I18nContext.java:16`），注释记录了修复的动机——旧的 `LangManager.currentLang` 是进程级静态字段，"两个玩家同时在线时后设置的会覆盖前一个，导致 A 收到 B 的语言"。`LanguageRequestFilter` 在请求进入时 `set`（`:50`），`LanguageCleanupFilter` 在 `finally` 里 `clear`（`:29`）。

**语言协商优先级**（`LanguageRequestFilter.java:16-27`）：`?lang=` → `X-Lang` → `Accept-Language`（取第一个可解析项）→ 服务端默认。刻意不读玩家偏好（需要 userId，而过滤器必须跑在 `JwtAuthFilter` 之前，401 的错误信息也要本地化），玩家偏好在业务层由 `LanguageResolver` 按 userId 解析。

### 6.4 缺失词条统计（可观测性做得不错）

- `I18nFallbackCounts`（61 行）：`LongAdder` 分别统计 **fallbackHits**（某语言没翻完但回退兜住了）与 **misses**（连回退源都没有，真 bug），并支持按语言维度累加（`PER_LANGUAGE`）。注释明确区分两种语义（`:10-12`）。
- `I18nManager.reportMissing()`（`:292-299`）：首次出现才打 WARN（`reportedMissing` 集合去重），避免循环内刷屏。
- `missingKeys(GameLanguage)`（`:200+`）：以 `zh_cn` 为基线算差集，供 `GET /admin/i18n/status`（`AdminResource.java:2973`）和 `GameResource.java:322` 使用。
- `GET /admin/i18n/reload`（`AdminResource.java:3037`）支持运行中重载语言包。

**当前实际数据：`zh_cn` 与 `en_us` 的 key 集合完全一致（1529 = 1529，双向缺失 0）**，`missingCount` 恒为 0。这是好状态。

### 6.5 维护成本：两套并行的 i18n 系统（核心问题）

| | `com.mtxgdn.util.LangManager`（90 行，遗留） | `com.mtxgdn.i18n.*`（7 文件，新） |
|---|---|---|
| 语言来源 | **进程级 `static String currentLang = "zh_cn"`** | `ThreadLocal` + 请求协商 |
| 文件路径 | `/data/mtxgdn/lang/<lang>.json` | 同 + 外部 `config/lang/` |
| 回退 | **无**（`getOrDefault(key, key)`，直接露 key） | 三级回退 |
| 缺失统计 | **无** | `I18nFallbackCounts` |
| 外部覆写 | **不支持** | 支持 |
| 插件合并 | `merge(lang, stream)` | `mergeFromStream(lang, stream)` |
| 占位符 | **无** | `{0}` `{1}` |
| 使用方 | `Item`、`SecretRealm`、`ExplorationEvent`、`ItemRegistry`、`RedeemCodeService:256`、`ItemMapCommand:30`、`SpiritualRootCommand:68` | 全部指令、REST、错误码 |

**致命细节**：`LangManager.setLanguage(String)`（`LangManager.java:27-29`）**在整个 `src/main` 中零调用点**（grep 确认，只有定义）。因此 `currentLang` 永远是 `"zh_cn"`。

**后果**：`en_us` 玩家看到的是"指令文案是英文、物品/秘境/事件名字是中文"。`Item.getName()`（`Item.java:60-62`）、`SecretRealm.getName()`（`SecretRealm.java:44-46`）、`ExplorationEvent.getName()`（`ExplorationEvent.java:41-43`）全部硬锁 zh_cn。语言包里的 `item.*.name`（244 个 key）虽然 en_us 版本完整存在，但**运行时永远不会被 en_us 通路读取**。

这是一个高严重度、低修复成本的问题：把 `Item`/`SecretRealm`/`ExplorationEvent` 的 `getName()` 改成 `I18n.t(nameKey)`，或至少把 `LangManager.get` 委托给 `I18nManager`。

### 6.6 未国际化的内容（第三类缺口）

`skills` / `techniques` / `recipes` 三张表的 `name` 与 `description` 是**数据库里的中文字符串**（`SkillService.java:374-389` 硬编码 15 条 INSERT；`TechniqueService.java:316+`；`CraftingService.java:252+`）。这些内容：

- 不走语言包（`skill.*` / `technique.*` 的 40 个 key 全是 UI 提示文案，不含技能名）；
- 语言包里没有对应 key；
- 因此 `en_us` 玩家看到的技能名是中文。

即项目里存在**三种内容定义方式**：物品/秘境/事件用 `data.mtxgdn.*` 代码定义 + `LangManager` 取名；技能/功法/配方用 DB 表 + 硬编码中文；UI 文案用 `I18nManager` + 语言包。三者互不相通。

### 7.1 错误码体系（`GameErrorCode`，114 行）

**每个错误码携带三份信息**（`GameErrorCode.java:5-17` 注释）：

```java
AUTH_INVALID_TOKEN(1001, "error.auth_invalid_token", "token无效或已过期"),
//               ↑数字码  ↑i18n key                 ↑zh_cn 兜底文案
```

- `getCode()`：数字码，客户端逻辑判断；
- `getKey()`：i18n key，新客户端自行本地化；
- `getMessage()`：zh_cn 硬编码，日志与老客户端；
- `getLocalized()`：按当前请求语言取文案，缺 key 回落 `getMessage()`。

**码段划分**：

| 段 | 含义 | 数量 |
|---|---|---|
| 0 | OK | 1 |
| 1001-1005 | 认证 | 5 |
| 2001-2002 | 参数 | 2 |
| 3001-3002 | 角色 | 2 |
| 4001-4003 | 物品 | 3 |
| 5001-5005 | 境界 | 5 |
| 6001-6003 | 消息/限流 | 3 |
| 6101-6104 | 技能 | 4 |
| 7101-7102 | PVP | 2 |
| 8101-8104 / 8201-8202 / 8301-8302 / 8401-8404 | 秘境 / 游历 / 聊天 / 好友 | 12 |
| 9001-9002 | 内部/网络 | 2 |

合计 **41 个码**。分段基本有序，但 `6001-6003`（消息）夹在 `5005`（境界）和 `6101`（技能）之间，段位与模块不对应，属于历史遗留。整体设计**优于绝大多数同类项目**：数字码 + i18n key + 硬编码兜底三重冗余，且明确解释了为什么不全塞进语言包（"语言包缺失时仍要能给人看一句人话，而不是一行 `error.xxx`"）。

### 7.2 `ApiResponse` / `GameMessage`

- **`ApiResponse`（80 行）**：`{code, message, data:JsonObject}` + `isSuccess()`（`code == 0`）+ `fromJson`/`toJson`（Gson）。附带 `getToken()`、`getDataString/Long/Int(key)` 便捷读法。**是"通用 HTTP 响应壳"**，但代码库里更常用 `GameMessage.restOk(...)` 返回裸 `JsonObject`——两套响应格式并存。
- **`GameMessage`（215 行）**：`{msgId, type, code, key, message, data}`，WS 主用。`key` 字段可空（"纯动态拼接的消息没有对应 key"）。静态工厂丰富：`ok/okKeyed/error/errorKeyed/create` + 一组 `restOk/restError` 返回 `JsonObject`（给 REST 用）。

**兼容性设计**（`:42-43` 注释）：`message` 永远是**当前请求语言下已译好的文案**，所以老客户端读 `message` 行为不变；新客户端读 `key` 自行本地化。这是正确的渐进式国际化策略。

**问题**：`restOk` / `restError` 直接返回 `JsonObject`，与 `ApiResponse` 的 POJO 风格割裂；`code` 语义不统一——`GameMessage.code` 用 `GameErrorCode` 数字码（0/1001/…），而 `AdminResource` 等 REST 端点用 HTTP 语义码（200/400/404/500）。同一条 API 上 `code` 可能是 0/1001 也可能是 200，客户端必须按端点区分。

### 7.3 `ServiceRegistry`（347 行）——服务定位器模式评价

**实现**：27 个 `static volatile` 字段 + 27 个 `getXxxService()` 方法，每个方法都是同一个双重检查锁模板：

```java
public static PlayerService getPlayerService() {
    if (playerService == null) {
        synchronized (ServiceRegistry.class) {
            if (playerService == null) { playerService = new PlayerService(); }
        }
    }
    return playerService;
}
```

`RealmService` / `SecretRealmService` / `ExplorationService` 等在构造时注入 `getPlayerService()`，形成隐式依赖图。

**优点**：

- 极简，零框架依赖；
- 有懒加载，避免启动期构造全部 Service；
- 部分 Service 通过构造器接收依赖（`new RealmService(getPlayerService())`），保留了可测性；
- `synchronized` 全部集中在 `ServiceRegistry`（28 处，是全项目 synchronized 最多的文件），业务 Service 本身是无状态单例，线程安全靠"不持有可变状态 + 每次自建连接"实现。

**缺点**：

1. **27 个方法 × 7 行 = 约 200 行样板代码**，纯手写，加一个 Service 要复制粘贴一整块。
2. **全局可变静态状态**：27 个 `static volatile` 字段**没有重置入口**。测试之间无法隔离（除非反射改字段），`unregister` 之类的能力完全不存在。而 `ItemRegistry` / `SecretRealmRegistry` / `ExplorationEventRegistry` / `CommandRegistry` 都提供了 `clear()`——只有 `ServiceRegistry` 没有，这是明显的不一致。
3. **隐藏依赖**：任何类 `import ServiceRegistry` 后就能拿到任意 Service，编译期看不到依赖关系。`LanguageResolver` 为了拿一个 `player.getLanguage()` 就去 `ServiceRegistry.getPlayerService().getPlayerInfoById(playerId)` 打一次库（`LanguageResolver.java:29-35`）——静态可及性鼓励了这种"随手取用"。
4. **无生命周期钩子**：`shutdown()` 分散在各 Service 自己身上（`TradeService.shutdown()`、`EconomyService.shutdown()`、`PlayerService.shutdown()`），由 `Main.registerShutdownHook()`（`Main.java:86-120`）手工按顺序调用 8 个任务。新增带调度线程的 Service 必须记得去 `Main` 里加一行，否则线程泄漏。
5. **`synchronized (ServiceRegistry.class)` 与业务代码共用同一把类锁**——所有 27 个 getter 串行化首次初始化。启动期可接受，但若某个 Service 构造较慢，会阻塞其它 Service 的首次获取。

**评价**：在"无 DI 框架、无 Spring"的约束下，这是**合理但不理想**的选择。它解决了"如何拿到 Service"，但把"依赖关系"变成了隐式的、不可静态分析的、不可重置的全局状态。`Command` 体系（§8.1）的注册式设计比它更干净，说明团队知道更好的模式，只是 Service 层没迁移。

## 8. 内容数据（`data.mtxgdn`）

### 8.1 声明式定义模式：构造器即注册

三类内容共享**完全同构**的模式：

```java
// 基类构造器 = 数据声明 + 自动注册
public abstract class Xxx {
    protected Xxx(String namespace, String key, ...) {
        this.fullKey = namespace + ":" + key;      // 1. 命名空间化 key
        this.nameKey = "xxx." + key + ".name";     // 2. 派生 i18n key
        this.descKey = "xxx." + key + ".desc";     // 3. 派生 i18n key
        ...
        XxxRegistry.register(this);                 // 4. 自我注册
    }
}
```

- `Item`（`Item.java:22-36`）：`fullKey`、`nameKey = "item.<key>.name"`、`descKey = "item.<key>.desc"`、`type`、`rarity`、`effects`、`maxStack`、`price`、`tradeable`、`requiredRealm`，末尾 `ItemRegistry.register(this)`。
- `SecretRealm`（`SecretRealm.java:14-28`）：`fullKey`、`name = "secretrealm.<key>.name"`、`requiredRealm`、`cooldownMs`、`raid`，末尾 `SecretRealmRegistry.register(this)`。
- `ExplorationEvent`（`ExplorationEvent.java:19-25`）：`fullKey`、`name = "explorationevent.<key>.name"`、`weight`，末尾 `ExplorationEventRegistry.register(this)`；另有 `abstract execute(Player, PlayerService, ItemService, Random, ExplorationResult, List<String>)`。

**扫描机制**（四处扫描器代码**几乎逐行相同**，是明显的复制粘贴）：

`ItemScanner` / `SecretRealmScanner` / `ExplorationEventScanner` / `CommandScanner` 的 `scanAndRegister()` 逻辑完全一致：

```
1. findClassesInPackage(pkg)
   - classLoader.getResources(packagePath)
   - protocol == "file" → 递归遍历目录，Class.forName
   - protocol == "jar"  → 打开 JarFile 遍历 entry，Class.forName
   - 兜底：user.dir + "/target/classes/" + packagePath
2. 逐个 class 过滤：
   - 不是基类子类 → skip "(未继承Xxx)"
   - 是基类本身 → skip "(基类)"
   - abstract → skip "(抽象类)"
   - 非 public → skip "(非public)"
3. clazz.getDeclaredConstructor().newInstance()   ← 构造器副作用完成注册
4. 返回 ScanResult{registered, skipped, failed}
```

硬编码的包名常量：`ItemScanner.java:14` `"data.mtxgdn.item"`、`SecretRealmScanner.java:14` `"data.mtxgdn.secretrealm"`、`ExplorationEventScanner` 同构、`CommandScanner.scanAndRegister("com.mtxgdn.onebot.command")`（`Main.java:182` 传入）。

**启动顺序**（`Main.java:160-188`）：

```
insertDefaultTechniques()  →  insertDefaultRecipes()  →  insertDefaultSkills()
→ ItemScanner.scanAndRegister()        // 115 个类
→ EquipmentDataChecker.checkEquipmentData()
→ SecretRealmScanner.scanAndRegister()  // 10 个
→ ExplorationEventScanner.scanAndRegister()  // 13 个
→ CommandScanner.scanAndRegister("com.mtxgdn.onebot.command")
→ I18nManager.load()
→ PluginManager 初始化
```

**这个模式的优点**：

- 新增一个物品 = 新增一个 13 行文件，零配置、零注册表维护、零 XML；
- 编译期类型安全（`ItemType.TREASURE` 拼错编译不过）；
- 可以用 IDE 的 "find usages" 反查；
- 扫描结果 `ScanResult.toString()` 输出 registered/skipped/failed 三档明细，启动日志里能看到"注册 115 个、跳过 0 个、失败 0 个"。

**缺点**：

1. **构造器有副作用**。`new Item(...)` 就注册进全局 Map，意味着无法"只创建不注册"、无法在测试里造一个临时物品而不污染全局。三个 Registry 都提供了 `unregister` / `clear` 作为补偿，但这是治标。
2. **类扫描依赖类加载器的行为**。`findClassesInJar` 用 `resource.getPath()` 手工剥 `file:` 前缀和 `!` 后缀（`ItemScanner.java:104-108`），**没有 URL 解码**。JAR 路径含空格或中文时（Windows 上极常见，例如 `C:\Users\张三\...`）会得到 `%E5%BC%A0%E4%B8%89`，`new JarFile(...)` 直接抛异常 → `scanAndRegister` 返回 `failed=["扫描包失败: ..."]` → **所有物品静默消失**。代码里有 `target/classes` 兜底（`:78-81`），但那只覆盖"目录协议"的情况，JAR 部署 + 非 ASCII 路径是最坏组合。四个扫描器都有这个问题。
3. **重复注册只告警不阻止**：`ItemRegistry.register`（`ItemRegistry.java:21-29`）发现同 key 已存在时 `LOG.warn("物品覆盖: ...")` 然后**覆盖**。`CommandRegistry.register`（`:27-37`）更严谨一些，会比对 `previous.getClass() != command.getClass()`，避免"同一个类重复注册"的误报。四个 Registry 的行为不一致。
4. **`LinkedHashMap` 的顺序 = 类加载顺序**，不可控。`SecretRealmRegistry.getByIndex(int)`（`:82-88`）先按 `requiredRealm` 排序再取下标，避开了这个问题；但 `ExplorationEventRegistry.randomByWeight`（`:62-82`）按 `events.values()` 迭代顺序累加权重，虽然数学上正确（概率与顺序无关），但 `totalWeight <= 0` 时的兜底 `events.values().iterator().next()`（`:71`）返回的是**任意一个**——取决于类加载顺序。

**与物品/秘境的关键差异：探索事件是"带行为的"，不是纯数据。** 每个事件实现 `execute(...)`，里面是真实的业务逻辑（`SpiritSpringEvent.java:18-51`，34 行；`MysteryEvent` 4,538 字节最大）。

**这导致内容层直接写了 SQL**（内容层的分层违规）：

```java
// data/mtxgdn/explorationevent/SpiritSpringEvent.java:40-48
try (var conn = com.mtxgdn.db.DatabaseManager.getConnection();
     var ps = conn.prepareStatement(
         "UPDATE players SET hp = LEAST(max_hp, hp + ?), mp = LEAST(max_mp, mp + ?) WHERE id = ?")) {
    ps.setInt(1, healHp); ps.setInt(2, healMp); ps.setLong(3, player.getId());
    ps.executeUpdate();
} catch (Exception e) { throw new RuntimeException("恢复生命法力失败", e); }

// data/mtxgdn/explorationevent/TrapEvent.java:29-36
try (var conn = com.mtxgdn.db.DatabaseManager.getConnection();
     var ps = conn.prepareStatement("UPDATE players SET hp = ? WHERE id = ?")) { ... }
```

三个问题：

1. **方言不兼容**：`LEAST(...)` 是 MySQL 函数，SQLite 没有。`SpiritSpringEvent` 在 SQLite 部署（= 默认配置）下**每次触发都会抛 `RuntimeException`**。同项目里 `PlayerService.java:777-779` 用 `DatabaseManager.isSqlite()` 做了分支，说明团队知道这个问题，只是这处漏了。
2. **绕过了 PlayerService**：`TrapEvent` 直接 `UPDATE players SET hp = ?`，不经过 `PlayerService.updatePlayer`，因此**不调用 `markDataDirty`**——扣血不会触发文件快照更新（`PlayerService.updatePlayer:321` 才 markDirty）。玩家的 HP 变化在下一次其它写入之前不会进快照。
3. **文案硬编码中文**：事件里 `log.add("💧 你发现了一处隐秘的灵泉！...")`（`SpiritSpringEvent.java:35-38`）、`result.setEventDescription("灵泉沐浴")`（`:22`）全部是 Java 字符串字面量，**不走 i18n**。而 `ExplorationEvent.getName()` 走的是 `LangManager`（也是 zh_cn 锁定，见 §6.5）。即事件的"名字"和"正文"是两套不同的（都不可翻译的）机制。

其余 11 个事件通过 `playerService.addExperience(...)` / `itemService.addItem(...)` 走正规路径，只有这两个"直接改玩家属性"的事件越层。

### 8.5 扩展一个物品需要改哪些地方

**最小路径（2 处）**：

1. 新建 `src/main/java/data/mtxgdn/item/XxxYyy.java`（13 行，继承 `Item`，构造器调 `super(...)`）——扫描器自动发现，无需注册任何地方。
2. 在 `data/mtxgdn/lang/zh_cn.json` 与 `en_us.json` 各加 2 个 key：
   ```
   "item.xxx_yyy.name": "物品名",
   "item.xxx_yyy.desc": "物品描述"
   ```

**若要让它真正产出（3~5 处，取决于用途）**：

3. **掉落来源**：改 `data/mtxgdn/explorationevent/*.java` 里某个事件的 `itemService.addItem(playerId, "mtxgdn:xxx_yyy", n)`。
4. **配方产出**：`CraftingService.insertDefaultRecipes()`（`CraftingService.java:252+`）里加一条 `INSERT INTO recipes ...`（硬编码中文名 + `result_item_key`）。
5. **商店/坊市可交易**：`Item` 构造器的 `tradeable` 参数置 `true`（价格由 `price` 决定）。
6. **若要给玩家一个获取途径**：`/发放` 类管理指令走 `ItemRegistry.resolve(input)`（`ItemRegistry.java:44-78`），它支持三种输入：完整 key `mtxgdn:xxx_yyy`、中文名精确匹配、中文名包含匹配（`findByTranslatedName` 两次遍历全表，O(n) 模糊匹配）。

**不需要改的地方**（这是模式的价值）：`ItemRegistry`（自动注册）、`ItemScanner`（自动扫描）、任何 switch/enum（`ItemType`/`ItemRarity` 是既有枚举，新物品复用）。

**需要注意的坑**：

- `Item.getName()` 走 `LangManager`，**新增 en_us key 对英文玩家无效**（§6.5）。
- `FormationItem` 子类（`super(key, rarity, level)`，3 参数）与 `Item` 子类（9 参数）签名完全不同，新增阵法物品要用前者的形态。
- `maxStack`/`price` 相邻同类型，写反不报错。
- 115 个物品里 `ItemType.EQUIPMENT` 一个都没用；若想加装备，走的是 `EquipmentDataChecker` + `players_equipment` 那条路径，而不是 `ItemType.EQUIPMENT`。

### 关于"无 ORM"这个选择的评价

这个项目**不应该**引入 ORM。理由：

- 40 张表的 schema 高度定制（`LEAST`/`ON DUPLICATE`/`PRAGMA`/`FOR UPDATE`），JPA 的方言层反而会打架；
- 已有 5 张表的"UPSERT 语义"和 7 张表的"原子 CAS 语义"（`claimOfflineTime`、`world_bosses` 的 `UNIQUE(scope,slot)` 护栏），这些是 ORM 最难表达的部分；
- 性能敏感路径（自动回血每 10 秒全服 UPDATE、Boss 血量 CAS）需要精确控制 SQL。

真正缺的不是 ORM，而是 **Repository 边界** 和 **事务模板**。建议方向：

- 用 `runTransaction(conn -> ...)` 作为唯一事务入口（现已 72 处使用），把剩余 7 处手写 `setAutoCommit` 也收编进来；
- 用 `*Repository` 类承载 SQL，Service 只做业务编排；
- 用 `conn` 重载作为事务传播的唯一约定，并**加静态检查**（凡是有 `(Connection, ...)` 重载的方法，无 conn 版本必须委托给它，反之亦然）——H3 这个 bug 就是这条约定被打破的直接后果。
