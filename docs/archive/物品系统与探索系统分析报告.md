## 二、物品效果系统设计分析

### 2.1 架构评价

**优点：**
- ✅ 采用策略模式（Strategy Pattern），每种效果独立为一个 `ItemEffect` 子类，扩展性好
- ✅ `ItemRegistry` 使用 `LinkedHashMap` 保证注册顺序，支持按 fullKey 查找、按类型/稀有度筛选
- ✅ `ItemScanner` 支持文件系统和 JAR 两种扫描方式，兼容性好
- ✅ `Item.use()` 作为入口统一调用各 Effect 的 `execute()`
- ✅ `EmptyEffect` 使用单例模式（`INSTANCE`），避免无效果物品创建多余对象

**设计问题：**

#### 🔴 问题1：多个 Effect 未真正执行业务逻辑（严重程度：高）

| 文件 | 问题 |
|------|------|
| `RealmBreakEffect.java` | `execute()` 只返回提示文字，未调用任何 PlayerService 方法设置突破加成。实际加成由 `RealmService` 突破流程读取，但 **execute 里没有设置状态**，依赖外部逻辑，耦合隐蔽 |
| `TribulationPillEffect.java` | 同上，只返回字符串，没有任何状态写入。玩家使用后**看不到任何数据库变化**，下次突破时是否有加成完全依赖 `RealmService` 的独立检查逻辑 |
| `DebuffCleanEffect.java` | `execute()` 只返回固定字符串 `"使用净化丹药，清除所有负面状态"`，**未调用任何服务清除 debuff** |
| `InventoryCapacityEffect.java` | `execute()` 只返回 `"背包容量 +X 格"`，**未修改任何背容量字段** |
| `TeleportEffect.java` | `to(String destination)` 方法**完全忽略 destination 参数**，硬编码为太虚城（ID=4L） |

**文件位置：**
- `src/main/java/com/mtxgdn/game/item/RealmBreakEffect.java:26-28`
- `src/main/java/com/mtxgdn/game/item/TribulationPillEffect.java:12-14`
- `src/main/java/com/mtxgdn/game/item/DebuffCleanEffect.java:27-29`
- `src/main/java/com/mtxgdn/game/item/InventoryCapacityEffect.java:26-28`
- `src/main/java/com/mtxgdn/game/item/TeleportEffect.java:21-25`

#### 🔴 问题2：BuffEffect 生成的 buffId 存在碰撞风险（严重程度：中）

**文件：** `src/main/java/com/mtxgdn/game/item/BuffEffect.java:81`

```java
buffService.addBuff(playerId, "buff_" + attackBonus + "_" + defenseBonus + "_" + speedBonus + "_" + spiritBonus, ...);
```

buffId 由数值参数拼接生成。若两种不同丹药恰好属性值相同（如攻+30 防+20 和攻+30 速+0 灵+0 防+20），生成的 buffId 会完全相同，导致后者**不叠加而是刷新时长**。这种碰撞在丹药种类增多后概率上升。

**修复建议：** 在 buffId 中加入物品 fullKey 或使用 UUID 前缀。

#### 🟡 问题3：ExpEffect 返回值末尾有多余逗号（严重程度：低）

**文件：** `src/main/java/com/mtxgdn/game/item/ExpEffect.java:28`

```java
return "获得了 " + expGain + " 点经验，";  // 末尾逗号
```

HealEffect 同样存在末尾逗号问题。如果多个 Effect 组合输出拼接，会产生 `获得了 X 点经验，恢复了 Y 点生命值，` 这样以逗号结尾的文本。

#### 🟡 问题4：LearnSkillEffect 每次执行都 `new SkillService()`（严重程度：低）

**文件：** `src/main/java/com/mtxgdn/game/item/LearnSkillEffect.java:28`

```java
SkillService skillService = new SkillService();
```

ExpMultiplierEffect（第33行）和 ReflectionBuffEffect（第33行）也有同样问题。建议通过依赖注入或静态工厂获取服务实例。

#### 🔴 问题5：RebirthEffect 使用 Integer.MAX_VALUE 实现满血（严重程度：高）

**文件：** `src/main/java/com/mtxgdn/game/item/RebirthEffect.java:29-30`

```java
playerService.addHp(playerId, Integer.MAX_VALUE);
playerService.addMp(playerId, Integer.MAX_VALUE);
```

如果 `addHp` 是做加法而非设上限，HP 会溢出到负数。同样的问题出现在 `AttributeResetEffect.java:19-20`。正确做法应该是读取 maxHp/maxMp 然后设置为满值。

#### 🟡 问题6：PurificationEffect 多次查询 Player（严重程度：低）

**文件：** `src/main/java/com/mtxgdn/game/item/PurificationEffect.java:14-17`

```java
int maxHp = playerService.getPlayerById(playerId) != null
        ? playerService.getPlayerById(playerId).getMaxHp() : 100;
int currentHp = playerService.getPlayerById(playerId) != null
        ? playerService.getPlayerById(playerId).getHp() : 0;
```

对同一 playerId 调用了 4 次 `getPlayerById()`，应缓存一次查询结果。

### 3.2 分析结论

#### 🔴 问题7：MYTHIC 级别仅有 1 个物品（严重程度：高）

**文件：** `src/main/java/data/mtxgdn/item/QilinAmulet.java`

圣品（MYTHIC）作为最高稀有度，仅有 **QilinAmulet** 一个物品。这导致：
- 最高稀有度的收集感极弱
- 掉落表中几乎没有圣品物品的获取途径
- 该物品被 BossForm 的 RAID_REWARD_TABLES 中 realm 5+ 的奖励表引用，但实际获取概率极低

**修复建议：** 补充 3-5 个 MYTHIC 物品，或将其降级为 LEGENDARY。

#### 🟡 问题8：LEGENDARY 级别的物品类型偏科（严重程度：中）

LEGENDARY 级别中大量是**合成材料**（FiveColoredDivineStone, DragonHeart, QilinBlood, PhoenixGallbladder, TenThousandYearLingzhi），缺乏消耗品和装备。唯一的 LEGENDARY 装备是 DragonSword、PhoenixArmor、JadeArmor。

| SeedEvent | 12 | 7.9% | 种子 |
| MaterialEvent | 10 | 6.6% | 材料 |
| MerchantEvent | 10 | 6.6% | 物品/金币 |
| RuinsEvent | 10 | 6.6% | 随机奖励 |
| MysteryEvent | 8 | 5.3% | 随机奖励 |
| SpiritSpringEvent | 8 | 5.3% | 恢复+经验 |
| TrapEvent | 7 | 4.6% | 扣血 |

### 4.2 分析结论

#### 🟡 问题9：TreasureEvent 与 MonsterEvent 权重相同但奖励差距大（严重程度：中）

两者权重均为 25（16.4%），但 TreasureEvent **100% 给予金币+灵石**（无风险），而 MonsterEvent **有概率输掉战斗什么都不得到**。从期望值来看，TreasureEvent 明显优于 MonsterEvent，这会让玩家对"遭遇妖兽"产生负面情绪。

**修复建议：** 降低 TreasureEvent 权重至 18-20，或提高 MonsterEvent 击败后的奖励。

#### 🟡 问题10：CultivatorEvent 中物品 key 使用了无命名空间格式（严重程度：中）

**文件：** `src/main/java/data/mtxgdn/explorationevent/CultivatorEvent.java:41`

```java
String[] items = {"spirit_grass", "iron_ore", "healing_pill", ...};
```

这些 key 没有加 `mtxgdn:` 前缀。但后续检查使用 `ItemRegistry.contains(giftItem)`，而 ItemRegistry 中存储的 fullKey 带有前缀（如 `mtxgdn:spirit_grass`）。因此 **`contains()` 会返回 false，物品永远不会被赠予**，30% 的"赠送物品"分支实际会回退到"赠送金币"分支。

**修复建议：** 将数组改为 `{"mtxgdn:spirit_grass", "mtxgdn:iron_ore", ...}`。

#### 🟡 问题11：RuinsEvent 引用了不存在的物品 key（严重程度：中）

**文件：** `src/main/java/data/mtxgdn/explorationevent/RuinsEvent.java:27-29`

```java
String[] rareItems = {"mtxgdn:cultivation_elixir", ..., "mtxgdn:basic_sword_manual", ..., "mtxgdn:spirit_stone_pouch"};
```

经验证 `basic_sword_manual` 和 `spirit_stone_pouch` 确实存在注册。但列表中的 `"mtxgdn:cultivation_elixir"` 需确认 —— 实际物品 key 是 `cultivation_elixir`（`CultivationElixir.java` 中注册），所以这些 key 都是正确的。此项无问题。

但有一个设计问题：RuinsEvent 的 rareItems 数组中混入了 **COMMON 级别的 BasicSwordManual（100金币售价）** 和 **COMMON 级别的 SpiritStonePouch（5个下品灵石）**，与 RARE/EPIC 物品放在同一个稀有奖励池中，稀释了真正稀有物品的获取概率。

#### 🔴 问题12：TrapEvent 直接操作数据库绕过 Service 层（严重程度：高）

**文件：** `src/main/java/data/mtxgdn/explorationevent/TrapEvent.java:29-36`

```java
try (var conn = com.mtxgdn.db.DatabaseManager.getConnection();
     var ps = conn.prepareStatement("UPDATE players SET hp = ? WHERE id = ?")) {
    ps.setInt(1, newHp);
    ps.setLong(2, player.getId());
    ps.executeUpdate();
}
```

同样的问题出现在 `SpiritSpringEvent.java:37-45`。这两个事件绕过了 `PlayerService` 直接操作数据库：
1. 绕过了可能的业务逻辑（如死亡检测、日志记录、buff 影响等）
2. 与其他事件使用 `playerService.addHp()` 的模式不一致
3. 如果 PlayerService 中的 `addHp()` 有上限保护或事件触发，这些事件都不会触发

**修复建议：** 改为使用 `playerService` 的方法或封装一个专用的 `setHp()` 方法。

### 5.3 分析结论

#### 🔴 问题13：境界 3 出现两个同冷却时间的秘境但难度不对等（严重程度：中）

ThunderValley（Raid，300s）和 AncientRuins（普通，300s）都是 realm 3，冷却相同。Raid 秘境有 3 个 Boss 阶段（参考 BossForm），而 AncientRuins 仅有随机事件。但它们共享同一个 cooldown，玩家进入一个后无法进入另一个。

**修复建议：** 考虑让 Raid 和普通秘境使用独立的冷却计时器，或增加区分。

#### 🟡 问题14：SecretRealm 基类缺少 rewardTable / difficulty 字段（严重程度：中）

**文件：** `src/main/java/com/mtxgdn/game/secretrealm/SecretRealm.java`

SecretRealm 仅定义了 `requiredRealm`、`cooldownMs`、`raid` 三个字段。所有奖励逻辑都硬编码在 `SecretRealmService.generateRealmEvent()` 中。这意味着：
1. 添加新秘境时无法自定义奖励池
2. 不同秘境之间的差异化完全依赖 if-else 判断 `area.getKey()`
3. Boss 奖励也是硬编码在 `BossForm.createFormsForRealm()` 中

**修复建议：** 在 SecretRealm 基类中添加 `lootTable`、`rewardMultiplier` 等字段。

#### 🟡 问题15：高级秘境专属奇遇仅区分两个秘境（严重程度：低）

**文件：** `src/main/java/com/mtxgdn/game/service/SecretRealmService.java:168`

```java
if ("hunyuan_mansion".equals(area.getKey())) { ... }
// else -> 太虚天宫
```

只有 HunyuanMansion 和 TaiXuPalace 有专属事件。其余 8 个秘境的事件逻辑完全相同，差异化不足。

#### 🟡 问题16：秘境冷却检查与更新不是原子操作（严重程度：中）

**文件：** `src/main/java/com/mtxgdn/game/service/SecretRealmService.java:69-89`

```java
boolean canEnter = com.mtxgdn.db.DatabaseManager.runTransaction(conn -> {
    String checkSql = "SELECT last_secret_realm_time FROM players WHERE id = ? FOR UPDATE";
    ...
    String updateSql = "UPDATE players SET last_secret_realm_time = ? WHERE id = ?";
    ...
});
```

使用了 `FOR UPDATE` 和事务，但 **runTransaction 返回的是 Boolean**。如果玩家在事务提交前断线，可能会导致冷却时间被设置但事件未执行。此外，**整个方法的事务性不够完整** —— 后续的 `generateRealmEvent()` 不在同一事务中，可能导致计数+1但事件失败的不一致。

## 六、掉落/奖励系统分析

### 6.1 怪物掉落

| 怪物类型 | 掉落概率 | 掉落池 |
|---------|---------|--------|
| 普通怪 | 30-45% | COMMON_LOOT（灵草/铁矿/治疗药/法力药/兽核） |
| Boss怪 | 60-85% | BOSS_LOOT（3个等级，随机选1个池） |
| Raid Boss | 50-80% | RAID_REWARD_TABLES（6个等级） |

### 6.2 掉落问题

#### 🔴 问题17：普通怪掉落表无境界差异化（严重程度：高）

**文件：** `src/main/java/com/mtxgdn/game/entity/Mster.java:64-66`

```java
private static final String[][] COMMON_LOOT = {
    {"mtxgdn:spirit_grass"}, {"mtxgdn:iron_ore"}, {"mtxgdn:healing_pill"}, 
    {"mtxgdn:mana_pill"}, {"mtxgdn:spirit_recovery_pill"}, {"mtxgdn:beast_core"}
};
```

无论玩家境界多高，普通怪永远掉落这 6 种 COMMON 级别物品。高境界玩家打怪获得的战利品与新手完全相同，缺乏正反馈。

**修复建议：** 根据怪物 realm 分层掉落表。

#### 🟡 问题18：Boss 掉落池等级划分基于随机而非 Boss 难度（严重程度：中）

**文件：** `src/main/java/com/mtxgdn/game/entity/Monster.java:105`

```java
String[] loot = BOSS_LOOT[random.nextInt(BOSS_LOOT.length)];
```

3 个 BOSS_LOOT 池随机选取一个，不是根据玩家境界或 Boss 等级选择。这意味着 realm 1 的 Boss 也有概率掉落 LEGENDARY 级别物品（heaven_pill 在 BOSS_LOOT[2] 中）。

#### 🟡 问题19：SeasonService 的 dropMultiplier 未在探索事件中生效（严重程度：中）

**文件：** 搜索结果显示 `SeasonService.getDropMultiplier()` 仅在 `CombatService.pveFight()`（第839行）和 `GameWebSocketApp`（第956行）中使用。

但探索事件中的 TreasureEvent、MaterialEvent、MysteryEvent 等给予物品/灵石时**不经过 CombatService**，因此季节掉率加成对这些事件无效。如果设计意图是季节活动影响所有掉落，这是个遗漏。

## 十、总结

**整体评价：** 物品系统和探索系统的基础架构设计合理，采用了策略模式、注册表模式、自动扫描等成熟方案。但在**效果系统的完整性**、**数值平衡**和**代码一致性**方面存在不少需要修复的问题。

最核心的问题是**多个 ItemEffect 的 execute() 方法只有外壳没有内核**——它们返回了漂亮的提示文字，但并未真正修改玩家数据。这可能是开发过程中"先占位后实现"的遗留，也可能是设计意图依赖外部系统读取（如 RealmBreakEffect），但这种隐式契约在代码中没有任何文档或断言保护，极易在后续维护中引发 bug。
