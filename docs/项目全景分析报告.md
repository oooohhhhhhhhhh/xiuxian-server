# 第一部分 · 最基础的一层：这是什么项目

## 1. 项目定位与形态

### 1.1 一句话定义

**一个单进程的 Java 多人在线文字修仙（MUD）游戏服务端**：自己实现玩法（修炼/突破/战斗/宗门/坊市/农场/秘境/世界 Boss），自己实现 HTTP + WebSocket 服务，自己实现插件系统，再把同一套玩法通过 **REST / WebSocket / OneBot QQ / QQ 官方机器人 / Minecraft** 五条通道暴露给玩家与运维。

它不是框架、不是库，是一个**可独立部署的产品级服务端**，同时保留了二次开发能力（插件 + 内容数据 + 指令扩展）。

### 1.2 形态特征

| 维度 | 事实 |
|---|---|
| 进程模型 | **单 JVM 单进程**。无微服务、无消息队列、无外部缓存。HTTP、WebSocket、OneBot、MOTD 全部在同一进程的不同端口上 |
| 状态模型 | **数据库为中心 + 少量内存态**。绝大多数玩法状态落 MySQL/SQLite；只有「玩家数据 JSON 快照」「野外分片」「PvP 挑战」「队伍」「限流窗口」等在内存/文件 |
| 扩展模型 | 两套并存：**外部插件**（`plugins/*.jar`，独立 ClassLoader）+ **内置玩法模块**（编译进主 jar 的 25+2+4 个模块，靠 `config/plugins.yml` 开关） |
| 多端一致性 | 同一 `Command` 可同时注册为 QQ 指令与 REST 路由（`addRoute`），因此**玩法逻辑只有一份**，入口有多份 |
| 国际化 | JSON 语言包（`zh_cn` / `en_us`），1,529 个词条；**已迁移约一半**（1,202 处 `I18n.t()`，仍有 2,672 处裸中文字面量） |
| 目标部署 | 单机/小服。默认 SQLite + 默认监听 `127.0.0.1`，明显面向「个人开服」而非大规模集群 |

### 1.3 版本与生命周期

- 版本号唯一来源：`pom.xml:12` 的 `<version>0.1.0</version>`，经资源过滤写入 `build-info.properties`，同时写入 JAR manifest，由 `com.mtxgdn.util.BuildInfo` 读取（`pom.xml:9-12, 264-271`）。这是**做得很好的一处**：版本号单点定义，避免了「pom 改了 jar 里还是旧的」这类经典问题。
- `CHANGELOG.md` 1,409 行，覆盖 `V1.3.0 → V1.4.0 → V1.4.1-alpha1/2/3 → V1.4.1-beta2 → 未发布`，条目写得非常细（每条都解释「为什么改」）。
- 注意：`pom.xml` 版本是 `0.1.0`，而 `CHANGELOG` 已写到 `V1.4.1-beta2`。**版本号体系存在两套**（Maven 的 `0.1.0` vs 产品线的 `V1.4.x`），读者容易困惑，属于文档债务。

## 3. 技术栈与依赖风险

### 3.1 依赖清单（`pom.xml` 实测）

| 依赖 | 版本 | 用途 | 评估 |
|---|---|---|---|
| `mysql-connector-j` | 9.7.0 | MySQL 驱动 | 较新，OK |
| `sqlite-jdbc` | 3.49.1.0 | 默认数据库 | OK；注意 SQLite 并发写限制 |
| `gson` | 2.14.0 | JSON | 全项目 JSON 主力，OK |
| `jersey-container-grizzly2-http` | 4.0.2 | REST | 4.x 已切 Jakarta EE 命名空间，版本较新 |
| `jersey-hk2` | 4.0.2 | DI | **实际未使用注解注入**，仅用于 Jersey 运行时 |
| `grizzly-websockets` / `grizzly-http-servlet` | 4.0.2 | WebSocket | Grizzly 社区活跃度已下降，是**技术栈里最脆的一环** |
| `jakarta.servlet-api` | 6.0.0 | WebSocket 升级 | OK |
| `jersey-media-json-jackson` | 4.0.2 | JSON Provider | **冗余**：项目全程用 Gson 手工序列化，Jackson 只被 Jersey 内部用到 |
| `jjwt-api/impl/jackson` | **0.11.5** | JWT | ⚠ 0.11.x 是**旧 API 分支**（`Jwts.parserBuilder` 系），0.12.x 已重构；且 `jjwt-jackson` 只为运行时 |
| `jbcrypt` | 0.4 | 密码哈希 | ⚠ 2014 年后停更；仅支持 `$2a$`；建议迁 `at.favre.lib:bcrypt` 或 Spring Security Crypto |
| `HikariCP` | **5.0.1** | 连接池 | ⚠ 明显落后（当前 6.x）。5.0.1 对 JDK 23 无已知阻断，但属「该升级」项 |
| `angus-mail` | 2.0.3 | 邮件 | OK |
| `snakeyaml` | 2.4 | YAML | OK（2.x 已修 CVE-2022-1471 系列） |
| `junit-jupiter` | 5.10.1 | 测试 | 可升 5.11+ |
| `mockito-core/junit-jupiter` | 5.8.0 | 测试 | 可升 5.14+ |

**依赖层面的三个真实风险**：
1. **无依赖治理机制**：没有 `versions-maven-plugin`、没有 `dependency-check`、没有 `enforcer`、没有 `dependabot`。版本靠人肉维护，上述 5 处落后项就是这样积累出来的。
2. **Grizzly 是单点风险**：HTTP + WebSocket 全部压在 Grizzly 4.0.2 上，而 `ServerConfigurator.java:58-62` 的注释明确记录「已用 javap 核实 Grizzly 4.0.2 不提供 WebSocket 单帧上限 API」——框架能力边界已经开始反向约束业务代码（只能在应用层补校验）。迁移成本高（WS 层 1,945 行 + REST 层 9,524 行都绑在 Grizzly/Jersey 上），但不迁就是长期技术债。
3. **`jersey-hk2` 与 `jersey-media-json-jackson` 是名义依赖**：项目没有用 HK2 注入（资源类全是无参构造 + 静态字段），也没用 Jackson 序列化（`Gson` 手写）。它们只增加启动时间与 jar 体积（30 MB 的一部分）。

### 3.2 构建期特殊处理（值得肯定的细节）

| 处理 | 位置 | 说明 |
|---|---|---|
| 版本号单点定义 | `pom.xml:9-12` | 见 1.3 |
| 资源过滤编码钉死 UTF-8 | `pom.xml:205-214` | 注释明确说明「不钉住编码，非 UTF-8 机器上中文注释会乱码」——这类问题通常要踩过才写得出 |
| `build-info.properties` 单独过滤 | `pom.xml:186-196` | 避免被未过滤的 resource 覆盖，注释解释了原因 |
| 排除 MC 插件源码 | `pom.xml:222-225` | `**/minecraft/plugin/**` 依赖 Bukkit，由 `build-mc-plugin.bat` 单独编译 |
| `src/main/java` 下 `**/*.json` 作为资源 | `pom.xml:197-202` | 让语言包能随 jar 走 |
| Surefire 隔离运行期目录 | `pom.xml:236-246` | 把 `xiuxian.plugins.config`、`player-data.dir`、`wilderness.dir` 全指向 `target/`，**避免测试污染真实数据**。注释还记录了动机（「以前测试跑完会在真实数据目录里留下上百个玩家快照」） |
| shade 合并 `META-INF/services` | `pom.xml:263` | 注释标了「关键！」——Jersey 需要 |
| 排除签名文件 | `pom.xml:274-283` | 标准做法 |

**这是全项目工程素养最高的文件**。注释密度高、每条非常规配置都写了「为什么」，不是抄模板。

### 3.3 构建缺失项

| 缺失 | 影响 | 优先级 |
|---|---|---|
| 无静态分析（Checkstyle / SpotBugs / PMD / ErrorProne） | 空 `catch`、未用变量、可疑并发全靠人眼 | 高 |
| 无覆盖率（JaCoCo） | 342 个测试到底覆盖了哪些代码，无人知道 | 高 |
| 无 `maven-enforcer-plugin` | 无法强制 JDK 版本下限与依赖收敛 | 中 |
| 无 `versions-maven-plugin` / `dependency-check` | 依赖落后与 CVE 无法自动发现 | 中 |
| 无 `-Werror` / lint 配置 | 编译告警无人处理 | 中 |
| 无 `spotless` / 格式化约束 | 同一文件里 `setModule(...)` 有时缩进 4 格有时 8 格（如 `PvpCommand.java:50-51`） | 低 |

### 5.1 「重启」这件事被认真对待了（值得单独表扬）

`Main.java:344-492` 用 150 行处理了一个通常被忽略的问题：**自动重启到底该由谁拉起进程**。

- 定义 `RestartMode { SUPERVISED, SELF_SPAWN }`（`Main.java:357`）；
- `restartMode()` 按 `restart.mode` 配置 → `INVOCATION_ID`（systemd）→ `/.dockerenv` / `/run/.containerenv` → `container` 环境变量 依次探测（`Main.java:368-396`）；
- 托管模式下**只 `System.exit(0)`**，绝不自我 spawn —— 注释解释了为什么：systemd 默认 `KillMode=control-group` 会把自我 spawn 的新 JVM 一起 SIGTERM 掉，而 `System.exit(0)` 又不触发 `Restart=on-failure`，结果「服务停在那里没人管」（`Main.java:346-355`）；
- 自我 spawn 模式下保留原 JVM 参数（`-Xmx` 等），但**剔除调试代理** `-agentlib` / `-Xrunjdwp`，避免新进程抢同一个调试端口（`Main.java:430-437`）；
- `waitForPortRelease()`（`Main.java:461-492`）最多等 15 秒让上一个实例释放端口 —— 注释点名了「Windows 上尤其明显」的 `Address already in use`。

这是**教科书级的运维细节**，明显来自真实踩坑。同类项目 99% 会在重启上翻车。

### 6.1 数据库初始化（`initializeDatabase`）

```
database.type=sqlite → jdbc:sqlite:<path> → DatabaseManager.init(url,"","")
database.type=mysql  → 若 host 是 localhost/127.0.0.1/::1 → MySqlLauncher.ensureMySqlRunning()
                     → DatabaseManager.init(url,user,password)
```

两个值得注意的设计：
- **`MySqlLauncher`（431 行）会尝试自动拉起本地 MySQL**。这是「开箱即用」的取向，但代价是：在容器/受限环境下探测与启动外部进程的行为不可控，且 431 行代码用于「让用户不用先装 MySQL」这一件事。**推断**：这是本项目最容易在生产环境出意外的一处。
- **`isLocalDatabase()`（`Main.java:613-646`）用字符串解析 JDBC URL 提取 host**，而不是用 `DriverManager`/`MysqlDataSource` 解析。手工解析对 `jdbc:mysql://user:pass@host` 这类少见写法会判断错，进而错误地触发本地启动。属低风险但可改进。

### 6.2 配置的「双基准路径」（重要陷阱）

| 配置项 | 解析基准 |
|---|---|
| `config/application.yml`、`config/plugins.yml` | **JAR 所在目录** |
| `config/adapters.json`、`xiuxian.db`、`data/`、`log/`、`plugins/` | **进程工作目录** |

两者不一致时 `Main.reportDeploymentPaths()`（`Main.java:495-514`）会 WARN。这是一个**真实存在且容易踩的坑**：同一个 `config/` 目录名，一半按 jar 定位、一半按 cwd 定位。Docker/systemd 通过把两者统一到同一目录来规避，但裸跑用户会中招。**建议**：统一到单一基准（推荐 jar 目录），或至少在启动日志里显式打印两套解析结果。

## 11. 线程模型

| 线程/池 | 来源 | 配置 |
|---|---|---|
| Grizzly IO 线程 | `ServerConfigurator.java:72` `setSelectorRunnersCount(ioThreads)` | `performance.grizzly_io_threads`，默认 **2** |
| Grizzly worker 池 | `ServerConfigurator.java:47-51` | core 4 / max 8 / queue 100，池名 `grizzly-worker` |
| 单线程调度器 | `PlayerService.java:33` | 静态 `Executors.newSingleThreadScheduledExecutor()` |
| 清理调度器 | `Main.java:286-291` | 守护线程 `cleanup-scheduler`，5 分钟周期 |
| 各服务自有调度器 | `EconomyService`、`TradeService`、`FarmService`、`CaveService`、`FormationService`、`SectService`、`WorldBossService`… | 各自 `shutdown*()` 方法，靠关闭钩子收尾 |
| 裸 `new Thread(...)` | **25 处** | 无池化、无命名、无异常处理 |

**风险点**：
1. **worker 池只有 4-8 个线程 + 队列 100**。而玩法逻辑是**同步阻塞的 JDBC**（`getConnection()` 327 处）。Grizzly 队列满 100 后新请求被拒。慢查询（例如 `SectService` 里的大范围扫描）会直接拖垮整个 REST + WS 的吞吐。
2. **没有线程池统一治理**：`Executors.` 出现 16 处、`new Thread(` 25 处，各服务自己建池，没有统一的命名/拒绝策略/监控。关闭时靠一堆 `shutdown()` 静态方法逐个调（`Main.java:97-118`）。
3. **并发正确性靠 `synchronized`（110 处）+ 静态 map**，缺少统一抽象。测试里已有并发用例（`EconomyServiceConcurrencyTest`、`TradeServiceConcurrencyTest`），说明作者意识到问题，但机制层面没有沉淀。

## 12. 关闭时序

`ServerShutdownHook`（`server/ServerShutdownHook.java`）是一个**任务列表 + 顺序执行**的极简框架：

`Main.registerShutdownHook()` 依次加入（`Main.java:86-120`）：
1. `AdapterManager.stopAll()`
2. `gameWebSocketApp.shutdownGracefully()`
3. `motdServer.stop()`
4. `TradeService.shutdown()`（坊市到期回收 + 价格历史清理）
5. `EconomyService.shutdown()`（拍卖结算）
6. `PlayerDataService.shutdown()`（**玩家数据落盘**）
7. `BuiltInPluginRegistry.disableAll()`
8. `DatabaseManager.shutdown()`

`createDefault()` 另外加了 `PluginManager.disablePlugins()`、`stopFileWatcher()`、`PlayerService/FormationService/FarmService/CaveService/BuffService.shutdown*()`。

**优点**：顺序有讲究 —— 先停入口、再停后台任务、再刷数据、最后关池。这是**正确**的顺序。
**缺点**：每个任务都 `try/catch` 只 WARN（`ServerShutdownHook.java:20-28, 37-43`），一个任务挂住（例如 JDBC 卡住）会拖住整个 JVM 退出，而 `Runtime.addShutdownHook` 没有超时机制。**建议**：给每个任务加超时，或用 `ExecutorService.invokeAll(tasks, timeout)`。

## 14. 依赖方向实测

### 14.1 分层是否被打破？

实测探测（`import` 级）：

| 探测 | 命中 | 结论 |
|---|---|---|
| `game/**` 导入 `rest.**` | **0** | ✅ 玩法层不依赖 REST |
| `game/**` 导入 `onebot.**` | **0** | ✅ 玩法层不依赖 QQ |
| `game/**` 导入 `websocket.**` | **0** | ✅ 玩法层不依赖 WS |
| `onebot/**` 导入 `rest.**` | **0** | ✅ 通道之间不互相依赖 |
| `rest/**` 导入 `onebot.**` | **0** | ✅ |
| `plugin/**` 导入 `rest.**` | **0** | ✅ |
| `game/**` 导入 `plugin.**` | **0** | ✅（方向是 plugin → game，`PluginContext` 提供 game 服务） |
| `rest/**` 导入 `game.**` | 62 处 / 4 文件 | 预期（REST 调用玩法） |
| `onebot/**` 导入 `game.**` | 181 处 / ~70 文件 | 预期 |
| `game/**` 导入 `db.**` | **25 处 / 25 个服务** | ⚠ 玩法服务**直接写 SQL**，没有 DAO/Repository 层 |
| `data/**` 导入 `game.**` | 522 处 / 138 文件 | 预期（内容数据依赖框架） |

**这是本项目最值得肯定的架构结论**：**入口层（REST/WS/OneBot/QQ/MC）与玩法层（game）之间是干净的单向依赖，且入口层之间互不耦合**。对一个 8 万行、由多人多轮迭代出来的项目，这个纪律保持得相当好 —— 说明作者一直在刻意避免「在 controller 里写业务」。

**最明显的分层缺陷**：`game/**` → `db.**` 的 **25 个服务直接写 SQL**。没有 Repository/DAO 抽象，导致：
- SQL 与业务逻辑交织在 1,000+ 行的方法里；
- 无法对服务做纯内存单测（必须连库）—— 这直接解释了为什么 `SectService`（2,383 行）这种核心服务**没有单元测试**；
- 方言差异（MySQL/SQLite）要在业务代码里 `if (dialect == SQLITE)` 处理。

### 14.2 服务定位器双轨制：**本项目最严重的结构性问题**

项目同时存在两种获取服务的方式：

| 方式 | 次数 | 例子 |
|---|---|---|
| `ServiceRegistry.getXxxService()` | **312** | `WorldBossService.java:87`、`GameResource.java:83`、`PvpCommand` 外层（`:25`） |
| `new XxxService()` 直接实例化 | **87** | 见下表 |

而**部分服务持有实例级可变状态**：

| 服务 | 实例状态 | 位置 |
|---|---|---|
| `CombatService` | `pendingChallenges`（PvP 待接受挑战） | `CombatService.java:82` |
| `TeamService` | `teams` / `playerTeamMap` / `pendingInvites` / `teamIdGenerator` | `TeamService.java:15-18` |
| `MapService` | `locationCache` / `connections` / `travelTimes` / `eventBias` / `wildernessStubCache` | `MapService.java:69-91` |

于是出现**真实的跨通道状态不一致**：

> **`PvpCommand` 持有自己的 `new CombatService()`**（`onebot/command/pvp/PvpCommand.java:52`），
> 而 **REST 侧 `/pvp/challenge` 用的是 `ServiceRegistry.getCombatService()`**（`rest/GameResource.java:83`）。
> `createChallenge()` 把挑战写进**实例**字段 `pendingChallenges`（`CombatService.java:252`），
> `acceptChallenge()` 从**同一实例**读（`:264`）。
> ⇒ **通过 REST 发起的挑战，QQ 侧 `/决斗 接受` 永远看不到**（反之亦然）。

同类问题还有：
- `SecretRealmService` 里 4 处 `new CombatService()`（`:278, :302, :585, :623`）—— 秘境战斗用的是**第四个**实例；
- `WorldBossService` 用 `ServiceRegistry.getCombatService()`（`:87`）—— 又是另一个实例；
- `BuffService` 的 `EXP_BOOSTS` / `REFLECTION_BUFFS` 是 **static**（`BuffService.java:21,23`），所以 `new BuffService()`（`BuffEffect.java:79,117`、`ExpMultiplierEffect.java:33`、`ReflectionBuffEffect.java:33`、`AttributeResetEffect.java:18`）**恰好**能共享状态 —— 但这是**靠 static 兜住了设计缺陷**，不是设计正确；
- `SectService.java:76,86`、`EconomyService.java:53` 用 `new XxxService().sweepXxx()` 跑后台任务，而前台用的是 registry 实例 —— 目前无害（无实例态），但一旦给这些服务加缓存，立刻变成 bug。

**影响评级：高**。它同时造成（a）真实功能缺陷、（b）测试难以隔离、（c）新人无法判断「该 new 还是该 get」。

**修复方案（成本低、收益高）**：
1. 把 `ServiceRegistry` 改成**真正的启动期装配**（`Main` 里显式 `new` 全部服务并注入），而不是 27 份复制粘贴的懒加载单例；
2. 全项目禁用 `new XxxService()`（可用 Checkstyle/SpotBugs 规则或 `@Deprecated` 构造器 + 单测断言）；
3. 把有状态的服务的状态**外移**（`pendingChallenges` → DB 表或 `ConcurrentHashMap` 静态 + 明确文档）；
4. 用构造器注入替代静态获取（`WorldBossService` 已经这么做了，`WorldBossService.java:82,87`，是全项目最好的范例）。

### 14.3 `ServiceRegistry` 本身的实现质量

`common/service/ServiceRegistry.java` 315 行，**27 个方法完全同构**（`if (x == null) synchronized (ServiceRegistry.class) { if (x == null) x = new X(); } return x;`）。

- 正确性：双检锁 + `volatile` 字段（`:8-35` 全是 `private static volatile`）—— **写法是对的**；
- 可维护性：**27 份复制粘贴**，新增服务必须手写一遍；无法批量操作（例如「关闭所有服务」只能手写）；
- 可测性：静态方法无法 mock，测试只能靠真实实例。

**建议**：`EnumMap<ServiceKey, Object>` + 一个泛型 `get(Class<T>)` + 注册表初始化，可把 315 行压到 ~60 行，并顺带解决「关闭所有」与「测试替换」两个需求。

## 15. 三个"总线"

项目里有三个隐式的「全局总线」，理解它们就理解了运行时的一半：

### 15.1 `ServiceRegistry` —— 服务总线

见 14.2/14.3。`onebot` 调用 160 次、`game` 79 次、`rest` 32 次、`plugin` 21 次、`minecraft` 9 次、`qq` 5 次。

### 15.2 `CommandRegistry` —— 指令总线

`common/command/CommandRegistry.java`，`LinkedHashMap<String, Command>`，**静态**。
- **注册发生在 `Command` 的构造函数里**（`Command.java:80` `CommandRegistry.register(this);`）；
- 因此 `CommandScanner` 只需要 `clazz.getDeclaredConstructor().newInstance()` 就能完成注册（`CommandScanner.java:49`）—— 构造函数有副作用，是「注册」而非「创建」；
- 同名冲突会 WARN（`CommandRegistry.java:31-38`），并注释解释了「扫描顺序不稳定导致谁生效取决于环境」这个真实踩过的坑；
- `get()` 内置**模块门控**（`:49-56`）：模块停用时视同指令不存在，于是「所有指令入口（OneBot/QQ/MC）统一生效」—— 这个设计很聪明，**门控只写一处**。

**评价**：巧妙，但属于「隐式副作用」反模式。若一个 `Command` 子类在构造里抛异常，`CommandScanner` 只记 `failed`（`CommandScanner.java:53-55`），指令静默消失。**建议**：至少把注册改成显式（`registry.register(new XxxCommand())`）或加启动自检「清单中的指令必须全部注册成功」。

### 15.3 `PluginEventManager` —— 事件总线

`plugin/event/` 3 个文件。提供 `PLAYER_LOGIN`、`SERVER_READY` 等事件；`fireQuietly()` 表示「异常不影响主流程」。`GameWebSocketApp.java:181-186`、`Main.java:309-313` 是典型用法。

**评价**：事件点太少（只有登录/服务器就绪这类），玩法层几乎没有事件（例如「玩家突破成功」「物品被使用」都没有事件）。这意味着**插件能挂载的位置很有限** —— 与 `README_PLUGIN.md` 承诺的「扩展命令/物品/事件/秘境/权限/REST/Web UI/WebSocket」相比，「事件」这一项的实际能力偏弱。

## 16. 指令即路由：本项目最独特的设计

### 16.1 机制

```
Command 子类构造
  ├─ super(names[], desc, usage, category, permission, privateOnly, requiresLogin)
  │    └─ CommandRegistry.register(this)                    ← 注册为「指令」
  ├─ setModule("farm")                                      ← 绑定内置模块开关
  ├─ setI18nKeys("cmd.farm.desc", "cmd.farm.usage")         ← 绑定语言包
  └─ registerSub("plant", handler) / addRoute(RouteDefinition.get(...))
       └─ RouteDefinition 描述「OneBot 子命令」和/或「HTTP 路由」
```

- **OneBot 侧**：`Command.execute()` 默认实现按空格切子命令，查 `subIndex` 分发（`Command.java:174-199`）；
- **HTTP 侧**：`UnifiedRestResource` 在首次实例化时收集**所有** `Command.getRestEndpoints()`，按方法分组、按「字面量段数降序」排序，然后用 `{path:.*}` catch-all 线性匹配（`UnifiedRestResource.java:51-69, 86-169`）；
- **门控**：`ModuleGateFilter`（REST）+ `CommandRegistry.get()`（指令）+ 服务层门控，三处统一读 `BuiltInPluginRegistry.isEnabledOrUnknown(module)`。

### 16.2 优点

1. **写一次，三端可用**：新增一个玩法只需写一个 `Command` 子类，QQ 指令 + REST 接口同时获得；
2. **门控单点**：模块开关在一处判断，不会出现「指令关了接口还开着」；
3. **i18n 单点**：描述/用法绑定 key，帮助信息自动多语言。

### 16.3 缺点（真实成本）

| 问题 | 证据 | 影响 |
|---|---|---|
| **catch-all 路由 + 线性扫描** | `UnifiedRestResource.java:72,79` `@Path("{path:.*}")`；`:92` `for (RouteDefEntry entry : candidates)` | 每条未命中 GameResource 的请求都要线性过一遍候选路由；路由规模增长后 O(n)。当前路由数（57 `addRoute` + 82 `registerSub`）尚可接受，但**没有上限保护** |
| **「未命中返回 null」依赖 Jersey 语义** | `:167-168` 注释「返回 404 让 Jersey 尝试其他资源」 | 这是依赖框架未文档化行为的脆弱点；Jersey 升级时可能变 |
| **路由优先级靠「字面量段数」启发式** | `:66-68` | `/sect/info/{id}` vs `/sect/{action}` 这类歧义靠排序猜测，不是真正的路由树 |
| **鉴权语义复杂** | `:97-144`，两段「V8 修复」注释 | admin 上下文与玩家上下文的 userId/playerId 映射有历史包袱（`playerId = 0` 的哨兵值） |
| **同一玩法两套入口实现** | `GameResource` 里 `/pvp/challenge`、`/market/list` 等**显式**端点，与 `Command` 注册的**隐式**端点并存 | 玩家侧接口有两套风格；新人不知道新接口该写哪边 |

### 16.4 评价

这是**有真实价值的架构创新**（对「多端 MUD」这个领域，指令与路由同源是自然且正确的抽象），但实现方式是「catch-all + 线性匹配 + null fallthrough」，属于**能用但脆**。若要长期维护，建议改成显式的路由注册表（启动时把 `RouteDefinition` 直接注册进 Jersey 的 `ResourceConfig`，而不是在运行时线性匹配），或在 `UnifiedRestResource` 里建 trie。

## 17. 数据驱动：四类扫描器

| 扫描器 | 扫描目标 | 注册到 | 产物 |
|---|---|---|---|
| `ItemScanner` | `data.mtxgdn.item` | `ItemRegistry`（静态 `LinkedHashMap`） | 115 个物品 |
| `SecretRealmScanner` | `data.mtxgdn.secretrealm` | `SecretRealmRegistry` | 10 个秘境 |
| `ExplorationEventScanner` | `data.mtxgdn.explorationevent` | `ExplorationEventRegistry` | 13 个事件 |
| `CommandScanner` | `com.mtxgdn.onebot.command` | `CommandRegistry` | 85 个指令 |

**共同实现方式**：反射 + `Class.forName` + `getDeclaredConstructor().newInstance()`，支持「目录」与「jar」两种 classpath 形态（`CommandScanner.java:61-123`）。

**内容数据有多简洁**（这是设计上的成功）：

```java
// data/mtxgdn/item/HealingPill.java —— 全文 13 行
public class HealingPill extends Item {
    public HealingPill() {
        super("mtxgdn", "healing_pill", ItemType.CONSUMABLE, ItemRarity.COMMON,
            99, 10, true, 0, HealEffect.hp(50));
    }
}

// data/mtxgdn/secretrealm/WildGrassland.java —— 全文 9 行
public class WildGrassland extends SecretRealm {
    public WildGrassland() { super("mtxgdn", "wild_grassland", 0, 120_000); }
}
```

**扫描器的已知缺陷**（作者已在 `docs/PROJECT_STRUCTURE.md:1141` 记录）：
- 只接受**无参构造**，因此 `FormationItem`（需要参数）永远注册失败，只在启动日志里出现一行「失败：缺少无参构造」；
- 目录扫描用 `File.listFiles()`，**顺序不保证**（这正是指令重名问题「谁生效看环境」的根因）；
- 扫描失败只进 `ScanResult.failed` 列表，**不阻断启动**。对内容数据这是合理的（降级），对指令则意味着「少了一条指令但服务照跑」。

**建议**：内容数据改用声明式格式（YAML/JSON，与 `realm_config.json` 一致），可彻底摆脱「一个物品一个类」和反射扫描。当前 138 个文件、2,295 行，改成 3 个 YAML 文件后维护成本会大幅下降，且能被非程序员编辑。

### 19.3 值得单独表扬：无限野外分片世界

这是全项目**技术含量最高**的一块（`game/map/` + `MapService` 野外部分）：

1. **地形是纯函数**：`WildernessTerrain` 的类注释明确两条不变量——地形 = `f(worldSeed, chunkX, chunkY)`，节点 id = 坐标的纯函数（`WildernessTerrain.java:10-39`）。因此**野外不进数据库**，`map_locations` 里没有一行属于野外。
2. **id 编码与配置解耦**：`ID_BASE + chunkKey * SLOT_STRIDE + slot`，而 `SLOT_STRIDE` 固定 64（`:29-32` 注释解释了"写成 `chunkSize²` 会让改配置时所有探索记录失效"）——这是**为未来改配置留出兼容性**的设计。
3. **只落盘可变状态**：分片文件仅存探索记录/资源库存/补货时间（1~3 KB/片）；写入用 `.tmp` + `ATOMIC_MOVE`（`WildernessChunkStore.java:48`）；`seedHash` 不匹配则丢弃重建（`:116-118`）。
4. **并发粒度正确**：`WildernessChunkStore` 方法级 `synchronized`，资源扣减下沉到**分片级** `synchronized`（`WildernessChunk.consume/refund/restock/markExplored`），比整表锁细；`markExplored` 置 `pinned=true` 保证"已探索永不回收"。
5. **采集有回滚**：`gather` 先从当前节点扣库存 → 存盘 → 发物品；发物品或写冷却失败则 `chunk.refund` + 再存盘（`MapService.java:1792-1810`）。
6. **数据库体积不随世界扩张增长** —— 对"无限世界"这是唯一可行的架构。

**唯一缺陷**：`MapService` 侧的三层缓存（`locationCache`/`wildernessCache`/`wildernessStubCache`）是裸 `LinkedHashMap`/`HashMap`，与 `synchronized` 的 `reload()` 竞争（见 P0-5）。**分片存储层是安全的，缓存层不安全** —— 修的时候不要动前者。

### 20.2 事务模型（最重要的数据层结论）

| 写法 | 处数 | 说明 |
|---|---|---|
| `DatabaseManager.runTransaction(SQLFunction)` | **72** | 唯一规范入口；分布：`EconomyService` 12、`FarmService` 10、`SectService` 9、`ItemService` 6、`BuffService` 5… |
| 手写 `setAutoCommit(false)` | 9（7 个文件） | `PlayerService.deletePlayer`、`PlayerDataService.restorePlayer`、`PermissionService`×2、`AdminResource.deleteUser`、`DebugCommand` |
| `executeInTransaction(SQLRunnable)` | **0** | 定义了但从未使用——死代码 |

**跨服务事务传播靠手工 `Connection` 重载**（`addItem(conn, ...)`、`addStat(conn, ...)`…）。这个约定**已经被打破**：

> `BuffEffect.execute(Connection conn, ...)`（`BuffEffect.java:113-149`）收到了 `conn`，
> 但在 `durationSeconds > 0` 分支调用的是 `buffService.addBuff(playerId, ...)`（`:119`），
> 而 `BuffService` **只有无 `Connection` 的 `addBuff`**（`BuffService.java:163`）。
> ⇒ **吃丹药时，Buff 写入落在另一个连接、另一个事务里，丹药事务无法覆盖它。**

**`DebugCommand` 的"事务沙箱"是假的**（`DebugCommand.java:143-150`）：它 `setAutoCommit(false)` 后执行目标指令，最后 `rollback()`——但目标指令通过 `ServiceRegistry` 拿到的是**池里的另一个连接**，其写入已提交。这个 rollback 什么也没撤销，却给了运维"调试是安全的"的错误预期。

### 20.3 持久化策略：DB 单写 + 定期文件快照

必须澄清一个常见误解：**玩家 JSON 文件不是主存储，DB 才是**。

- 所有写入先落 DB，成功后只调 `markDataDirty(playerId)`（仅把一个 id 放进 `Set`，**无 I/O**）；
- `flushDirty()` 每 `player-data.auto-sync-seconds`（默认 30s）对脏玩家 `exportPlayer(id)` → 读 DB 全表 → 写文件；
- 文件 → DB 的回流只有一条路：`restorePlayer`，且默认 `self-restore: false`。

**快照的工程质量很高**（`PlayerDataService` 884 行）：
1. 读失败即导出失败（不产出"缺表的完整快照"）；
2. **写后回读校验**：写 tmp → 读回反序列化 → 重算 `rowCount` + `checksum`（SHA-256）→ 再写 → 再回读比对；
3. 覆盖前保留 `<id>.json.bak`；
4. 还原时强制跳过 `user_id`/`id`/`created_at`/`updated_at`（防止把角色挂到他人账号）；
5. 注释记录了一个真实踩坑：摘要必须算在**解析后的规范形态**上，因为 JDBC 的 `Long` 读回 JSON 会变 `Double`（`123` vs `123.0`）——"这正是最初版本每次导出都报摘要不一致的原因"。

**宕机丢数据窗口**：`kill -9` / 断电 → **DB 层零丢失**（全部同步 JDBC 写，SQLite WAL 已提交事务持久）。文件快照最多丢 30 秒，且只是备份。**唯一真实风险是 `MySqlLauncher` 在 shutdown hook 里对 mysqld 执行 `destroy()` → 5 秒 → `destroyForcibly()`（SIGKILL）**，可能导致 InnoDB 崩溃恢复，且会连带杀死同机其它应用的 MySQL。

### 21.1 两套并行的"插件"概念

|---|---|---|
| 载体 | `plugins/*.jar`（独立 `URLClassLoader`） | 编译进主 jar |

**这是本模块最大的认知负担**：两套系统互不相通，而文档只覆盖一套。

### 21.2 `PluginManager` 生命周期

`init()` → `loadPlugins()`（扫 `plugins/`）→ `enablePlugins()` → 运行期 `enable/disable/reload/unload` + 可选热重载文件监听 → `disablePlugins()` → `stopFileWatcher()`。

`PluginClassLoader`（59 行）是**父优先**的 `URLClassLoader`，只对插件自己的 jar 做隔离——**无法隔离传递依赖**，两个插件带不同版本的同名库会互相覆盖。这对"完全可信插件"模型是可接受的，但对第三方生态不够。

`PluginContext`（423 行）暴露：服务获取（21 个 `getXxxService`）、`Connection`、`AppConfig`、`JwtUtil`、文件 IO、事件注册、i18n 合并、REST 资源注册、Web UI 注册、WebSocket handler 注册。

> **安全定位**：`plugins/` 目录的写权限 ≈ **RCE**。这在单机自建场景是合理取舍，但必须写进文档（当前 `README_PLUGIN.md` 未强调）。另外插件 `loadLang()` 可**覆盖任意内置 key**（含 `admin.*`/`error.*`）且停用后不回滚（`I18nManager.mergeFromStream` 只增不删）——恶意插件能篡改"权限不足"提示。

### 21.3 关键发现：25 个玩法模块是**空壳**

`builtin/` 下 25 个类 + `experimental/` 下 2 个类，`onEnable`/`onDisable` **全部只有一行 `logger.info("XXX系统已启用")`**：

```java
// builtin/FarmPlugin.java 全文 38 行
@Override public void onEnable(PluginContext context) {
    context.getLogger().info("农场系统已启用");
}
```

**它们不注册任何东西、不持有任何状态。** 真正的门控逻辑散落三处：
1. `Command.isModuleEnabled()`（指令分发时）；
2. `ModuleGateFilter`（HTTP 请求按路径首段，**35 条硬编码映射**）；
3. 各 `*Service` 内部的 `isEnabledOrUnknown("xxx")` 早退（**11 处**，分布在 7 个服务）。

**结论**：「内置插件」实际是一个**配置开关层**，不是模块化边界。玩法代码（`game/service` 约 2 万行）与插件框架完全没解耦——关掉 `farm` 只是让 `FarmService` 某方法提前 `return`，`FarmService` 仍被 `ServiceRegistry` 实例化、仍被 `GameWebSocketApp` 静态持有。

**一个真实风险**：`ModuleGateFilter` 的 35 条映射与 `PluginCatalog` **没有任何自动一致性校验**。新增玩法模块时若忘了往映射表加一行，该模块的所有 HTTP 接口就**永久绕过门控**，而现有测试（`BuiltInModuleSetTest`）只校验 `PluginCatalog` ↔ `plugins.yml`。

### 21.4 事件系统

### 22.2 Filter 链（**本节是全项目最关键的安全分析**）

按 JAX-RS 规范（未标 `@Priority` 的过滤器默认 `Priorities.USER = 5000`），实际执行顺序：

```
 900  LanguageRequestFilter   协商语言 → I18nContext.set(lang)
1000  AdminAuthFilter         /admin/* 管理 JWT（含登录锁定 5 次/15 分钟）
1950  ModuleGateFilter        /game/* 按首段查模块开关，停用则 403
2000  PermissionFilter        读 @RequirePermission → PermissionService.hasPermission
3900  EntityBufferFilter      POST body 预读成 byte[] 塞回 entityStream（上限 64 KB）
5000  JwtAuthFilter           ← 解析玩家 Bearer token，setProperty("userId")
（响应）3000 LanguageCleanupFilter → I18nContext.clear()
```

### 🔴 P0-7：`JwtAuthFilter` 缺 `@Priority`，排在 `PermissionFilter` **之后**

- `JwtAuthFilter` 只有 `@Provider`（`JwtAuthFilter.java:10-11`），**没有 `@Priority`** → 默认 5000；
- `PermissionFilter` 是 `@Priority(Priorities.AUTHORIZATION)` = 2000（`PermissionFilter.java:18`）；
- `PermissionFilter` 从 `requestContext.getProperty("userId")` 取 id（`:65-80`），取不到就 `abortWith(401 "未登录")`；
- 而 `userId` 正是 `JwtAuthFilter` 在 `:70` 写入的。

**⇒ `GameResource` 的 102 个 `@RequirePermission` 端点在鉴权时 `userId` 恒为 `null`，一律返回 401。**

**为什么线上没被发现**（推断，但逻辑自洽）：
- 真实玩家流量走 OneBot 指令与 WebSocket，`GameResource` 的 REST 只是辅助面；
- `/api/admin/*` 由 `AdminAuthFilter`（1000）负责，它在 `PermissionFilter` 之前就写入了 `adminRole`/`adminUserId`（`AdminAuthFilter.java:244` 只对 `admin/me`、`admin/whoami` 写 `userId`），所以**管理后台的 94 个端点工作正常**；
- 现有安全测试（`AdminWritePermissionTest`、`EndpointAlignmentTest`）全是**反射/源码级静态断言**，没有一个是真跑"登录 → 调受保护端点"的端到端用例。

**修复**：给 `JwtAuthFilter` 加 `@Priority(Priorities.AUTHENTICATION + 10)`（= 1010），并补一个 `JerseyTest` 端到端用例。
**验证方式（强烈建议先做）**：启动服务 → 用玩家 JWT 调 `GET /api/game/inventory`（该端点带 `@RequirePermission`）→ 若返回 401 即证实。

> ⚠️ 本条为**静态分析结论**，未做运行时验证（本次分析不编译、不启动服务）。请在修复前用一次真实请求确认。

### 22.4 权限模型的结构性缺陷

73 个权限码 + 5 个内置组（`SUPER_ADMIN`/`ADMIN`/`MODERATOR`/`PLAYER`/`GUEST`）的分层设计本身是合理的，但有四个短路/缺口：

## 24. 消息通道适配器（`adapter` 719 + `onebot` 13,044 + `qq` 2,206 + `minecraft` 4,739 行）

### 24.1 三层结构


**适配器本身几乎不含业务逻辑** —— 只做三件事：把外部协议归一化成 `CommandContext`、把回复写回通道、维护身份绑定（QQ号/openid/MC UUID ↔ `user_id`）。这是**正确的分层**。

### 24.2 🔴 P0-1：OneBot 通道**完全没有鉴权**，且绑定 `0.0.0.0`

```java
// adapter/AdapterManager.java:330-334
NetworkListener listener = new NetworkListener("onebot-" + cfg.getId(), "0.0.0.0", port);
...
```

**声明式程度极高**：

```java
// data/mtxgdn/item/HealingPill.java 全文 13 行
public class HealingPill extends Item {
    public HealingPill() {
        super("mtxgdn", "healing_pill", ItemType.CONSUMABLE, ItemRarity.COMMON,
            99, 10, true, 0, HealEffect.hp(50));
    }
}
```

**物品体系**：`Item` 基类 + 13 个效果实现（`HealEffect`/`ExpEffect`/`ExpMultiplierEffect`/`BuffEffect`/`ReflectionBuffEffect`/`DebuffCleanEffect`/`TeleportEffect`/`LearnSkillEffect`/`InventoryCapacityEffect`/`AttributeResetEffect`/`RebirthEffect`/`PurificationEffect`/`CurrencyEffect`）+ 4 档稀有度 + 类型枚举。

**实际内容分布（实测 115 个物品）**：

| 维度 | 分布 |
|---|---|
| 类型 | `MATERIAL` 61 / `CONSUMABLE` 23 / `TREASURE` 9 / `SEED` 8 / `CURRENCY` 4 / `QUEST` 4 / `SKILL_BOOK` 3 / **`EQUIPMENT` 0** |
| 稀有度 | `RARE` 29 / `EPIC` 27 / `UNCOMMON` 21 / `LEGENDARY` 17 / `COMMON` 16 / `MYTHIC` 4 |
| **效果** | **79 个（69.3%）用 `EmptyEffect.INSTANCE`——即"有物品、无实效"**（绝大多数是 `MATERIAL`） |

> 69.3% 的物品无效果本身不是 bug（材料类物品本就不该有效果），但它说明**"115 个物品"这个数字不能直接当作内容量**：真正可交互的消耗品/技能书/珍宝只有约 36 个。

**扩展一个新物品的成本**：新建 1 个类（约 14 行）+ 在 `zh_cn.json`/`en_us.json` 各加 2 个词条（`item.<key>.name`/`.desc`）+ 重启。**这个成本是低的**，是这个设计最大的优点。

**四个问题**：
1. **`ItemType.EQUIPMENT` 零使用**（115 个物品中）——装备走 `EquipmentDataChecker` + `players_equipment` 的另一条路径，死枚举误导扩展者；
2. **探索事件不是"数据"而是"带行为的插件"**：`TrapEvent`/`SpiritSpringEvent` 直接 `DatabaseManager.getConnection()` + 裸 SQL 改 `players` 表（绕过 `PlayerService`，**不调 `markDataDirty`**，HP 变化不进快照），其中 `SpiritSpringEvent.java:41` 还用了 MySQL 专有的 `LEAST(max_hp, hp + ?)` → **SQLite（默认配置）下每次触发必抛异常**；
3. 秘境下标不稳定：`SecretRealmRegistry.getByIndex(int)` 按 `requiredRealm` 排序后 1-based 取下标（`:82-88`）→ 新增秘境会改变既有下标，玩家 `/秘境 1` 指向的目标会变；
4. **四个扫描器的 `resource.getPath()` 都没有 URL 解码**（`ItemScanner`/`SecretRealmScanner`/`ExplorationEventScanner`/`CommandScanner`）→ 部署路径含非 ASCII 字符（如中文目录）时，`File` 构造失败，**内容静默消失**（只在启动日志里表现为"注册数量为 0"）。

## 29. 测试体系

### 29.1 真实数字

| 指标 | 数值 |
|---|---|
| 测试文件 / 行数 | **44** / **10,251**（占主源码 12.2%） |

| 使用 Mockito 的类 | **1**（`LanguageRequestFilterTest`，9 个用例） |
| 继承 `TestBase`（真实建库）的类 | **20** |

### 29.2 测试风格：不是"单元测试"，而是"以真实 SQLite 为载体的服务层集成测试"

设计意图很清楚——**不做"测 mock"的假测试，而是喂真库跑真逻辑**。三种非典型但很有价值的手法：

1. **反射静态分析**（无运行时依赖，纯架构护栏）：
   - `EndpointAlignmentTest`：收集全部 HTTP 路由 → method → 权限码，断言三通道对齐；
   - `AdminWritePermissionTest`：把"只读权限码不得门控写端点"变成可执行断言；
   - `CommandNameConflictTest`：扫指令名唯一性（锁定历史 4 组重名事故）。
2. **注入固定随机源**：`BreakthroughPityTest` 用 `RealmService.setRandomForTest` 把概率玩法变成可断言逻辑——**避免了 `while(retry<1000)` 撞运气式测试**。
3. **真并发**：`TradeServiceConcurrencyTest`（2/4 线程同时撤单与抢购，断言"只有 1 个成功"且"物品恰好退回一次"）、`EconomyServiceConcurrencyTest`。

### 29.3 测试质量亮点

- **断言是行为断言，不是"跑通即通过"**：例如断言物品守恒（撤单退回 + 买家获得 == 10）、灵石守恒（买家支出 == 卖家所得 + 抽成）。这类不变量断言能抓住普通功能测试发现不了的经济漏洞。
- **每个测试类的 Javadoc 写清了"为什么需要这个测试"**（历史 bug 编号、线上现象、曾长期红灯的原因）。
- **测试写文件全部重定向到 `target/`**（surefire 注入 `xiuxian.plugins.config` / `player-data.dir` / `wilderness.dir`），工作区不被污染。
- **契约型测试防清单漂移**：`BuiltInModuleSetTest`（插件清单 ↔ 配置键）、`MapWildernessTest`（采集配置里的物品 key 必须真实存在）。

### 29.5 测试的具体缺陷

1. **2 个空测试**：`PlayerServiceTest.java:41-51` 两个方法体都是 `assertTrue(true)`，`@DisplayName` 却写着 `getFinalAttack should apply title bonus` / `addGold should increase player gold`。**这类"假绿"比没有测试更糟**——它让用例数虚高，也让人误以为称号加成与金币增加已被覆盖。
2. **共享数据库 + 顺序耦合**：`LegacySchemaUpgradeTest.java:27-30` 自己承认——Windows 上因连接池持有文件句柄，删库会失败 → 前一个测试类的夹具行污染后一个类（"曾导致 `MapServiceTest` 断言 15 个地点时读到 16 个"）。**已记录、未根治**，让"单独跑绿、全量跑红"成为可能。
3. **`@TestMethodOrder` 剧本式测试**（`MultiPlayerFullTest`、`CombatServiceTest`）依赖前序用例副作用 → 一挂就是连锁挂，失败信息指向最后一个用例而非根因。
4. **"环境未就绪就 return"式跳过**（`TradeServiceConcurrencyTest.java:252,306`）：`if (!ready) { println("跳过"); return; }` **记为通过而非 skipped** → 并发测试最关键的断言可能被静默放弃。
5. **`MultiPlayerFullTest` 里的反射兜底**（`:378-420` 用 `getDeclaredField("id")` 逐级找父类字段）→ 字段改名时测试不报错，只打印一行 `○`。把"失败"降级成"提示"。
6. `src/test/resources/` **不存在** → 测试所需数据全部取自 `src/main` 的类路径资源，测试与生产资源强耦合。

## 39. 反面清单：这些设计**不应该**在重构中被改掉

评审时最容易"顺手重构掉"但实际是项目精华的部分：

1. **无限野外的纯函数地形**（`WildernessTerrain`）——"地形 = 种子函数、只落盘可变状态、`SLOT_STRIDE` 与配置解耦、`seedHash` 不匹配即重建"。改掉任何一条都会让数据库体积随世界扩张增长。
2. **世界 BOSS 的四条不变量**（无内存态 / 无定时器 / 按伤害分红 / 超发熔断）——重启后血条与冷却原样还在，这是正确性设计。
3. **`compareAndSetTravel` 的 CAS 移动**（`MapService.java:876`）——防止并发重复扣时间。
4. **农场惰性结算**（按 `settled_time` 推算，不依赖定时器）——比"每秒 tick 全服农田"优得多。
5. **拍卖的事务内 `FOR UPDATE` + 前手退款**（`EconomyService.createAuction/placeBid`）。
6. **`TokenBlacklist` 的内存 + DB 双层 + 只存摘要**（`TokenBlacklist.java:14-33`）。
7. **玩家快照的"写后回读校验 + 规范形态摘要"**（`PlayerDataService.java:199-203` 的注释解释了 `123` vs `123.0` 的坑）。
8. **WebSocket 在反序列化之前做帧长校验**（`GameWebSocketApp.java:85-103`）。
9. **重启模式探测**（`Main.java:344-492` 的 `SUPERVISED`/`SELF_SPAWN`、剔除调试代理、等端口释放）——这是运维正确性的核心。
10. **`ServiceRegistry` 的双检锁 + `volatile` 写法本身是对的**（问题在"双轨"与"无 reset"，不在锁）。
11. **`Command` 的模块门控单点化**（`CommandRegistry.get()` 内置 `isModuleEnabled()`）——让"停用玩法"在所有通道一致生效。
12. **`AdminAuthFilter` 的登录失败锁定 + 域分离派生密钥**（`admin.jwt_secret` 缺失时用 `jwt.secret` 做 HMAC 域分离，重启后 token 仍有效）。
